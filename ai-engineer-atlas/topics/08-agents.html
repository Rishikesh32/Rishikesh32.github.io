AI agents

An agent is a language model running in a loop: it decides what to do, calls a tool, reads the result and decides again until the task is done. This area teaches you to build that loop, give it good tools and memory, connect it to the world through MCP, and keep it safe when it can take real actions.

In this area

    Everything in this area hangs off one loop. The model reads its context, picks an action, a tool runs, and the result goes back into the context. Tool design decides what actions exist. Planning and reflection decide how well the model picks among them. Memory decides what stays in the context as the loop runs long. Multi-agent systems run several loops that talk to each other. MCP standardises how tools and data plug into the loop, computer use extends the action space to screens and browsers, and guardrails sit between the model's decision and the real world.

    08.1 · Core mechanism

    The agent loop

    A chat model answers once. An agent keeps going: the model either answers or asks for a tool, your code runs the tool, appends the result, and calls the model again. That while-loop, about twenty lines of code, is the whole architecture.

    Why it matters for AI engineers

    Coding assistants, research bots and support agents are all this loop with different tools, and every agent bug shows up in one specific turn.

    Think, act, observe, repeat

    In the think step the model reads its whole context and emits either text or a structured tool call: a tool name plus JSON arguments. In the act step your harness runs that call. In the observe step the output is appended as a tool result, and the loop repeats.

    The model only proposes. Your harness decides what runs, which is where logging and guardrails live.

    The loop in code

    Here it is with the Anthropic Python SDK. Other providers use the same shape with different field names.

    import json, os
import anthropic

client = anthropic.Anthropic()
MODEL = os.environ["AGENT_MODEL"]       # pick a current tool-capable model id

tools = [{
    "name": "get_weather",
    "description": "Current weather for a city. Returns temperature in C and conditions.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string", "description": "City name, e.g. 'Lisbon'"}},
        "required": ["city"],
    },
}]

def get_weather(city: str) -> dict:
    return {"city": city, "temp_c": 21, "conditions": "sunny"}   # stub

REGISTRY = {"get_weather": get_weather}

def run_agent(goal: str, max_steps: int = 10) -> str:
    messages = [{"role": "user", "content": goal}]
    for step in range(max_steps):
        resp = client.messages.create(model=MODEL, max_tokens=1024,
                                      tools=tools, messages=messages)
        messages.append({"role": "assistant", "content": resp.content})
        if resp.stop_reason != "tool_use":              # model chose to answer
            return "".join(b.text for b in resp.content if b.type == "text")
        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                out = REGISTRY[block.name](**block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": json.dumps(out)})
            except Exception as e:                       # errors become observations
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"Error: {e}", "is_error": True})
        messages.append({"role": "user", "content": results})
    return "Stopped: step limit reached."

    Three details matter: append the assistant's tool-call message verbatim so result ids pair up, return all parallel tool results in one message, and turn exceptions into error observations the model can fix.

    Stop conditions, cost and when not to loop

    Every loop needs exits: a final answer, a step limit, a token or dollar budget, a timeout and a repeated-error limit. Because each call resends the whole history, input tokens grow roughly quadratically with steps.

    \[ \text{total input tokens} \approx \sum_{n=1}^{N} \left(P + n\,\Delta\right) = NP + \Delta\,\frac{N(N+1)}{2} \] \(P\) is the fixed prefix (system prompt and tool definitions), \(\Delta\) the tokens added per step, \(N\) the number of steps. The quadratic term is why long runs need compaction (08.4).

    If you know the steps in advance, a workflow (a fixed chain of LLM calls) is cheaper and easier to test.

    Key ideas
    • An agent is an LLM called in a loop, with tool results appended each turn.
    • The model proposes; your harness executes and stays in control.
    • Always set exits: answer, step limit, budget, timeout, error limit.
    • Use a fixed workflow when the steps are known.
    Common mistakes
    • No step or budget limit, so one run calls a failing tool 200 times.
    • Dropping the assistant's tool-call message, which breaks call-id pairing.
    • Building an agent where a three-step workflow would do.

    08.2 · Agent-computer interface

    Tool design

    The model sees your tools only through their names, descriptions and parameter schemas, and learns what happened only from the text you send back. A tool is a user interface for a fast, literal reader who has never seen your codebase.

    Why it matters for AI engineers

    Most production agent failures trace back to tools: a vague description, an argument the model keeps getting wrong, a huge payload that floods the context, or an error it cannot recover from. Fixing tools usually beats tweaking prompts.

    Anatomy of a tool call

    A definition has a name (a verb phrase like search_orders), a description saying when to use it and what it returns, and an input schema in JSON Schema with types, enums and ranges. All three are sent on every call, so they cost tokens and steer behaviour.

    Results and errors are prompts too

    Return only what the next decision needs, paginate with a visible note ("20 of 312; refine with date_from"), and validate arguments before running anything. Pydantic can generate the schema and produce compact validation messages.

    from typing import Literal
from pydantic import BaseModel, Field, ValidationError

class SearchOrders(BaseModel):
    """Search one customer's orders. Use before refunds to confirm the order exists.
    Returns at most `limit` orders, newest first: id, date, total, status."""
    customer_id: str = Field(description="Customer id like 'C-1042'")
    status: Literal["open", "shipped", "refunded"] | None = None
    limit: int = Field(10, ge=1, le=20)

# Pydantic generates the JSON Schema you pass to the model
tool_def = {
    "name": "search_orders",
    "description": SearchOrders.__doc__,
    "input_schema": SearchOrders.model_json_schema(),
}

def call_search_orders(raw_args: dict) -> tuple[str, bool]:
    try:
        args = SearchOrders.model_validate(raw_args)
    except ValidationError as e:
        # actionable, compact error the model can fix next turn
        msgs = "; ".join(f"{'.'.join(map(str, x['loc']))}: {x['msg']}" for x in e.errors())
        return f"Invalid arguments: {msgs}", True
    rows = db_search(args.customer_id, args.status, args.limit)   # your data layer
    lines = [f"#{r.id} {r.date:%Y-%m-%d} {r.total:.2f} {r.status}" for r in rows]
    return f"{len(rows)} orders:\n" + "\n".join(lines), False

    Granularity and idempotency

    Wrapping every REST endpoint as its own tool forces the model through long chains, and every step can fail. One tool that matches a real intent does the chaining in reliable code. If the agent always calls A, B, C in order, merge them.

    Agents also retry, so make writes idempotent: the same call twice leaves the same end state, for example via an idempotency key. Label read and write tools clearly so policies (08.8) can treat them differently.

    Design choiceWeak versionStrong version
    Namedo_querysearch_orders
    Parameterstatus: stringstatus: enum[open, shipped, refunded]
    Result sizeRaw API JSON, 30k tokens20 rows, key fields, "312 total" note
    ErrorError 400"date_from must be YYYY-MM-DD"
    WritesRetries create duplicatesIdempotency key, dry-run option
    Key ideas
    • Name, description and schema are the model's only view of a tool.
    • Constrain arguments with enums and ranges; validate before running.
    • Return concise results and errors that say how to fix the call.
    • Merge tools that are always chained; make writes idempotent.
    Common mistakes
    • One tool per REST endpoint, leaving the model to chain fifteen calls.
    • Raw API payloads that bury the one field that matters.
    • Overlapping descriptions, so the model picks between tools at random.

    08.3 · Deciding well

    Planning & reflection

    A bare loop makes one greedy decision at a time. Planning lays out the steps before acting so the agent does not wander. Reflection looks back at the result and checks it against the goal so the agent catches its own mistakes.

    Why it matters for AI engineers

    On long tasks the usual failures are drift, premature "done!" and repeating a failed approach. Plans, checklists and verification steps are the cheapest fixes.

    ReAct and plan-and-execute

    ReAct (reason plus act) writes a short thought before each tool call. Modern tool-calling APIs and reasoning models do this natively.

    Plan-and-execute has a planner write a numbered list, an executor work through it, and a re-planner revise the rest after each step. Allow revision, because a plan written before seeing data can be wrong.

    Same task, three strategies Try it

    Reflection needs evidence

    Reflection means critiquing an output and trying again with the critique in context. Reflexion stored short written lessons from failed attempts and improved coding and reasoning scores without any weight updates.

    Ground the critique in real evidence. A model shown failing test output has something to fix; one asked "is this correct?" usually says yes.

    def solve_with_reflection(task, attempt_fn, verify_fn, critique_fn, max_tries=3):
    """attempt_fn(task, lessons) -> candidate
       verify_fn(candidate)      -> (ok: bool, evidence: str)   e.g. run the tests
       critique_fn(task, candidate, evidence) -> short lesson text (an LLM call)"""
    lessons = []
    for i in range(max_tries):
        candidate = attempt_fn(task, lessons)
        ok, evidence = verify_fn(candidate)          # grounded signal first
        if ok:
            return candidate, i + 1
        lessons.append(critique_fn(task, candidate, evidence))
    return None, max_tries                            # report failure honestly

    Searching over thoughts

    Tree of Thoughts turns reflection into search: propose several next thoughts, score them, expand the best and backtrack from dead ends. Best-of-n is the cheap cousin: sample n full answers and keep the one a verifier rates highest.

    Reasoning models now plan, check and backtrack inside one response, so they need less scaffolding. Keep a plan file, real verifiers and a rule that "done" requires passing checks.

    PatternExtra callsBest forWatch out for
    ReActNone (thought per step)General tool useMyopic, can loop
    Plan-and-execute1 plan + re-plansMany sub-tasks, human plan reviewStale plans
    Reflection / Reflexion1 critique per attemptTasks with a verifierSelf-approval without evidence
    Tree of Thoughts / best-of-n\(b\) branches per step, or \(n\) samplesSearch problems, puzzlesCost grows fast
    Key ideas
    • ReAct interleaves a short thought with each action.
    • Plan-and-execute writes steps first and must allow re-planning.
    • Reflection needs grounded evidence such as test output.
    • Tree of Thoughts and best-of-n buy accuracy with many more calls.
    Common mistakes
    • Asking "is this correct?" with no evidence and trusting the yes.
    • Declaring success before running the check that proves it.
    • Heavy planning scaffolding around a reasoning model that already plans.

    08.4 · Context engineering

    Memory & context management

    A model has no memory between calls. All it knows about the task is the text in its context window right now. Agent "memory" is the set of decisions you make about what goes into that window and what moves out to storage, often called context engineering.

    Why it matters for AI engineers

    Long runs hit the context limit, and well before that they get slower, pricier and less accurate as stale tool output piles up. Assistants that remember users across sessions need a store and a retrieval path. Both are your job.

    The context window is a budget

    Five tenants share the window: the system prompt, tool definitions (a few hundred tokens each), the growing history, retrieved documents and an output reserve for the reply and any thinking tokens. Even when everything fits, models attend less reliably to facts buried mid-context.

    The widget assumes 350 tokens per tool and 2,200 per step; compaction keeps 8 steps plus a 1,500-token summary.

    Short-term memory: trim, compact, write notes

    Trimming replaces old tool outputs with stubs like "[search_logs output, 5,012 tokens, omitted]". Compaction has the model summarise goal, decisions, facts, open TODOs and exact identifiers, then restarts from that summary plus recent turns. Scratchpad files such as todo.md survive any number of compactions.

    def compact(messages, llm, keep_recent=8, max_tokens=1500):
    """Replace all but the last `keep_recent` messages with a summary."""
    old, recent = messages[:-keep_recent], messages[-keep_recent:]
    if not old:
        return messages
    prompt = ("Summarise this agent transcript for your future self. Keep: the goal, "
              "decisions and why, facts learned, files changed, open TODOs, and exact "
              "identifiers. Drop raw tool output.\n\n" + render(old))
    summary = llm(prompt, max_tokens=max_tokens)
    head = {"role": "user", "content": f"[Summary of earlier work]\n{summary}"}
    # keep the system prompt and tool definitions outside `messages` so the cached prefix stays stable
    return [head] + recent

    Long-term memory and caching

    Long-term memory persists across sessions. On write, extract candidate facts, dedupe them and store them with embeddings, timestamps and sources. On read, search (as in RAG, Area 07) and insert the top few. A small always-loaded memory file works well for a few hundred facts. MemGPT framed this as paging between a small main context and a large external store.

    Prompt caching lets providers reuse an identical prompt prefix at lower cost and latency. Keep stable content first and append new content at the end.

    Key ideas
    • The model is stateless; memory is what you put in each call.
    • Budget the window, including an output reserve.
    • Trim old outputs, compact history, keep notes in files.
    • Keep the prompt prefix stable so caching works.
    Common mistakes
    • Forgetting the output reserve, so answers get cut off.
    • Summaries that drop exact identifiers the agent needs later.
    • A timestamp at the top of the prompt, which breaks caching on every call.

    08.5 · Many loops

    Multi-agent systems

    A multi-agent system runs several agent loops, each with its own prompt, tools and context window, and connects them. The gains are parallelism and clean, focused contexts. The costs are more tokens and new failures at the handoffs.

    Why it matters for AI engineers

    Deep-research products, large codebase searches and document pipelines split work across agents. You need to tell when a split helps and when it only multiplies cost.

    Three core topologies

    Orchestrator–workers: a lead writes briefs, workers (sub-agents) run in parallel with fresh contexts, and the lead merges condensed results. Pipeline: agents run in a fixed sequence, each transforming the last output. Debate: agents propose, critique each other and a judge decides.

    Multi-agent pattern switcher Try it

    Handoffs, shared state and cost

    A worker sees only its brief. A good brief states objective, scope, what others cover, output format and a budget. Results should come back condensed, while full artefacts go to a shared store such as files or a database.

    A handoff is different: one agent passes the whole conversation and control to a specialist, like triage passing a billing question to a billing agent. Cost multiplies with agents; teams running research agents report several times to an order of magnitude more tokens than single-agent chat.

    import asyncio

async def orchestrate(task, llm, run_worker, max_workers=4):
    # 1. plan: ask the lead for independent sub-tasks with clear boundaries
    briefs = await llm.plan_subtasks(task, max_items=max_workers)   # list of dicts
    # 2. fan out: each worker gets only its brief, its own tools and a budget
    results = await asyncio.gather(
        *(run_worker(b["objective"], scope=b["scope"], budget_tokens=40_000) for b in briefs),
        return_exceptions=True,
    )
    # 3. reduce: the lead sees condensed findings, never full worker transcripts
    findings = [r for r in results if not isinstance(r, Exception)]
    return await llm.synthesise(task, findings)

    When not to split

    Tightly coupled work, such as one refactor, goes wrong in parallel because workers cannot see each other's decisions. Splitting also adds prompts, briefs and handoff bugs, which are pure overhead when one agent with compaction would fit. Build the single agent first, measure where it fails, and split only the part that is parallel and context-hungry.

    Key ideas
    • Orchestrator–workers for parallel breadth, pipelines for fixed stages, debate for hard judgement.
    • Each agent has its own context, which is why splitting can help.
    • Write explicit briefs and return condensed results.
    • Tokens scale with agent count; only parallel designs cut latency.
    Common mistakes
    • One-line briefs, so workers duplicate each other or wander.
    • Full worker transcripts piped back into the lead's context.
    • Splitting tightly coupled work across parallel agents.

    08.6 · Standard plumbing

    Model Context Protocol (MCP)

    The Model Context Protocol is an open standard for connecting AI applications to tools and data. A provider writes one MCP server, and any MCP-capable application can use it, much as the Language Server Protocol let any editor use any language's tooling.

    Why it matters for AI engineers

    Most major assistants, IDEs and agent frameworks speak MCP. You will consume servers to give agents access without glue code, and write servers to expose your company's systems.

    Hosts, clients and servers

    The host is the AI application: a chat app, an IDE or your agent. Inside it, each client holds one stateful connection to exactly one server, a program that exposes capabilities. Servers never see each other or the whole conversation, so the host controls what is shared.

    Servers offer three primitives. Clients can offer features back, such as sampling (model completions for the server), roots (filesystem boundaries) and elicitation (asking the user).

    PrimitiveWhat it isControlled byMethods
    ToolsFunctions with a JSON Schema input; may have side effectsModeltools/list, tools/call
    ResourcesReadable data by URI: files, schemas, docsApplicationresources/list, resources/read
    PromptsReusable templates with argumentsUserprompts/list, prompts/get

    Messages, handshake and transports

    Messages are JSON-RPC 2.0: requests with an id, matching responses, and notifications without one. A session opens with initialize, where both sides declare a protocol version and capabilities, so neither calls a feature the other lacks.

    An MCP session, message by message Try it

    With stdio the host runs the server as a subprocess and exchanges newline-delimited messages over stdin and stdout. With Streamable HTTP the client POSTs to one endpoint and the server replies with JSON or a server-sent event stream. It replaced the older HTTP-plus-SSE transport in 2025, and the spec defines OAuth-based authorization for HTTP.

    // client -> server: the model decided to call a tool
{"jsonrpc": "2.0", "id": 7, "method": "tools/call",
 "params": {"name": "query_db", "arguments": {"sql": "SELECT count(*) FROM orders"}}}

// server -> client: result content goes back to the model as an observation
{"jsonrpc": "2.0", "id": 7,
 "result": {"content": [{"type": "text", "text": "count: 18342"}], "isError": false}}

    The Python SDK builds schemas from type hints and docstrings.

    # pip install "mcp[cli]"  -- the official Python SDK
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("orders")

@mcp.tool()
def count_orders(status: str = "open") -> int:
    """Count orders with the given status (open, shipped or refunded)."""
    return db.count(status=status)                 # your data layer

@mcp.resource("schema://orders")
def orders_schema() -> str:
    """Column names and types of the orders table."""
    return "id TEXT, customer_id TEXT, total NUMERIC, status TEXT, created_at DATE"

@mcp.prompt()
def weekly_report(week: str) -> str:
    return f"Summarise order volume and refunds for week {week}. Use count_orders."

if __name__ == "__main__":
    mcp.run()          # stdio transport by default; a host launches this script

    Treat third-party servers as code you run: their descriptions can carry prompt injection, and remote ones see every argument.

    Key ideas
    • MCP turns N×M integrations into N+M.
    • A host runs one client per server connection.
    • Servers offer tools, resources and prompts.
    • JSON-RPC 2.0 over stdio (local) or Streamable HTTP (remote).
    Common mistakes
    • Logging to stdout in a stdio server, which corrupts the stream. Log to stderr.
    • Connecting untrusted servers with broad credentials and auto-approved writes.
    • Treating MCP as an agent framework; the loop, memory and guardrails stay in the host.

    08.7 · Acting on screens

    Computer & browser use

    Many systems have no API, only a user interface. A computer-use agent operates it like a person: look at a screenshot, decide where to click or what to type, act, take another screenshot. It is the 08.1 loop with a screen as the environment.

    Why it matters for AI engineers

    Legacy apps, portals and internal dashboards are often reachable only through a UI. These agents can click anything a logged-in human could, and they read untrusted content on every page, so they are also the riskiest agents you will build.

    The screenshot-action loop

    The harness sends a screenshot to a vision-capable model, which replies with an action from a small vocabulary: click at (x, y), type, press keys, scroll, wait. The harness executes it in a VM, container or automated browser and captures the new screen.

    Harnesses usually downscale screenshots to a size the model handles well, so the model's coordinates must be scaled back up. Get this wrong and every click lands somewhere else.

    Where does the click land? Try it

    The model sees a 1280 px image. With scaling off on a 1920 px screen, aiming at Submit hits "Delete account".

    import base64
from playwright.sync_api import sync_playwright

MODEL_W = 1280                                       # width the model sees

def browser_agent(task, decide, max_steps=25):
    """decide(task, screenshot_b64, history) -> dict like
       {"action": "click", "x": 412, "y": 300} | {"action": "type", "text": "..."} | {"action": "done", "answer": "..."}"""
    with sync_playwright() as p:
        browser = p.chromium.launch(headless=True)
        page = browser.new_page(viewport={"width": 1280, "height": 800})
        page.goto("https://example.com")
        scale = page.viewport_size["width"] / MODEL_W
        history = []
        for _ in range(max_steps):
            shot = base64.b64encode(page.screenshot()).decode()
            act = decide(task, shot, history)
            history.append(act)
            if act["action"] == "click":
                page.mouse.click(act["x"] * scale, act["y"] * scale)
            elif act["action"] == "type":
                page.keyboard.type(act["text"])
            elif act["action"] == "scroll":
                page.mouse.wheel(0, act.get("dy", 600))
            elif act["action"] == "done":
                return act["answer"]
            page.wait_for_load_state()
        return "Stopped: step limit"

    Pixels or accessibility tree

    Browsers offer richer views than pixels. The accessibility tree is the simplified element list built for screen readers, with roles and names. Acting by element reference is cheaper and more precise; screenshots still cover canvas charts and unlabelled icons. Many agents use both, and a direct API beats either when one exists.

    Sandboxing and prompt injection

    Run these agents in an isolated VM or container, with a browser profile holding only the accounts the task needs and network rules that block internal services. Benchmarks such as WebArena and OSWorld show they remain far less reliable than people on long tasks.

    The biggest risk is indirect prompt injection: page text written to hijack the agent. Models cannot reliably separate your instructions from instructions inside content, so limit data access, allowlist domains and confirm purchases, logins, messages and deletions with a human (08.8).

    Key ideas
    • Screenshots in, mouse and keyboard actions out.
    • Scale coordinates exactly between model image and real screen.
    • Prefer accessibility trees or APIs when available.
    • Sandbox everything; treat every page as untrusted input.
    Common mistakes
    • Running the agent on your own logged-in desktop.
    • Skipping coordinate scaling, so clicks land on the wrong element.
    • Acting before the page has finished loading.

    08.8 · Safe autonomy

    Guardrails & human-in-the-loop

    An agent that can act can act wrongly: delete the wrong branch, email the wrong customer, or follow instructions planted in a web page. Guardrails are checks your harness runs around the model. Human-in-the-loop routes the riskiest decisions to a person.

    Why it matters for AI engineers

    You cannot prompt your way to safety, because models are sometimes wrong, confused or manipulated. Making the worst-case action survivable is the builder's job, and it is the first thing security reviewers ask about.

    Layers of defence

    Input guardrails screen what enters the context. Action guardrails check each proposed tool call. Isolation (sandboxes, scoped credentials) bounds the damage, output guardrails check what leaves, and an audit log records everything.

    Permission tiers and approvals

    Classify every tool, and sometimes every call, by risk. Arguments matter as much as names: run_shell("ls") and run_shell("rm -rf /") are the same tool.

    A good approval request shows the exact call and arguments, the agent's reason and the expected effect, and lets the person approve, edit or deny with feedback. Too many prompts cause approval fatigue. In the simulator, try the permissive policy with the injection box ticked.

    Approval policy simulator Try it

    Least privilege, injection and budgets

    Least privilege gives the agent the narrowest credentials that work: a read-only database role, a token for one repository, an email tool that can only draft. If the agent is tricked, damage stays bounded.

    No filter catches every injected instruction, so break that combination by design. Add budgets on steps, tokens, dollars and time, and alert on unusual tool patterns or denial spikes.

    import re
from enum import Enum

class Decision(Enum):
    ALLOW = "allow"; ASK = "ask"; BLOCK = "block"

TIERS = {"search_docs": "read", "read_file": "read", "write_file": "reversible",
         "send_email": "external", "refund": "external", "run_shell": "dynamic"}
FORBIDDEN_SHELL = re.compile(r"\brm\s+-rf\b|\bmkfs\b|curl[^|]*\|\s*(sh|bash)")

def decide(tool: str, args: dict, spent: float, limit: float) -> Decision:
    tier = TIERS.get(tool)
    if tier is None:
        return Decision.BLOCK                                    # unknown tools never run
    if tool == "run_shell":
        if FORBIDDEN_SHELL.search(args.get("cmd", "")):
            return Decision.BLOCK
        tier = "read" if args.get("cmd", "").split()[:1] in (["ls"], ["cat"], ["grep"]) else "external"
    if spent + args.get("amount", 0) > limit:
        return Decision.ASK                                      # over budget: a human decides
    return {"read": Decision.ALLOW, "reversible": Decision.ALLOW,
            "external": Decision.ASK}[tier]

# In the loop: BLOCK -> return "Blocked by policy: ..." as the tool result;
# ASK -> pause, show the call to a human, resume with their decision; log everything.
    Key ideas
    • Guardrails are code around the model, in layers.
    • Auto-run reads, approve irreversible actions, block forbidden ones.
    • Least privilege bounds the damage of prompt injection.
    • Budgets stop runaway loops.
    Common mistakes
    • A system-prompt sentence as the only control.
    • Policies keyed on tool name that miss dangerous arguments.
    • Approval prompts on every step, until users approve blindly.
