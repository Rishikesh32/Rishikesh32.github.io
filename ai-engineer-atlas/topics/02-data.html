Data skills

Models are only as good as the data they learn from, retrieve from and get evaluated on. This area covers how to query data, clean it, move it reliably, store it efficiently, label it consistently and keep every version reproducible.

In this area

    Data work is a pipeline. Raw data arrives from apps, logs and documents, gets moved and stored, cleaned and explored, labeled and checked, sometimes extended with synthetic examples, and finally frozen as a versioned dataset that training, evals and RAG can depend on. SQL is the tool you use to look at it at every stage.

    02.1 · The universal data language

    SQL

    SQL lets you describe the answer you want ("revenue per user for the last 30 days") and lets the database work out how to compute it. It has outlived every data fashion since the 1970s, and today it also queries Parquet files, data lakes and vector tables.

    Why it matters for AI engineers

    Building an eval set, pulling fine-tuning examples from logs, measuring cost per user, filtering RAG results by metadata: each is a SQL query. Postgres with pgvector and DuckDB on Parquet are everyday AI tools.

    The order a query really runs in

    You write SELECT first, but the database evaluates it near the end. Knowing the logical order explains most confusing errors, such as why WHERE cannot use a column alias or an aggregate.

    Joins

    A join pairs rows from two tables where a condition holds, usually matching keys. The join type decides what happens to rows with no partner.

    JOIN visualizer Try it

    Notice that Ana appears twice in every join that keeps her: one row per matching order. Joins multiply rows, which is the usual cause of inflated sums. Order 104 points to user 5, who does not exist, so only RIGHT and FULL joins keep it.

    Window functions and NULL

    A window function computes across related rows without collapsing them, unlike GROUP BY. Ranking within each user is the classic use: keep each user's latest event, or number the turns of a conversation.

    NULL means unknown, so NULL = NULL is not true. Test with IS NULL, and remember COUNT(col) skips NULLs while COUNT(*) does not.

    -- Latest conversation per user with total spend, last 30 days (Postgres)
WITH ranked AS (
  SELECT c.*,
         ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC) AS rn
  FROM conversations c
  WHERE created_at >= now() - interval '30 days'
),
spend AS (
  SELECT user_id, SUM(cost_usd) AS total_cost, COUNT(*) AS n_calls
  FROM llm_calls
  GROUP BY user_id
  HAVING COUNT(*) >= 5
)
SELECT r.user_id, r.id AS last_conversation, s.total_cost, s.n_calls
FROM ranked r
LEFT JOIN spend s ON s.user_id = r.user_id
WHERE r.rn = 1
ORDER BY s.total_cost DESC NULLS LAST
LIMIT 20;
    In practice

    Add an index on columns you filter and join on, and read the plan with EXPLAIN ANALYZE before guessing why a query is slow. For local analytics on CSV or Parquet, DuckDB runs the same SQL with no server.

    Key ideas
    • Logical order: FROM/JOIN, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT.
    • INNER keeps matches; LEFT keeps every left row; FULL keeps everything; anti-joins find rows with no match.
    • Joins on non-unique keys multiply rows; check counts before and after.
    • Window functions rank and accumulate without collapsing rows.
    • NULL is unknown: use IS NULL, and know which aggregates skip it.
    Common mistakes
    • Summing after a one-to-many join and double counting.
    • Filtering a LEFT JOIN's right table in WHERE, which silently turns it into an INNER JOIN; put that condition in ON.
    • Writing col = NULL instead of col IS NULL.
    • Building SQL with string formatting from user input instead of parameters (SQL injection).

    02.2 · Look before you model

    Data cleaning & EDA

    Real data is messy: missing values, impossible values, duplicates, mixed units, mangled text. Exploratory data analysis (EDA) means looking at the data systematically before trusting it. Cleaning means deciding, on purpose and in code, what to do about each problem you find.

    Why it matters for AI engineers

    A fine-tuning set with 5% duplicated or garbled examples, or a RAG corpus full of boilerplate pages, quietly caps quality. An hour of EDA often beats a week of model tuning.

    An EDA routine

    Run the same checks on every new dataset, in the same order, and write down what you find. Most surprises appear in the first three steps.

    Outliers and missing values

    A box plot summarizes a column with its quartiles. The interquartile range (IQR) is Q3 − Q1; points beyond 1.5 × IQR from the box are flagged as outliers. They may be errors, or the most important rows you have.

    Cleaning choices change your statistics Try it

    The raw column has four missing values, a sentinel −1 written by a buggy logger and two huge pasted documents. Watch the mean jump around with each choice while the median barely moves. Mean imputation also shrinks the spread, because every filled value sits exactly at the center.

    Ask why a value is missing. Missing completely at random is harmless to drop. If missingness depends on the value itself (long prompts timing out before logging, say), dropping biases everything downstream, so add an "is_missing" flag column.

    import pandas as pd
import numpy as np

df = pd.read_parquet("prompts.parquet")
print(df.shape, df.dtypes, df.isna().mean().sort_values(ascending=False).head(), sep="\n")

df["n_tokens"] = df["n_tokens"].replace(-1, np.nan)        # sentinel to real missing
df["n_tokens_missing"] = df["n_tokens"].isna()            # keep the signal
q1, q3 = df["n_tokens"].quantile([0.25, 0.75])
iqr = q3 - q1
df["n_tokens"] = df["n_tokens"].clip(upper=q3 + 1.5 * iqr).fillna(df["n_tokens"].median())

df["text"] = df["text"].str.normalize("NFKC").str.strip()  # unicode + whitespace
before = len(df)
df = df.drop_duplicates(subset="text")
print(f"removed {before - len(df)} exact duplicates")
    Key ideas
    • Run a fixed EDA routine: shape, missingness, distributions, duplicates, relationships, notes.
    • The median and IQR resist outliers; the mean and standard deviation do not.
    • Every cleaning choice changes downstream numbers, so make it explicit in code.
    • Missingness can carry signal; keep a flag when you impute.
    Common mistakes
    • Computing imputation values or clipping thresholds on the full dataset before the train/test split (leakage).
    • Treating sentinel values like −1, 0 or "N/A" strings as real data.
    • Deleting outliers that are actually the rare cases your model most needs to handle.
    • Cleaning by hand in a spreadsheet, so nobody can reproduce the dataset.

    02.3 · Moving data reliably

    Pipelines & ETL

    A pipeline is a scheduled program that moves data from where it is created to where it is useful, transforming it on the way. One-off scripts break quietly. Good pipelines are idempotent (safe to rerun), observable and recoverable, so a failure at 3 a.m. costs a retry, not a week of corrupted data.

    Why it matters for AI engineers

    A RAG system is only as fresh as its ingestion pipeline. Eval sets, fine-tuning data and usage analytics are all pipeline outputs, and a retry that double-inserts records will silently skew every metric built on them.

    A pipeline is a DAG of tasks

    Each task does one step and declares its inputs. An orchestrator (Airflow, Dagster, Prefect) runs them in dependency order on a schedule, retries failures and lets you backfill: rerun past dates after a fix.

    ETL or ELT

    ETL transforms data before loading it into the warehouse. ELT loads raw data first and transforms it inside the warehouse with SQL (often with dbt). Cheap storage made ELT the default for analytics: you keep the raw copy and can redo transforms later.

    Idempotency: safe to run twice

    Retries and backfills mean every task will eventually run more than once on the same input. An idempotent task leaves the same result however many times it runs. Plain appends are not idempotent; upserts by a key, or overwriting a whole date partition, are.

    Retry a daily load Try it

    Each run loads the same five orders for one day; order 103's amount is corrected in later runs. Append piles up duplicates and keeps the stale amount. Upsert and partition overwrite keep exactly five rows with the latest values.

    import sqlite3

con = sqlite3.connect("warehouse.db")
con.execute("""CREATE TABLE IF NOT EXISTS orders (
    order_id INTEGER PRIMARY KEY, day TEXT, amount REAL)""")

def load(day: str, rows: list[tuple[int, float]]) -> None:
    with con:                                           # one transaction: all or nothing
        con.executemany(
            """INSERT INTO orders (order_id, day, amount) VALUES (?, ?, ?)
               ON CONFLICT(order_id) DO UPDATE SET amount = excluded.amount""",
            [(oid, day, amt) for oid, amt in rows])

batch = [(101, 30.0), (102, 12.0), (103, 45.0)]
load("2026-11-16", batch)
load("2026-11-16", batch)                               # retry: still 3 rows
print(con.execute("SELECT COUNT(*) FROM orders").fetchone())   # (3,)
    Key ideas
    • Pipelines are DAGs of small tasks run by an orchestrator on a schedule.
    • Make every task idempotent: upsert by key or overwrite a partition, inside a transaction.
    • Validate data between steps and quarantine bad rows instead of failing silently.
    • ELT keeps raw data so transforms can be fixed and rerun; backfills replay history.
    • Batch is simpler; use streaming (Kafka and friends) only when minutes of delay are too slow.
    Common mistakes
    • Plain INSERTs in a task that retries, doubling rows on every failure.
    • Using "now" inside a task instead of the run's logical date, so backfills load today's data for every past day.
    • No alerting: the pipeline fails for a week and the RAG index goes stale unnoticed.
    • Re-embedding the entire corpus daily instead of only new or changed documents (track a content hash).

    02.4 · How bytes sit on disk

    File formats & storage

    The same table can be a 40 GB CSV that takes minutes to scan or a 9 GB Parquet file that answers the same question in seconds. The difference is layout: whether values are stored row by row or column by column, whether they are compressed, and whether the file carries statistics that let a reader skip what it does not need.

    Why it matters for AI engineers

    Training corpora, eval logs and embedding tables are large. Picking Parquet over CSV, JSONL for streaming records and safetensors over pickle for weights saves money, time and, in the last case, a security hole.

    Row-oriented vs column-oriented

    Row formats (CSV, JSONL, most OLTP databases) store each record together: great for writing and reading whole records. Columnar formats (Parquet, Arrow) store each column together: an analytic query that needs 3 of 50 columns reads only those 3, and similar values next to each other compress well.

    Inside a Parquet file

    A Parquet file is split into row groups (often around 128 MB), each holding one compressed chunk per column. The footer stores the schema plus min and max values per chunk, so readers skip whole row groups that cannot match a filter: predicate pushdown.

    Bytes read: row file vs Parquet Try it

    The demo assumes 8 bytes per value, 3× compression for Parquet and a 1 GB/s disk. Lower the matching row groups (as a date filter on sorted data would) and the two savings multiply.

    FormatLayoutBest forWatch out
    CSVRow, textSmall exchanges, spreadsheetsNo types, quoting bugs, slow
    JSONLRow, textChat logs, fine-tuning and eval records, streamingLarge; schema drift
    ParquetColumnar, compressedAnalytics, training corpora, lakesSlow for single-row updates
    ArrowColumnar, in memoryZero-copy hand-off between pandas, Polars, DuckDBNot an archival format
    safetensorsRaw tensors + headerModel weightsPrefer over pickle, which can run code on load

    At larger scale, files live in object storage, and table formats such as Delta Lake and Apache Iceberg add transactions, schema evolution and time travel on top of Parquet files.

    import pyarrow.parquet as pq
import duckdb

# read 2 columns, and only row groups whose stats can match the filter
table = pq.read_table("events.parquet", columns=["day", "tokens"],
                      filters=[("day", ">=", "2026-06-01")])

# the same question in SQL, over a whole folder of Parquet files
print(duckdb.sql("""
    SELECT day, SUM(tokens) AS tokens
    FROM 'events/*.parquet'
    WHERE day >= '2026-06-01'
    GROUP BY day ORDER BY day
""").df())
    Key ideas
    • Row layouts suit whole-record reads and writes; columnar layouts suit analytics.
    • Parquet = row groups of compressed column chunks plus footer statistics.
    • Column pruning and predicate pushdown multiply: read fewer columns from fewer row groups.
    • JSONL for records and streams, Parquet for tables, safetensors for weights.
    Common mistakes
    • Storing large analytic datasets as CSV and paying for every full scan.
    • Writing thousands of tiny Parquet files; each has overhead, so compact them.
    • Loading untrusted .pkl or .pt files, which can execute arbitrary code.
    • Letting pandas guess types from CSV, turning ids into floats and dates into strings.

    02.5 · Ground truth you can trust

    Labeling & data quality

    A label is a human (or model) judgment written down: this ticket is "billing", this answer is "correct", this reply is "unsafe". Labels become ground truth for training and evaluation, so if two careful people would disagree about them, your metric measures noise. Good labeling is mostly about writing clear guidelines and measuring agreement.

    Why it matters for AI engineers

    Every eval set and fine-tuning set you build needs labels. When you use an LLM as an annotator or judge, you validate it the same way: by measuring how well it agrees with careful humans.

    The labeling loop

    Never jump straight to labeling 10,000 items. Pilot a small batch with two or more annotators, measure where they disagree, fix the guidelines, then scale with ongoing audits.

    Measuring agreement

    Raw percent agreement flatters you when one label dominates: two annotators who both always say "safe" agree 95% of the time on data that is 95% safe. Cohen's kappa subtracts the agreement you would expect by chance from each annotator's label rates.

    \[ \kappa = \frac{p_o - p_e}{1 - p_e} \qquad p_e = \sum_{k} p_{A,k}\, p_{B,k} \] \(p_o\) is observed agreement; \(p_e\) is chance agreement from each annotator's label rates. Example: 100 items, both "yes" 45, both "no" 40, split 15. \(p_o = 0.85\); A says yes 55%, B 50%, so \(p_e = 0.55 \cdot 0.5 + 0.45 \cdot 0.5 = 0.50\) and \(\kappa = 0.70\).
    Agreement calculator Try it

    Try "Rare positive class": 95% raw agreement, yet kappa is only about 0.26 because the annotators barely agree on the rare positives that matter. For three or more annotators or missing labels, use Fleiss' kappa or Krippendorff's alpha.

    Scaling with models

    LLMs can pre-label or fully label many tasks. Treat the model as one more annotator: label a gold set with humans, measure model-human kappa, and route low-confidence or disagreeing items to people. Active learning sends humans the items the model is least sure about, which buys the most improvement per label.

    from sklearn.metrics import cohen_kappa_score, confusion_matrix

human = ["bug", "billing", "bug", "other", "billing", "bug", "other", "bug"]
llm   = ["bug", "billing", "other", "other", "billing", "bug", "bug", "bug"]

print(cohen_kappa_score(human, llm))       # chance-corrected agreement, about 0.6 here
print(confusion_matrix(human, llm, labels=["bug", "billing", "other"]))

disagree = [i for i, (h, m) in enumerate(zip(human, llm)) if h != m]
print("send to adjudication:", disagree)    # [2, 6]
    Key ideas
    • Guidelines with definitions, edge cases and examples are the main quality lever.
    • Pilot with two or more annotators and measure agreement before scaling.
    • Kappa corrects for chance; raw agreement is misleading on imbalanced labels.
    • Treat LLM labelers as annotators: validate against a human gold set.
    • Gold questions and periodic audits catch drift during large labeling jobs.
    Common mistakes
    • Single-annotator labels with no agreement check, then trusting a 1-point eval difference.
    • Reporting percent agreement on a 95/5 class split.
    • Letting the engineer who built the system label its eval set alone.
    • Changing guidelines midway without relabeling the earlier items.

    02.6 · Make more data, and never lose track of it

    Synthetic data & versioning

    When real data is scarce, private or missing the rare cases you care about, you can generate it, usually with an LLM prompted from seed examples. Generation is the easy half. The hard half is filtering out the junk, removing near-duplicates and recording exactly which version of the data trained or evaluated which model.

    Why it matters for AI engineers

    Synthetic examples bootstrap eval sets, cover edge cases and feed distillation. Versioning answers the question every regression raises: "what changed?" Without dataset hashes you cannot reproduce a result or roll back.

    A generate-then-filter pipeline

    Seed the generator with real examples, a taxonomy of topics and varied personas, so outputs cover the space instead of repeating one style. Then filter hard: most of what an LLM generates is valid but redundant.

    Verification beats judgment when you can get it: run generated code against tests, check generated SQL against a database, or confirm a math answer. Where you cannot, an LLM judge with a clear rubric filters the obvious failures. Keep synthetic and real examples labeled separately and evaluate on real data, or the model learns the generator's quirks.

    Near-duplicate detection

    Exact hashes miss paraphrases that differ by a word. Near-duplicate detection compares sets of shingles (overlapping runs of k words) using Jaccard similarity: shared shingles divided by total distinct shingles. MinHash estimates it fast enough for millions of documents.

    Shingle overlap and Jaccard similarity Try it

    With k = 1 almost any two questions on the same topic look similar. Larger k demands longer exact runs, so paraphrases drop below the threshold. Real pipelines typically use 3 to 5 word shingles or character n-grams.

    Version data like code

    Git cannot hold 50 GB of data, so tools like DVC commit a small pointer file containing a content hash, while the bytes go to object storage. Every training run records the dataset hash, so "which data trained model 7?" has an exact answer.

    dvc init
dvc remote add -d storage s3://my-bucket/dvc      # where the bytes live
dvc add data/train.jsonl                         # writes data/train.jsonl.dvc (hash pointer)
git add data/train.jsonl.dvc data/.gitignore
git commit -m "train data v1.3: +3,100 synthetic, deduped"
git tag data-v1.3
dvc push                                         # upload the data to the remote

git checkout data-v1.2 && dvc checkout           # time travel to the old dataset
    Key ideas
    • Seed generation with real examples, a taxonomy and personas to get diversity.
    • Filter in stages: schema validation, deduplication, then verification or an LLM judge, then a human spot check.
    • Jaccard similarity on shingles (via MinHash at scale) catches near-duplicates that hashes miss.
    • Evaluate on real data; keep synthetic examples tagged.
    • Version datasets by content hash and record the hash with every training run.
    Common mistakes
    • Generating eval and training data with the same prompts, so the model is tested on its own style.
    • Skipping dedup and over-weighting whatever the generator likes to repeat.
    • Ignoring the model provider's terms on using outputs to train other models.
    • Overwriting data/latest.jsonl in place, making past results impossible to reproduce.

    Put it together

    Projects for this area

    Starter

    EDA report on a public dataset

    Load a public dataset of support tickets or reviews into DuckDB, run the six-step EDA routine and write a one-page findings note. Convert it from CSV to Parquet and record the size and query-time difference.

    Intermediate

    Idempotent ingestion pipeline

    Build a daily pipeline that pulls documents from a folder or API, cleans and chunks them and upserts them into Postgres, keyed by content hash. Prove it is idempotent by running every day twice, and add a validation step that quarantines bad rows.

    Stretch

    Versioned eval set with synthetic hard cases

    Label 200 real examples with two annotators, report kappa and fix the guidelines. Add 500 filtered, deduplicated synthetic edge cases, version the whole set with DVC and use it to compare two prompts with confidence intervals.
