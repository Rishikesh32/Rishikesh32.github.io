Deep learning

Deep learning stacks simple units into networks with millions or billions of parameters and trains them with gradients. Every LLM, image model and speech model is built from the pieces on this page: neurons, backpropagation, PyTorch, a handful of architectures, a training recipe and the GPUs that run it.

In this area

    A neural network is a stack of layers (lesson 01). Backpropagation computes how every weight should change (02), and PyTorch does that bookkeeping for you (03). Architectures (04) decide the network's shape for images, sequences or compression. The training recipe (05) makes optimization converge, and GPUs (06) make it fast enough to matter. Under all of it runs the same four-beat loop.

    04.1 · From neuron to network

    Neural network basics

    A neuron is logistic regression with a choice of squashing function: multiply inputs by weights, add a bias, pass the sum through a nonlinear activation. A network is many neurons side by side (a layer) and many layers in a row. Each layer re-describes its input in features the next layer finds easier to use.

    Why it matters for AI engineers

    A transformer is mostly these same layers: matrix multiplies, activations and normalization. Knowing what a layer computes lets you read model configs ("hidden size 4096, MLP ratio 4"), estimate parameter counts, and reason about what a fine-tune actually changes.

    One neuron

    Why the activation? Stacking linear layers gives another linear layer (\(W_2 W_1 x\) is just one matrix times \(x\)), so without a nonlinearity depth buys nothing. With one, a wide enough network can approximate essentially any smooth function, and depth lets it build features out of features.

    Single-neuron playground Try it

    Drive \(z\) far negative with ReLU and the slope (dashed) becomes exactly 0: that neuron passes no gradient back, which is how ReLUs "die". Push sigmoid or tanh far either way and the slope flattens towards 0 too. That saturation is why deep networks moved from sigmoid to ReLU, and why modern LLMs use smooth variants like GELU and SwiGLU.

    Layers are matrix multiplies

    \[ h^{(\ell)} = \phi\big(W^{(\ell)} h^{(\ell-1)} + b^{(\ell)}\big), \qquad W^{(\ell)} \in \mathbb{R}^{d_\ell \times d_{\ell-1}} \] A layer with \(d_{\ell-1}\) inputs and \(d_\ell\) outputs has \(d_\ell d_{\ell-1} + d_\ell\) parameters. Processing a batch of \(B\) examples at once turns this into one matrix-matrix product, which is exactly what GPUs are fast at. 
    import numpy as np

rng = np.random.default_rng(0)
sizes = [3, 4, 4, 2]
# He initialization keeps activations from shrinking or exploding through ReLU layers
params = [(rng.normal(0, np.sqrt(2 / n_in), (n_in, n_out)), np.zeros(n_out))
          for n_in, n_out in zip(sizes[:-1], sizes[1:])]

def forward(X):                       # X: (batch, 3)
    h = X
    for i, (W, b) in enumerate(params):
        z = h @ W + b                 # (batch, n_out): one matmul per layer
        h = np.maximum(z, 0) if i < len(params) - 1 else z   # ReLU, except on the logits
    return h

print(forward(rng.normal(size=(5, 3))).shape)            # (5, 2)
print(sum(W.size + b.size for W, b in params))           # 46
    Key ideas
    • A neuron is a weighted sum plus bias, passed through a nonlinear activation.
    • Without nonlinearities, any stack of layers collapses to one linear map.
    • A layer is a matrix multiply; batching turns it into the matrix-matrix product GPUs excel at.
    • Activation slopes matter for learning: saturated sigmoids and dead ReLUs pass almost no gradient.
    • Parameter count per dense layer is inputs × outputs + outputs.
    Common mistakes
    • Applying ReLU or softmax to the final logits and then also using a loss that expects raw logits.
    • Initializing all weights to the same value, so every neuron in a layer learns the same thing.
    • Mixing up weight shapes: PyTorch's nn.Linear stores \(W\) as (out, in) and computes \(xW^\top + b\).

    04.2 · The chain rule at scale

    Backpropagation

    Training needs to know, for every weight, "if I nudge this up a little, does the loss go up or down, and how fast?" That number is the gradient. Backpropagation computes all of them in one backward sweep: run the network forward and remember the intermediate values, then walk the graph from the loss back to the inputs, multiplying local slopes as you go.

    Why it matters for AI engineers

    You will rarely write backprop by hand, but you will debug it: NaN losses, exploding gradients, a frozen layer that is not learning, out-of-memory errors caused by stored activations. All of these make sense once you can see the forward and backward passes on a graph.

    Forward values, backward gradients

    Take one neuron with a squared-error loss: \(u = xw\), \(z = u + b\), \(a = \sigma(z)\), \(L = (a - y)^2\). The forward pass computes values left to right. The backward pass starts from \(\partial L / \partial L = 1\) and multiplies by each node's local derivative right to left.

    \[ \frac{\partial L}{\partial w} = \underbrace{2(a-y)}_{-0.755}\cdot\underbrace{\sigma(z)(1-\sigma(z))}_{0.235}\cdot\underbrace{1}_{\partial z/\partial u}\cdot\underbrace{x}_{2} = -0.355 \] The gradient is negative, so increasing \(w\) lowers the loss. Gradient descent does exactly that: \(w \leftarrow w - \eta \cdot (-0.355)\).
    Step through forward and backward Try it

    Step through once with the defaults, then change \(x\). The gradient for \(w\) scales with \(x\): a multiply node passes each input the upstream gradient times the other input. The last step checks the backprop answer against a finite difference, \((L(w+h) - L(w-h))/2h\), the same "gradient check" you would use to test hand-written code.

    Three local rules cover most of a network

    Two practical consequences. The forward pass must cache activations for the backward pass, so training memory grows with batch size and depth; the backward pass costs roughly twice the forward. And long chains multiply many factors: if they are mostly below 1 gradients vanish, if above 1 they explode. Careful initialization, normalization, residual connections and gradient clipping all exist to keep that product near 1.

    import torch

x = torch.tensor(2.0)
w = torch.tensor(0.5, requires_grad=True)
b = torch.tensor(-0.5, requires_grad=True)
y = torch.tensor(1.0)

a = torch.sigmoid(x * w + b)          # forward: autograd records the graph
loss = (a - y) ** 2
loss.backward()                       # backward: fills .grad on leaf tensors
print(loss.item(), w.grad.item(), b.grad.item())   # 0.1425  -0.3549  -0.1774

# finite-difference check of dL/dw
h = 1e-4
f = lambda wv: (torch.sigmoid(x * wv + b.detach()) - y) ** 2
print(((f(w.detach() + h) - f(w.detach() - h)) / (2 * h)).item())   # about -0.355
    Key ideas
    • Backprop is the chain rule applied on a graph, right to left, reusing values cached in the forward pass.
    • One backward pass gives the gradient for every parameter, at roughly twice the forward cost.
    • Add copies gradients, multiply swaps in the other input, max routes to the winner.
    • Long products of local slopes cause vanishing or exploding gradients.
    • Check hand-written gradients with central finite differences.
    Common mistakes
    • Forgetting to zero gradients between steps; PyTorch accumulates them by default.
    • Calling .item() or converting to NumPy mid-graph and silently cutting gradient flow.
    • Running evaluation without torch.no_grad(), wasting memory on a graph you never use.

    04.3 · The everyday toolkit

    PyTorch

    PyTorch is NumPy that runs on GPUs and remembers how every number was computed. You build a model from nn.Module layers, call it like a function, and autograd records the operations so loss.backward() can fill in every gradient. Almost all open models, including most open-weight LLMs, ship as PyTorch code and weights.

    Why it matters for AI engineers

    Fine-tuning, running open models locally, writing custom evaluation, debugging a Hugging Face model: all of it is PyTorch underneath. Reading tensor shapes fluently and writing a correct training loop are core skills, even if a library such as Transformers or Lightning writes the loop for you.

    Three ideas: tensors, modules, the loop

    A tensor is an n-dimensional array with a shape, a dtype (float32, bfloat16, int64) and a device (cpu or cuda). Operations between tensors must agree on device, and most bugs show up as shape errors. An nn.Module holds parameters and defines forward. The training loop is the same five lines in every project:

    Think in shapes

    Broadcasting lets tensors of different shapes combine: PyTorch aligns shapes from the right, and each dimension must be equal or 1 (a 1 is stretched; a missing dimension counts as 1). It saves memory and code, and it is also how a (32, 1) minus (32,) quietly becomes a (32, 32) matrix.

    Broadcasting checker Try it

    Try A = (32, 1) with B = (32,): the result is (32, 32), the classic bug when subtracting predictions from targets of a slightly different shape. Then try (4, 3) with (3, 4) to see a real mismatch error.

    import torch, torch.nn as nn
from torch.utils.data import DataLoader, TensorDataset

device = "cuda" if torch.cuda.is_available() else "cpu"
X, y = torch.randn(10_000, 784), torch.randint(0, 10, (10_000,))   # stand-in data
train = DataLoader(TensorDataset(X, y), batch_size=64, shuffle=True)

model = nn.Sequential(nn.Linear(784, 256), nn.ReLU(), nn.Linear(256, 10)).to(device)
opt = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=0.01)
loss_fn = nn.CrossEntropyLoss()                # takes raw logits; applies log-softmax itself

for epoch in range(3):
    model.train()                              # enables dropout, batch-norm updates
    for xb, yb in train:
        xb, yb = xb.to(device), yb.to(device)
        loss = loss_fn(model(xb), yb)
        opt.zero_grad(set_to_none=True)
        loss.backward()
        opt.step()
    model.eval()
    with torch.no_grad():                      # no graph, less memory
        acc = (model(X[:1000].to(device)).argmax(1) == y[:1000].to(device)).float().mean()
    print(epoch, loss.item(), acc.item())

torch.save(model.state_dict(), "mlp.pt")       # save weights, not the Python object
    Key ideas
    • A tensor has a shape, a dtype and a device; operations need matching devices and compatible shapes.
    • Every step is: batch, forward, loss, backward(), step(), zero_grad().
    • Broadcasting aligns shapes from the right; size-1 and missing dimensions stretch.
    • Switch model.train() and model.eval(), and evaluate under torch.no_grad().
    • Save and load state_dict(), not whole pickled models.
    Common mistakes
    • Putting softmax before CrossEntropyLoss, which already expects raw logits.
    • Leaving the model in train mode during evaluation, so dropout and batch norm change the results.
    • Accidental broadcasting from a (N, 1) vs (N,) mismatch in a loss.
    • Moving the model to the GPU but not the batch, or creating new tensors on the CPU inside forward.

    04.4 · Shapes of networks

    CNNs, RNNs & autoencoders

    An architecture builds an assumption about the data into the network's wiring. Convolutional networks assume that nearby pixels matter together and that a cat is a cat anywhere in the frame. Recurrent networks assume order matters and read one step at a time. Autoencoders assume the data can be squeezed through a narrow bottleneck and rebuilt.

    Why it matters for AI engineers

    Transformers replaced RNNs for text, but CNNs still run most on-device vision and appear inside vision-language models, and autoencoders compress images into the latent space where diffusion models work. Knowing these ideas also explains transformer design: attention is what you get when you drop the locality and recurrence assumptions.

    Convolution: one small filter, slid everywhere

    A convolution layer slides a small kernel (say 3×3) across the image and takes a weighted sum at each position. The same nine weights are reused everywhere (weight sharing), so a layer needs far fewer parameters than a dense layer and detects a pattern wherever it appears.

    3×3 convolution on a pixel grid Try it

    Blue output cells are positive, orange are negative. Sobel x responds only to left and right edges of the square and the diagonal; Sobel y only to top and bottom. A CNN's first layer learns dozens of kernels like these, and deeper layers combine their outputs into corners, textures, then object parts.

    \[ n_{\text{out}} = \frac{n + 2p - k}{s} + 1, \qquad \text{params} = k^2\, C_{\text{in}}\, C_{\text{out}} + C_{\text{out}} \] Input size \(n\), padding \(p\), kernel \(k\), stride \(s\). A 3×3 conv from 64 to 128 channels has \(9 \cdot 64 \cdot 128 + 128 = 73{,}856\) parameters, whatever the image size.

    Recurrence and bottlenecks

    An RNN updates \(h_t = \tanh(W h_{t-1} + U x_t)\) one token at a time. Gradients through long chains vanish, which LSTMs and GRUs ease with gates. The real limit is that step 1000 must wait for step 999, so RNNs cannot be parallelized across a sequence; transformers can. An autoencoder's code \(z\) becomes a compact representation; a variational autoencoder (VAE) makes that space smooth enough to sample from, and latent diffusion models generate inside such a space.

    ArchitectureBuilt-in assumptionStill used for
    CNN (ResNet, ConvNeXt)Locality, translation invarianceOn-device vision, image encoders, audio spectrograms
    RNN / LSTM / GRUSequential order, fixed-size memorySmall streaming models, some time series
    Autoencoder / VAEData lies near a low-dimensional spaceCompression, anomaly detection, latents for diffusion
    Transformer (Area 05)Any token may attend to any otherLanguage, and increasingly everything else
    Key ideas
    • Convolutions slide a shared kernel; parameters depend on kernel size and channels, not image size.
    • Stacked convolutions build features hierarchically: edges, textures, parts, objects.
    • RNNs carry a hidden state through time and cannot parallelize across the sequence.
    • Autoencoders learn a compressed code by reconstructing their input; VAEs make the code space sampleable.
    Common mistakes
    • Getting the output size wrong after strides and padding; compute it with the formula before building.
    • Feeding images as (H, W, C) when PyTorch convolutions expect (N, C, H, W).
    • Reaching for an RNN for new text work when a small transformer or a pretrained encoder is the better default.

    04.5 · Making it converge

    Training techniques

    Backprop tells you which way is downhill; the training recipe decides how big a step to take, how to keep activations well-behaved and how to stop memorizing. Most "my model won't train" problems are recipe problems, such as a learning rate off by 10× or no warmup.

    Why it matters for AI engineers

    Every fine-tuning config you touch (learning rate, warmup ratio, scheduler, weight decay, max grad norm, bf16) is a line from this lesson. Knowing what each one does lets you read a loss curve and fix a run instead of re-launching it with random changes.

    The learning rate is the first knob

    SGD with momentum steps along a running average of gradients. Adam also tracks squared gradients and gives each parameter its own step size. AdamW, which decouples weight decay from that scaling, is the transformer default.

    Warmup and decay

    Early in training, Adam's statistics are noisy and the weights are random, so large steps can blow the run up. Warmup ramps the learning rate from near 0 over the first few hundred or thousand steps. A cosine or linear decay then lowers it so the model can settle into a minimum.

    \[ \eta(t) = \begin{cases} \eta_{\max}\, \dfrac{t}{T_w} & t < T_w \\[6pt] \eta_{\min} + \tfrac12(\eta_{\max} - \eta_{\min})\Big(1 + \cos\big(\pi \tfrac{t - T_w}{T - T_w}\big)\Big) & t \ge T_w \end{cases} \] \(T_w\): warmup steps, \(T\): total steps. A common choice is warmup of 1–5% of training and \(\eta_{\min} = 0.1\,\eta_{\max}\).
    Learning-rate schedule plotter Try it

    Set warmup to 0 and imagine the very first update hitting random weights at full learning rate. Then compare cosine with linear: both end at the same floor, but cosine spends longer near the peak and drops faster at the end.

    import math, torch

opt = torch.optim.AdamW(model.parameters(), lr=3e-4, betas=(0.9, 0.95), weight_decay=0.1)
total, warmup, min_ratio = 10_000, 500, 0.1

def lr_lambda(step):                         # multiplier on the peak lr
    if step < warmup:
        return (step + 1) / warmup
    progress = (step - warmup) / max(1, total - warmup)
    return min_ratio + (1 - min_ratio) * 0.5 * (1 + math.cos(math.pi * progress))

sched = torch.optim.lr_scheduler.LambdaLR(opt, lr_lambda)

for step, (xb, yb) in zip(range(total), loader):
    with torch.autocast(device_type="cuda", dtype=torch.bfloat16):
        loss = loss_fn(model(xb), yb)
    loss.backward()
    torch.nn.utils.clip_grad_norm_(model.parameters(), max_norm=1.0)
    opt.step(); sched.step(); opt.zero_grad(set_to_none=True)
    In practice

    Before a long run, make the model overfit a single batch to near-zero loss. If it cannot, the bug is in the code (labels, loss, shapes), not the hyperparameters.

    Key ideas
    • The learning rate matters most; sweep it on a log scale.
    • AdamW with warmup and cosine decay is the default recipe for transformers.
    • Normalization, good initialization and residual connections keep signals and gradients in range.
    • Gradient clipping guards against spikes; weight decay, dropout and augmentation fight overfitting.
    • Train in bf16 mixed precision for speed and memory.
    Common mistakes
    • Copying a learning rate from a paper with a very different batch size or model size.
    • Calling scheduler.step() once per epoch when the schedule was defined in steps, or vice versa.
    • Applying weight decay to biases and normalization weights (most LLM recipes exclude them).
    • Changing three hyperparameters at once and not knowing which one helped.

    04.6 · Memory, compute, many GPUs

    GPUs & scaling training

    Deep learning is mostly big matrix multiplies, and GPUs are machines with thousands of small cores and very fast memory built for exactly that. Two numbers decide what you can train: how many bytes the model's training state needs (memory) and how many floating-point operations the run needs (compute). When either outgrows one GPU, you split the work across many.

    Why it matters for AI engineers

    "Can we fine-tune this 8B model on one GPU?", "Why is this training job only using 30% of the GPU?", "Do we need FSDP?" are weekly questions. Back-of-envelope memory and compute math answers them before you spend money, and it is a staple of AI engineering interviews.

    Memory: count the bytes per parameter

    Inference in bf16 needs 2 bytes per parameter: a 7B model is about 14 GB of weights, plus the KV cache. Full training with AdamW in mixed precision needs about 16 bytes per parameter before activations: bf16 weights and gradients, an fp32 master copy, and Adam's two fp32 moment estimates.

    Training and inference memory calculator Try it

    Start at 7B, full training, one 80 GB GPU: it does not fit. Switch to LoRA and it fits easily. Return to full training and add GPUs with sharding on: per-GPU memory falls as 1/N. Switch to "replicate" and it never falls, because data parallelism copies everything.

    Compute: about 6 FLOPs per parameter per token

    \[ C_{\text{train}} \approx 6\,N\,D \] \(N\) parameters, \(D\) training tokens (2 FLOPs forward, 4 backward). A 7B model on 1T tokens needs \(6 \cdot 7\times10^{9} \cdot 10^{12} = 4.2\times10^{22}\) FLOPs. An H100 peaks near \(10^{15}\) dense bf16 FLOP/s; at a realistic 40% utilization that is about 29,000 GPU-hours.

    The fraction of peak you actually achieve is MFU (model FLOPs utilization); 35–55% is good for large training. Small batches, slow data loading and communication waits all lower it. Many operations (normalization, element-wise ops, small-batch decoding) are memory-bound: the cores wait on memory bandwidth (about 3.35 TB/s on an H100), not on math.

    Four ways to split the work

    # launch: torchrun --nproc_per_node=8 train.py   (one process per GPU)
import os, torch, torch.distributed as dist
from torch.nn.parallel import DistributedDataParallel as DDP

dist.init_process_group("nccl")
local_rank = int(os.environ["LOCAL_RANK"])
torch.cuda.set_device(local_rank)

model = build_model().cuda()
model = DDP(model, device_ids=[local_rank])       # gradients all-reduced during backward
# for models whose states do not fit on one GPU, wrap with FSDP instead of DDP
# and give each rank its own data shard with DistributedSampler

print(f"rank {dist.get_rank()}: {torch.cuda.max_memory_allocated() / 2**30:.1f} GiB peak")
    Key ideas
    • Inference in bf16: about 2 bytes per parameter. Full AdamW training: about 16 bytes per parameter plus activations.
    • Training compute is roughly \(6ND\) FLOPs; divide by achieved FLOP/s to get GPU-time.
    • Many operations are limited by memory bandwidth, not math; MFU measures how close you get to peak.
    • Data parallel replicates, FSDP/ZeRO shards states, tensor parallel splits matrices, pipeline parallel splits layers.
    Common mistakes
    • Budgeting only for the weights when planning a fine-tune and forgetting gradients and optimizer state.
    • Quoting sparse or fp8 peak FLOPs when estimating a dense bf16 run.
    • Ignoring activation memory, which grows with batch size and sequence length (activation checkpointing trades compute for it).
    • Reaching for tensor or pipeline parallelism when FSDP on one node would do.
