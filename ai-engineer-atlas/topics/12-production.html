Production & LLMOps

A demo works once; a product works every day for users you never meet. This area covers how to ship AI changes safely, see what every request did, notice when quality, inputs or costs drift, and run the infrastructure underneath. LLMOps is ordinary operations discipline plus one twist: failures are usually wrong answers, not crashes.

In this area

    Production work is a loop. You run experiments and track them, register the winner, pass it through an eval gate in CI, roll it out gradually, and then watch it through traces and monitors. What you see in production (regressions, drift, new kinds of questions) becomes the next round of eval data and experiments. Kubernetes, queues and caches carry the whole loop.

    12.1 · Ship changes without breaking users

    Deployment

    Deploying an AI feature means putting a new combination of model, prompt, parameters and retrieval setup in front of real users. The risky part is that a bad release rarely crashes. It answers a little worse, refuses more often or costs twice as much, so you need versioning that makes every change explicit and rollouts that expose few users until the evidence is in.

    Why it matters for AI engineers

    You will change prompts weekly and models a few times a year. Each change can shift behavior across thousands of conversations. Canary and shadow deploys, plus instant rollback, are what let you move fast without gambling with every user at once.

    What a release is

    Treat the whole bundle as one versioned release. A prompt edit is a deploy, just like a code change.

    # Fetch the prompt version labelled "production" from Langfuse's prompt management
from langfuse import Langfuse

langfuse = Langfuse()                      # reads LANGFUSE_* keys from the environment
prompt = langfuse.get_prompt("answer-support", label="production")
text = prompt.compile(question="Where is my refund?")
# Roll back by moving the "production" label to the previous version: no code deploy needed.

    Rollout strategies

    A canary only protects you if something watches it: compare the canary's error rate (or judge score, refusal rate, cost) against the stable version, and roll back automatically when it crosses a threshold. The catch is sample size: at 5% traffic, a minute of data may hold only a handful of canary requests.

    Canary rollout simulator Try it

    Baseline error rate is 1%. The monitor checks a 5-minute window and waits for at least 100 canary requests before deciding, so a bad canary still reaches some users before it is caught.

    Key ideas
    • A release = model snapshot + prompt version + parameters + retrieval config + tools + guardrails.
    • Version prompts and pin model snapshots so every request is traceable to an exact release.
    • Shadow deploys test safely, canaries limit blast radius, A/B tests measure user impact.
    • Automated rollback needs a metric, a threshold and enough samples to decide.
    Common mistakes
    • Editing a production prompt in a dashboard with no version history or review.
    • Calling a provider's floating model alias and getting silently upgraded.
    • Watching only HTTP errors on a canary while answer quality quietly drops.
    • Shadowing traffic into tools with side effects (sending emails, issuing refunds).

    12.2 · Evals as tests

    CI/CD for AI

    Classic CI runs unit tests: same input, same output, pass or fail. A prompt tweak can pass every unit test and still make answers worse. CI for AI adds an eval gate: run the system on a fixed set of cases, score the outputs, and block the merge if quality falls below a floor or regresses against the current baseline.

    Why it matters for AI engineers

    Without a gate, every prompt or model change is a guess checked by eyeballing five examples. With one, regressions show up on the pull request with a score diff, before users see them.

    The pipeline

    A good gate has two checks: an absolute floor ("pass rate at least 75%") and a non-regression check against the baseline from the main branch, with a tolerance for noise. Cache model responses keyed on prompt and inputs so unchanged cases cost nothing on re-runs.

    # tests/test_eval_gate.py, run by pytest in CI
import json, pathlib
from app import answer            # the system under test
from evals import judge           # returns 1 if the answer is acceptable, else 0

CASES = [json.loads(l) for l in pathlib.Path("evals/smoke.jsonl").read_text().splitlines()]
BASELINE = json.loads(pathlib.Path("evals/baseline.json").read_text())["pass_rate"]

def test_eval_gate():
    scores = [judge(c["input"], answer(c["input"]), c["reference"]) for c in CASES]
    rate = sum(scores) / len(scores)
    assert rate >= 0.75, f"below floor: {rate:.1%}"
    assert rate >= BASELINE - 0.03, f"regression: {rate:.1%} vs baseline {BASELINE:.1%}"
    # .github/workflows/eval-gate.yml
name: eval-gate
on:
  pull_request:
    paths: ["src/**", "prompts/**", "evals/**"]
jobs:
  smoke-eval:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt
      - run: pytest tests/test_eval_gate.py
        env:
          LLM_API_KEY: ${{ secrets.LLM_API_KEY }}

    Noise: the gate's real enemy

    A pass rate measured on 100 cases has a standard error of about 4 points. A small gate cannot tell a real 3-point regression from luck. Bigger suites, paired comparisons on the same cases, and per-category breakdowns all help.

    Will the gate catch it? Try it

    Key ideas
    • An eval gate turns quality into a merge check: absolute floor plus non-regression against baseline.
    • Trigger evals on prompt, model, index and config changes, not only on code.
    • Small smoke suites on every PR, large suites nightly and before release.
    • Eval scores are noisy; size suites and tolerances so the gate catches the regressions you care about.
    Common mistakes
    • Setting a tolerance tighter than the noise, so the gate flakes and people learn to ignore it.
    • Updating the baseline automatically on every merge, letting small regressions accumulate.
    • Assuming temperature 0 makes outputs fully deterministic across runs and providers.
    • Letting eval cases leak into prompts as few-shot examples, inflating the score.

    12.3 · See inside every request

    Observability & tracing

    One user question can trigger a guardrail check, an embedding, two searches, a reranker, two model calls and a tool call. When the answer is slow or wrong, you need to see each of those steps. A trace records one request as a tree of timed spans, each carrying attributes such as the model, token counts and prompt version.

    Why it matters for AI engineers

    Traces are how you debug "the bot said something weird yesterday", find which step makes p95 latency bad, attribute cost to features, and collect real examples for eval sets. Logging only the final answer leaves you guessing.

    Anatomy of a trace

    Each span has a trace id shared by the whole request, its own span id, a parent, start and end times, and attributes. OpenTelemetry (OTel) is the vendor-neutral standard, and its GenAI semantic conventions define attribute names like gen_ai.request.model and gen_ai.usage.input_tokens (still evolving, so check the current spec).

    Trace waterfall of a RAG + tool request Try it

    Read a waterfall for the critical path: the chain of spans that sets total latency. Model calls usually dominate, and a tool call adds a whole second model round trip. Running independent searches in parallel shortens the path for free.

    Across services

    # Manual OpenTelemetry spans around the steps of a RAG request
from opentelemetry import trace
from opentelemetry.sdk.trace import TracerProvider
from opentelemetry.sdk.trace.export import BatchSpanProcessor, ConsoleSpanExporter

provider = TracerProvider()
provider.add_span_processor(BatchSpanProcessor(ConsoleSpanExporter()))  # swap for an OTLP exporter
trace.set_tracer_provider(provider)
tracer = trace.get_tracer("rag-service")

def handle(question):
    with tracer.start_as_current_span("rag.request") as root:
        root.set_attribute("app.release", "r42")
        with tracer.start_as_current_span("retrieve") as s:
            docs = search(question)
            s.set_attribute("retrieval.num_docs", len(docs))
        with tracer.start_as_current_span("llm.chat") as s:
            s.set_attribute("gen_ai.request.model", MODEL)
            resp = call_llm(question, docs)
            s.set_attribute("gen_ai.usage.input_tokens", resp.usage.prompt_tokens)
            s.set_attribute("gen_ai.usage.output_tokens", resp.usage.completion_tokens)
        return resp

    Langfuse

    Open-source, self-hostable LLM tracing with prompt management, datasets and evals; accepts OTel data.

    LangSmith

    LangChain's hosted platform for traces, datasets and evals; works with or without LangChain via its SDK.

    OTel + any backend

    Instrument once with OpenTelemetry, send to Jaeger, Grafana Tempo, Datadog or an LLM-specific tool.

    Key ideas
    • A trace is a tree of timed spans sharing one trace id; attributes make it searchable.
    • Record model, tokens, prompt version and release on every LLM span.
    • The critical path, not the sum of spans, sets latency; parallelize independent steps.
    • OpenTelemetry keeps instrumentation portable across backends.
    Common mistakes
    • Storing full prompts and outputs with personal data and no redaction or retention policy.
    • Tracing only the LLM call, so retrieval and tool latency stay invisible.
    • Losing the trace id at a queue or thread boundary, which splits one request into orphan traces.

    12.4 · Notice before users complain

    Monitoring quality, drift & cost

    Traces show single requests; monitors watch aggregates over time and alert when something moves. AI systems need four kinds: operational health, answer quality, drift in what users send, and cost. The model can be unchanged and still get worse, because the questions changed.

    Why it matters for AI engineers

    Quality problems in AI systems are silent. A dashboard of latency and errors stays green while a new product launch floods the bot with questions it was never evaluated on, or a prompt change quietly doubles token spend.

    Four things to watch

    Measuring drift with PSI

    Drift compares a reference distribution (say, last month's prompt lengths) with the current one. Bin both, then add up how much each bin's share changed. The population stability index (PSI) is the standard score, and it equals the KL divergence measured in both directions.

    \[ \text{PSI} = \sum_{i} (a_i - e_i)\,\ln\frac{a_i}{e_i} = \mathrm{KL}(a\,\|\,e) + \mathrm{KL}(e\,\|\,a), \qquad \mathrm{KL}(p\,\|\,q) = \sum_i p_i \ln\frac{p_i}{q_i} \] \(e_i\) = share of reference data in bin \(i\), \(a_i\) = share of current data. Add a small epsilon to empty bins so the log stays finite.
    Drift detector Try it

    Set the shift to zero and the sample size to 50: PSI is still above zero from noise alone. Small windows need higher thresholds or longer windows.

    import numpy as np

def psi(reference, current, bins=10, eps=1e-4):
    edges = np.quantile(reference, np.linspace(0, 1, bins + 1))   # equal-mass bins on the reference
    edges[0], edges[-1] = -np.inf, np.inf
    e = np.histogram(reference, edges)[0] / len(reference)
    a = np.histogram(current, edges)[0] / len(current)
    e, a = np.clip(e, eps, None), np.clip(a, eps, None)
    return float(np.sum((a - e) * np.log(a / e)))

ref = np.random.lognormal(5.0, 0.6, 50_000)    # last month's prompt lengths (tokens)
cur = np.random.lognormal(5.3, 0.6, 5_000)     # this week: longer prompts
print(round(psi(ref, cur), 3))                  # about 0.25: significant shift
    Key ideas
    • Monitor four families: operational, quality, drift and cost; each needs its own signal.
    • Quality monitoring = LLM-judge scores on a traffic sample + user feedback + proxies like refusal rate.
    • PSI sums per-bin share changes weighted by their log ratio; it is symmetric KL.
    • Small samples produce non-zero PSI from noise; set thresholds and windows accordingly.
    Common mistakes
    • Alerting on every PSI blip from tiny hourly windows until the team mutes the alert.
    • Monitoring averages only; p95 latency and the worst customer's cost matter more.
    • Running the judge on 100% of traffic and paying more for monitoring than for serving.

    12.5 · Remember every attempt

    Experiment tracking

    You will try dozens of variants: chunk sizes, prompts, models, rerankers. An experiment tracker records each attempt as a run with its exact inputs and its results, so "which setup gave 85% last Tuesday?" has an answer and the winner can be reproduced.

    Why it matters for AI engineers

    Without tracking, results live in notebooks and memory, and the best configuration is lost the day someone changes a default. With it, you compare runs side by side and promote one to the registry with full lineage.

    What a run records

    import mlflow

mlflow.set_experiment("support-bot-rag")
with mlflow.start_run(run_name="70b-chunk512-rerank"):
    mlflow.log_params({"model": "llama-3.1-70b", "prompt_version": "v14",
                       "chunk_size": 512, "top_k": 8, "eval_set": "v7"})
    results = run_eval()                          # your eval harness
    mlflow.log_metrics({"answer_quality": results.quality,
                        "cost_per_1k_usd": results.cost, "p95_latency_s": results.p95})
    mlflow.log_artifact("eval_outputs.jsonl")    # every answer, for later inspection

# Weights & Biases equivalent:
#   run = wandb.init(project="support-bot", config={...}); run.log({...}); run.finish()

    Choosing a winner

    Rarely does one run win on everything. Plot quality against cost (or latency) and keep only the Pareto front: runs that no other run beats on both axes. Your budget then picks a point on that front.

    Pick a run from the Pareto front Try it

    ToolStrengthNotes
    MLflowOpen source, self-hostable tracking server, model registry, LLM tracing and evaluationCommon default in Databricks and self-hosted stacks
    Weights & BiasesPolished hosted dashboards, sweeps, artifacts; Weave for LLM appsPopular for training and fine-tuning work
    Langfuse / LangSmithDatasets and experiments over LLM traces and promptsGood fit when the "model" is a prompt + pipeline
    Key ideas
    • A run = exact inputs (commit, data and eval-set versions, config) + outputs (metrics, artifacts, outputs).
    • Only compare runs evaluated on the same eval set version.
    • Choose from the Pareto front of quality vs cost or latency, then apply your budget.
    • Log raw outputs as artifacts so you can inspect failures, not just averages.
    Common mistakes
    • Logging metrics but not the prompt version or data version that produced them.
    • Picking the top run by one metric and discovering it triples latency.
    • Comparing runs across eval sets that changed in between.

    12.6 · The plumbing

    Kubernetes, queues & caching

    Three pieces of infrastructure carry most AI products. Kubernetes runs and scales the containers, including GPU model servers. Queues absorb slow or bursty work so users are not stuck on an open HTTP connection. Caches skip the model entirely when an answer is already known.

    Why it matters for AI engineers

    GPU pods take minutes to start, model calls take seconds, and identical questions arrive all day. Autoscaling on the right metric, async jobs for long tasks and a cache in front of the model often matter more for cost and latency than any prompt tweak.

    A model server on Kubernetes

    apiVersion: apps/v1
kind: Deployment
metadata:
  name: llm-server
spec:
  replicas: 2
  selector:
    matchLabels: { app: llm-server }
  template:
    metadata:
      labels: { app: llm-server }
    spec:
      containers:
        - name: vllm
          image: vllm/vllm-openai:v0.x.y        # pin an exact release tag
          args: ["--model", "Qwen/Qwen2.5-7B-Instruct", "--max-model-len", "16384"]
          ports: [{ containerPort: 8000 }]
          resources:
            limits: { nvidia.com/gpu: 1 }        # exposed by the NVIDIA device plugin
          readinessProbe:
            httpGet: { path: /health, port: 8000 }
            initialDelaySeconds: 60

    Async jobs with a queue

    Anything slower than a few seconds (document processing, agents, batch evals) should not hold an HTTP request open. Return a job id immediately and let workers pull from a queue. Delivery is usually at-least-once, so workers must be idempotent.

    Caching model answers

    An exact cache keys on a hash of model, prompt version, parameters and normalized input. A semantic cache embeds the question and reuses an answer when a past question is similar enough. It hits far more often, and sometimes returns the answer to a subtly different question. Provider prompt caching is a third layer: it reuses the KV cache of a shared prefix and still runs the model.

    Cache hit rate vs cost and latency Try it 

    import numpy as np

class SemanticCache:
    def __init__(self, embed, threshold=0.95):
        self.embed, self.threshold = embed, threshold    # embed() returns a unit-norm vector
        self.keys, self.values = [], []

    def get(self, question, version):
        if not self.keys:
            return None
        q = self.embed(question)
        sims = np.array(self.keys) @ q                   # cosine similarity
        i = int(sims.argmax())
        hit = sims[i] >= self.threshold and self.values[i][0] == version
        return self.values[i][1] if hit else None

    def put(self, question, version, answer):
        self.keys.append(self.embed(question))
        self.values.append((version, answer))           # version = release id; new release, no stale hits
    Key ideas
    • Kubernetes runs model servers as GPU pods; scale on queue depth or running requests and plan for slow cold starts.
    • Queues decouple slow work from requests: 202 + job id, idempotent workers, retries with backoff, a dead-letter queue.
    • Exact caches are safe, semantic caches hit more but can return wrong answers; tune the threshold on real data.
    • Include the release version in cache keys so a new prompt or model never serves stale answers.
    Common mistakes
    • Autoscaling GPU pods on CPU utilization, which barely moves when the GPU is saturated.
    • Scaling to zero for a latency-sensitive service and paying a multi-minute cold start on the first request.
    • Semantic-caching personalized or time-sensitive answers ("my order status").
    • Non-idempotent workers that charge a card twice when a job is redelivered.

    12.7 · Versioned models and features

    Model registries & feature stores

    A model registry is the catalog of every model version you might serve, with its lineage and a movable label for "the one in production". A feature store does the same for model inputs: one definition of each feature, computed the same way for training and for live predictions.

    Why it matters for AI engineers

    Fine-tuned adapters, classifiers, rerankers and embedding models all need versioning, promotion and rollback. Personalization and ranking features need to match exactly between training and serving, or models that looked great offline fail live.

    Registry: versions and aliases

    import mlflow
from mlflow import MlflowClient

mv = mlflow.register_model(f"runs:/{run_id}/model", "support-classifier")
MlflowClient().set_registered_model_alias("support-classifier", "champion", mv.version)

model = mlflow.pyfunc.load_model("models:/support-classifier@champion")   # what serving loads

    For LLM apps, the same idea applies to prompts, adapters and embedding models. Register the embedding model and the vector index as a pair: an index built with one embedding model is useless with another.

    Feature stores and point-in-time correctness

    A point-in-time join attaches to each training example the feature values as they were at that example's timestamp. Joining today's values instead leaks the future into training, and the model looks better offline than it will ever be live.

    Point-in-time join vs naive join Try it 

    from feast import FeatureStore

store = FeatureStore(repo_path=".")
# Training: entity_df has user_id + event_timestamp; Feast does the point-in-time join
train_df = store.get_historical_features(
    entity_df=labels_df,
    features=["user_stats:orders_30d", "user_stats:refunds_90d"],
).to_df()
# Serving: latest values from the online store
feats = store.get_online_features(
    features=["user_stats:orders_30d", "user_stats:refunds_90d"],
    entity_rows=[{"user_id": 1001}],
).to_dict()
    Key ideas
    • A registry holds versioned models with lineage; serving loads an alias like @champion.
    • Promotion and rollback are alias moves, not rebuilds.
    • Version embedding models and indexes together.
    • Feature stores share one definition between an offline store (history) and an online store (latest).
    • Point-in-time joins prevent future data from leaking into training.
    Common mistakes
    • Hard-coding a model version or file path in serving code.
    • Computing features one way in a training notebook and another way in the API (train/serve skew).
    • Joining current feature values to historical labels and celebrating an inflated offline score.
