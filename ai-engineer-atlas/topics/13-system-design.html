AI system design

System design is where models, retrieval, agents and infrastructure become one product that answers fast enough, costs little enough and keeps working when a provider falls over. This area teaches the recurring architectures, the numbers you use to size them, and how to defend your choices in a design review or an interview.

In this area

    Every AI system design follows the same arc: pick an architecture pattern that fits the job, size it against quality, latency, cost and reliability, make it survive rate limits and outages, and design a UX that makes a probabilistic system feel trustworthy. Case studies combine all four.

    13.1 · Reference shapes

    Architecture patterns

    Most AI products use the same parts: a gateway, an orchestrator, retrieval, tools, models and observability. An architecture pattern is a proven arrangement of those parts for a common job, so you can spend your thinking on what is different about this product.

    Why it matters for AI engineers

    Recognising the pattern behind "a Slack bot for HR questions" or "a coding assistant" tells you the latency target, the hard component and the main risk before you draw a single box.

    The building blocks

    The gateway is the single entry point for model traffic: auth, quotas, routing, caching and cost logging. The orchestrator is your application code that builds prompts, calls models and runs tool loops. Retrieval, tools and models hang off the orchestrator, and every box emits traces so you can answer "why did it say that?".

    Composing patterns in practice

    Real products combine patterns. A support product is a chat assistant answering from RAG, with a few agent-style tools, behind a company gateway, plus a nightly batch job that labels conversations for evaluation. Saying the composition out loud shows you know which part needs which latency and model.

    Start with the simplest pattern that could work. Anthropic's "Building effective agents" essay separates fixed workflows (code decides the steps) from agents (the model decides). Use an agent only when the steps cannot be known in advance.

    # A minimal gateway-style router: rules first, then fallbacks.
# `call` is whatever client function you use (OpenAI, Anthropic, vLLM...).
import time

ROUTES = {
    "classify":  ["small-model", "medium-model"],
    "chat":      ["medium-model", "large-model", "small-model"],
    "reasoning": ["large-model", "medium-model"],
}

def route(task: str, prompt_tokens: int) -> list[str]:
    chain = ROUTES.get(task, ROUTES["chat"])
    if prompt_tokens > 100_000:              # only some models take long inputs
        chain = [m for m in chain if m != "small-model"]
    return chain

def complete(task, messages, call, log, timeout_s=20):
    chain = route(task, sum(len(m["content"]) // 4 for m in messages))
    for model in chain:
        t0 = time.monotonic()
        try:
            out = call(model=model, messages=messages, timeout=timeout_s)
            log(model=model, ok=True, ms=1000 * (time.monotonic() - t0))
            return out
        except Exception as err:             # rate limit, timeout, 5xx
            log(model=model, ok=False, error=type(err).__name__)
    raise RuntimeError("all models in the chain failed")
    Key ideas
    • The pattern tells you the latency target and the hard component before you design anything else.
    • Editor copilots live or die on latency; RAG search on ingestion and permissions; agents on loop control and sandboxing; batch on throughput and validation.
    • Prefer a fixed workflow over an agent when the steps are known in advance.
    • A gateway centralises keys, quotas, routing, caching and cost logging for the whole organisation.
    Common mistakes
    • Reaching for a multi-agent framework when one prompt plus retrieval would answer the question.
    • Filtering documents by permission after retrieval, or by instructing the model, instead of inside the retrieval query.
    • Running batch jobs through the synchronous API at full price and hitting rate limits that starve interactive traffic.

    13.2 · The four forces

    Quality, latency, cost & reliability

    Almost every design decision moves four numbers at once. A bigger model raises quality, cost and latency; caching lowers cost and latency but can go stale. Good design writes targets for all four, then measures each component's share so you know which lever to pull.

    Why it matters for AI engineers

    Features fail for boring reasons: a 12-second answer, or $0.40 per request when the plan assumed $0.02. Decomposing latency and cost turns "the model is slow" into "rerank adds 300 ms at p95".

    Latency: where the milliseconds go

    An LLM call has two phases. Prefill reads the whole prompt in parallel; its duration is the time to first token (TTFT) and grows with prompt length. Decode then emits tokens one at a time, each costing a roughly fixed time per output token (TPOT), often 10 to 50 ms.

    \[ T_{\text{total}} \approx T_{\text{net}} + T_{\text{retrieve}} + T_{\text{rerank}} + \text{TTFT} + N_{\text{out}} \cdot \text{TPOT} + T_{\text{guard}} \] \(N_{\text{out}}\): output tokens. 400 tokens at 25 ms each is 10 s, however fast the rest is.

    So the cheapest latency win is fewer output tokens (concise answers, structured fields, a max_tokens cap). Streaming lets the user read while decode continues, which is why products set two targets: TTFT and total.

    Tail latency: percentiles do not add

    Report p50 (the typical request) and p95 (the slow request users remember). Summing component p95s overestimates the total p95, because every component is rarely slow at once. Fan-out works the other way: a request that waits on \(k\) parallel calls, each slow with probability \(q\), is slow with probability \(1-(1-q)^k\).

    Latency budget builder Try it

    The demo fits a log-normal to each component's p50 and p95, simulates 4,000 requests and sums them. Compare the simulated p95 with the naive sum of p95s, and try removing one optional step.

    Cost: a per-request formula you can multiply

    Providers price per million tokens; output costs several times input, and cached input (prefix caching) is heavily discounted.

    \[ C_{\text{req}} = \frac{N_{\text{in}}\big[(1-h)\,p_{\text{in}} + h\,p_{\text{cache}}\big] + N_{\text{out}}\,p_{\text{out}}}{10^6} \cdot s \] \(h\): cached share of input; \(p\): price per million tokens; \(s\): model calls per request (an agent may make 10 to 50).

    Put stable content (system prompt, tool definitions) first so prefix caching hits. The cost calculator in 13.5 lets you try these levers.

    Every lever moves all four numbers

    Reliability is written as a service level objective (SLO), such as "99.9% of requests succeed over 30 days". The remaining 0.1% is the error budget, about 43 minutes a month. Measure every quality lever on an eval set before paying for it.

    Key ideas
    • Write explicit targets for quality, latency (p50 and p95, TTFT and total), cost per request and availability.
    • Input length drives TTFT; output length drives total latency. Fewer output tokens is the cheapest speed-up.
    • Percentiles do not add, and fan-out amplifies tail latency.
    • Cost per request is tokens times prices times calls; multiply by traffic before committing to a design.
    Common mistakes
    • Reporting average latency, which hides the slow tail users complain about.
    • Ignoring the number of calls per request: an agent with 30 steps multiplies every per-call number by 30.
    • Putting dynamic content (timestamps, user names) at the top of the prompt, which breaks prefix caching.

    13.3 · Keep it up

    Rate limits & fallbacks

    Model providers are shared, overloaded and occasionally down. A resilient system limits its own traffic before the provider does, retries carefully, stops calling a dependency that is clearly broken, and falls back to something useful instead of an error page.

    Why it matters for AI engineers

    A single provider at 99.5% availability means over three hours of failures a month. Rate-limit errors (HTTP 429) are among the most common production errors in LLM apps, and naive retry loops turn them into self-inflicted outages.

    Rate limits and the token bucket

    Providers cap requests per minute (RPM) and tokens per minute (TPM), answering excess traffic with HTTP 429. Add per-tenant limits of your own so one runaway agent cannot drain the shared quota.

    The standard algorithm is the token bucket: a bucket holds up to \(B\) tokens and refills at \(r\) per second; each request spends its cost (1 request, or its LLM token count). Over any window \(t\) it admits at most \(B + r\,t\). With several servers, keep the bucket in Redis and update it atomically.

    Token-bucket rate limiter Try it

    Capacity is the burst you tolerate; refill rate is the sustained throughput you promise. Push traffic just above the refill rate and watch rejections settle into a steady trickle.

    Retries, timeouts and circuit breakers

    Retry only errors that can succeed next time (429, 5xx, timeouts), never a 400. Use exponential backoff with jitter: the wait ceiling doubles per attempt and the actual sleep is random below it, so clients that failed together do not retry together. Cap attempts and keep a retry budget (for example at most 10% extra load).

    Streams need a first-token timeout and an idle timeout. A circuit breaker stops calling a failing dependency so users skip its timeout. Hedged requests duplicate a call that has not answered by its p95.

    import random, time

RETRYABLE = {429, 500, 502, 503, 504, 529}

class TokenBucket:
    def __init__(self, capacity: float, rate: float):
        self.capacity, self.rate = capacity, rate
        self.tokens, self.t = capacity, time.monotonic()

    def allow(self, cost: float = 1.0) -> bool:
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.t) * self.rate)
        self.t = now
        if self.tokens >= cost:
            self.tokens -= cost
            return True
        return False

def call_with_retry(send, max_attempts=3, base=0.5, cap=8.0):
    for attempt in range(max_attempts):
        status, body, retry_after = send()
        if status < 400:
            return body
        if status not in RETRYABLE or attempt == max_attempts - 1:
            raise RuntimeError(f"giving up after status {status}")
        ceiling = min(cap, base * 2 ** attempt)
        sleep_s = retry_after if retry_after else random.uniform(0, ceiling)  # full jitter
        time.sleep(sleep_s)

    Fallback chains and availability math

    A fallback chain is an ordered list of ways to answer, each cheaper and less capable than the last, ending in an honest degraded response.

    \[ A_{\text{serial}} = \prod_i a_i \qquad\qquad A_{\text{fallback}} = 1 - \prod_i (1 - a_i) \] Series: multiply availabilities. Fallbacks: multiply failure probabilities. Two independent 99.5% providers give \(1 - 0.005^2 = 99.9975\%\), if failures really are independent.

    Independence is the trap. Endpoints sharing a region fail together, a too-long prompt fails on every model, and an outage at one provider sends everyone's traffic to the next. Diversify for real, keep a non-LLM last resort, and run evals on the fallback prompt too.

    Fallback chain simulator Try it

    Raise the correlation and availability falls towards the primary's own; open the breaker and mean latency drops.

    Key ideas
    • Enforce your own per-user and per-tenant limits with token buckets so one caller cannot exhaust the shared provider quota.
    • Retry only retryable errors, with capped exponential backoff, jitter and a retry budget; honour Retry-After.
    • Serial availability multiplies; fallback availability multiplies failure probabilities, but only if failures are independent.
    • End every chain with a non-LLM degraded response, and evaluate the fallback path like the primary.
    Common mistakes
    • Retrying immediately in a tight loop, which multiplies load on an already overloaded provider.
    • Retrying non-idempotent tool calls (send email, charge card) without an idempotency key.
    • Falling back to a model whose prompt was never tested, so outages also become quality incidents.

    13.4 · Designing for a probabilistic system

    UX for AI products

    AI features are slow, sometimes wrong and a little unpredictable, so the interface has three extra jobs: make waiting feel short, help users judge how much to trust each answer, and let them correct or undo what the system did.

    Why it matters for AI engineers

    These are engineering decisions in disguise. Streaming needs a server-sent-events endpoint, citations need stable chunk IDs, undo needs an action log, and feedback needs trace IDs. If the backend lacks them, no designer can add them later.

    Make waiting feel short

    Usability research gives three limits: 0.1 s feels instant, 1 s keeps the flow of thought, 10 s loses attention. LLM answers land between 1 and 10 s, so stream tokens, show steps ("Searching 3 sources..."), and go asynchronous with a notification beyond 10 to 20 s.

    Calibrate trust

    Aim for calibrated trust: users rely on the answer when it is right and check it when it might be wrong. Each technique below needs backend support.

    Citations next to claims

    One click to verify. Needs stable chunk IDs from retrieval.

    An honest "not found" path

    A designed empty state beats a guess. Needs abstention in the prompt and the eval set.

    Clear scope

    Starter prompts show what the assistant is for, and steer users to questions you have evaluated.

    Concrete confidence

    "Based on 2 sources, updated March" beats an uncalibrated percentage. Label AI-generated content.

    Match autonomy to reversibility

    Let autonomy follow the cost and reversibility of a mistake. Ignoring a ghost-text suggestion costs nothing; a customer email needs draft-and-approve; moving money needs confirmation, limits and an audit log. Show diffs, keep undo, and prefer edit-in-place over "regenerate".

    Close the feedback loop

    Thumbs ratings are sparse (often under 1% of interactions) and skewed towards angry users. Implicit signals (copy, accept, heavy edit, regenerate, rephrase, abandon) are far richer. Join every signal to the request's trace ID so a bad answer leads to the exact prompt, chunks and model version.

    # Streaming endpoint with server-sent events, plus a trace id the UI echoes
# back with feedback. Uses FastAPI and the Anthropic Python SDK.
import json, uuid
import anthropic
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()
client = anthropic.Anthropic()
MODEL = "your-model-id"

@app.post("/chat")
def chat(body: dict):
    trace_id = str(uuid.uuid4())
    def events():
        yield f"data: {json.dumps({'type': 'start', 'trace_id': trace_id})}\n\n"
        with client.messages.stream(model=MODEL, max_tokens=800,
                                    messages=body["messages"]) as stream:
            for text in stream.text_stream:
                yield f"data: {json.dumps({'type': 'text', 'text': text})}\n\n"
        yield f"data: {json.dumps({'type': 'done'})}\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")

@app.post("/feedback")
def feedback(body: dict):
    # body: {"trace_id": ..., "signal": "thumbs_down" | "copied" | "edited", ...}
    print(json.dumps(body))   # in production: write to your trace store
    return {"ok": True}

    Task takes minutesasync task list, notificationjob queue, durable state, status API

    Key ideas
    • Streaming turns perceived latency into TTFT; show progress for multi-step work and go asynchronous past about 10–20 s.
    • Aim for calibrated trust: citations, honest abstention, clear scope and visible AI provenance.
    • Set autonomy by reversibility: suggest, draft, act on confirmation, act with undo.
    • Implicit signals (accept, copy, edit, regenerate) beat sparse thumbs ratings; join them to trace IDs.
    Common mistakes
    • A blank spinner for eight seconds when the first tokens were ready after one.
    • Showing a numeric "confidence" that is not calibrated, which teaches users to trust the wrong answers.
    • Letting an agent take irreversible actions with no confirmation, limit or audit trail.

    13.5 · Putting it together

    Design case studies

    A system design answer is a story with numbers: clarify requirements, estimate load and cost, draw an architecture that meets the targets, go deep on the hardest parts, and close with trade-offs and how you would know it works.

    Why it matters for AI engineers

    "Design an AI assistant for X" is a standard AI engineering interview question, and design docs with back-of-envelope numbers are what get real projects funded.

    A repeatable framework

    Little's law turns traffic into concurrency, which sizes streams, workers and sandboxes.

    \[ L = \lambda \cdot W \] \(L\): requests in flight; \(\lambda\): arrivals per second; \(W\): seconds per request. 7/s streaming for 8 s each is about 56 concurrent streams.

    Case 1: a customer-support assistant over 1M documents

    Requirements. A retailer's help-page assistant answers from the help center, internal KB and past tickets (1M documents, several languages), looks up orders, issues small refunds after customer confirmation, and hands off to humans. Targets: 50,000 conversations a day of about 4 turns, p95 TTFT under 2 s, 90% correct and grounded on a 500-question eval set, a citation on every factual answer.

    QuantityCalculationResult
    Corpus1M docs × 1,500 tokens1.5B tokens
    Chunks~400 tokens each, small overlap~4.5M chunks
    Vector index4.5M × 1,024 dims × 4 bytes~18 GB (≈4.5 GB int8) + HNSW overhead
    Embed corpus once1.5B tokens × example $0.02/M~$30
    Model calls50k × 4 turns200k/day ≈ 2.3/s avg, ~7/s peak
    Concurrent streams7/s × 8 s (Little's law)~56
    Tokens per call2k system+tools (cached) + 2k chunks + 1k history + 100~5,100 in, 250 out
    Cost per call3,100×$3 + 2,000×$0.30 + 250×$15, per 1M~$0.014
    Monthly bill200k × 30 × $0.014~$82k; ~$38k if 60% routed to a 10× cheaper model

    Deep dive. Hybrid search (BM25 for order numbers, vectors for paraphrases) with locale and visibility filters inside the query, then rerank 50 to 5. Ingest only recent resolved tickets, PII-scrubbed and ranked below official articles. Freshness beats embedding choice: ingest CMS change events within minutes.

    Trade-offs. The router adds ~200 ms but saves most of the cost. Ticket text is untrusted, so refunds need customer confirmation and server-side limits. Evaluate offline on the golden set and online with resolution, handoff and repeat-contact rates.

    Case 2: a coding agent that turns issues into pull requests

    Requirements. An agent picks up tracker issues, edits a repository of up to 1M lines, runs tests in a sandbox and opens a pull request for human review. 500 tasks a day, under 30 minutes and a few dollars each, never pushing to the main branch or touching production secrets.

    QuantityCalculationResult
    Repository1M lines × ~10 tokens~10M tokens: never fits; navigate with tools
    Input per task40 steps × ~45k average context~1.8M tokens
    Input cost15% uncached × $3 + 85% cached × $0.30~$1.27
    Output cost40 × 400 tokens × $15/M~$0.24, so ~$1.50/task

    Trade-offs. Text search and language-server symbol lookup beat a stale embedding index for most code navigation. Long tasks need context compaction (summarise old tool output) and a stable prompt prefix for caching. Issue text and repository files are untrusted input, so all safety lives in the sandbox and token scope. Evaluate on historical issues with hidden tests, SWE-bench style, tracking resolve rate, cost per task and PR merge rate.

    Case 3: batch extraction from 10M pages a month

    DecisionNumbers and reasoning
    Throughput10M / 30 days ≈ 333k pages/day ≈ 4 pages/s; a queue with a worker pool, no user waiting
    Cost~1,000 in + 200 out per page ≈ $0.006 at the example prices; batch API halves it to ≈ $1,000/day, a small model cuts it far more
    CorrectnessJSON schema plus arithmetic checks (line items sum to total); ~5% low-confidence pages go to human review
    Idempotencykey = document hash + schema version, so retries and re-runs never duplicate rows
    Key ideas
    • Follow the five steps: requirements, estimates, diagram, deep dives, trade-offs with evaluation.
    • Back-of-envelope numbers (tokens, QPS, concurrency, dollars) turn a box diagram into a design.
    • Little's law sizes streams, workers and sandboxes.
    • Put safety in architecture (sandboxes, scoped tokens, server-side limits), not in the prompt.
    Common mistakes
    • Drawing boxes before asking about traffic, latency and quality targets.
    • Forgetting to multiply per-call cost by calls per request, which hides most of an agent's bill.
    • No evaluation plan, or "we'll use an LLM judge" with no golden set to calibrate it.
