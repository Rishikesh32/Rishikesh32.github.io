Fine-tuning & adaptation

Fine-tuning changes a model's weights so it behaves the way your product needs, instead of asking nicely in every prompt. This area covers when that is worth it, how supervised fine-tuning, LoRA and preference tuning actually work, and how to run them on hardware you can afford.

In this area

    Adapting a model is a pipeline with a decision at the front. First you decide whether the problem needs new weights at all (09.1). If it does, supervised fine-tuning teaches the format and behaviour by imitation (09.2), and preference tuning sharpens it by comparison or reward (09.4). LoRA and QLoRA are how you make either step cheap enough to run on one GPU (09.3). Distillation and synthetic data are where much of the training data comes from (09.5), and the Hugging Face tooling ties it together (09.6).

    09.1 · The decision

    Prompt vs RAG vs fine-tune

    You have three levers for changing a model's output. The prompt changes what you tell it, retrieval (RAG) changes what it can see, and fine-tuning changes what it is. They fix different problems at very different costs, so the skill is matching the lever to the failure.

    Why it matters for AI engineers

    Teams lose weeks fine-tuning a model to "know" their docs and still get hallucinations, while others pay for huge prompts a small fine-tuned model could replace.

    Diagnose the failure first

    Pull 30 to 50 bad outputs and sort each one by what is actually wrong. The bucket with the most failures tells you which lever to pull.

    Fine-tuning is a poor way to add facts. RAG beat it for knowledge injection (Ovadia et al., 2023), training on unknown facts increases hallucination (Gekhman et al., 2024), and facts in weights cannot be cited or updated.

    Two separate axes

    Knowledge and behaviour are independent. RAG moves you along one axis, fine-tuning along the other, and many production systems use both.

    The cost ladder

    Each lever costs more to build and maintain than the one before. The easily forgotten cost: when a better base model ships, a prompt carries over in an afternoon, while a fine-tune must be redone.

    LeverFixesData neededTime to first resultOngoing cost
    PromptingInstructions, light format, few-shot behaviour0–20 examplesHoursLong prompts are paid on every call (caching helps)
    RAG / toolsMissing, private or fast-changing facts; citationsA document corpusDaysIndex upkeep, retrieval latency, context tokens
    SFT (usually LoRA)Consistent format, style, domain behaviour, shorter promptsHundreds to tens of thousands of good examplesDays to weeksHosting, retraining on base-model upgrades
    Preference / RL tuningQuality judgements, verifiable skills, refusalsPreference pairs or a reward functionWeeksAs SFT, plus reward and data maintenance
    DistillationCost and latency of a big model that already worksThousands of teacher outputsWeeksRe-distil when the task drifts

    A decision procedure

    1. Build a 100–300 example eval set first (Area 10).
    2. Max out prompting on the strongest model you can afford. This sets the ceiling.
    3. Fix knowledge failures with retrieval.
    4. Fine-tune for stable behaviour or format failures once you have a few hundred good examples.
    5. Re-run the same eval, plus a general-abilities slice, on the result.

    Worked example: a 40-category ticket classifier with a 2,500-token prompt at 2 million tickets a month uses about 5 billion input tokens. A LoRA-tuned 3B model with a 150-token prompt matches it on one GPU.

    Which lever should you pull? Try it

    Key ideas
    • Classify failures first: knowledge, behaviour or format, capability, or cost.
    • RAG is for facts. Fine-tuning is for behaviour, format and style. They combine well.
    • Prompting on the strongest model sets the quality ceiling and is the baseline every fine-tune must beat.
    • Fine-tuning pays off at high volume, with stable tasks, and when it lets a smaller model replace a bigger one.
    • Every fine-tune carries a maintenance cost when the base model changes.
    Common mistakes
    • Fine-tuning on a document dump to make the model "know" your docs, then being surprised by confident hallucinations.
    • Starting a fine-tune before there is an eval set, so nobody can say whether it worked.
    • Comparing a fine-tuned model against a weak prompt instead of the best prompt you can write.
    • Ignoring the cost of retraining when the base model is upgraded or the label set changes.

    09.2 · Learning by imitation

    Supervised fine-tuning

    Supervised fine-tuning (SFT) continues next-token training on curated conversations. Render each example with the model's chat template, and compute loss only on the tokens the model should learn to write.

    Why it matters for AI engineers

    SFT is the first step of almost every custom fine-tune. Most SFT failures are formatting bugs: wrong template, missing end-of-turn token, unmasked prompts.

    Chat templates

    A chat model never sees a list of messages. The chat template, a Jinja rule stored with the tokenizer, renders them into one token stream with special tokens marking each turn. ChatML-style models see this:

    <|im_start|>system
You are a support assistant. Reply with one action.<|im_end|>
<|im_start|>user
My card was charged twice for order 1182.<|im_end|>
<|im_start|>assistant
Refund issued for the duplicate charge.<|im_end|>

    Other families use other tokens, so always call tokenizer.apply_chat_template and serve with the training template. Keep the end-of-turn token in the labels or the model never stops.

    Loss masking: learn the answer, not the question

    You want the model to learn assistant turns, not to predict user messages. So every non-assistant token gets label -100, the default ignore_index of PyTorch's cross-entropy. With \(A\) the assistant positions:

    \[ \mathcal{L}_{\text{SFT}}(\theta) = -\frac{1}{|A|}\sum_{t \in A} \log p_\theta\left(x_t \mid x_{\lt t}\right) \] The context \(x_{\lt t}\) still includes the system and user tokens, so the model conditions on them. They just never appear as prediction targets.

    Masking matters most when prompts are long. Drag the sliders: with a 1,500-token retrieved context and a 60-token answer, an unmasked loss spends about 96% of its signal predicting the context.

    Where does the training signal go? Try it

    Writing the masking once by hand shows what libraries do for you:

    from transformers import AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct")

def build_example(messages, max_len=2048):
    # messages ends with the assistant turn we want to learn
    prompt_txt = tok.apply_chat_template(messages[:-1], add_generation_prompt=True, tokenize=False)
    full_txt = tok.apply_chat_template(messages, tokenize=False)
    # the template already contains special tokens, so don't add BOS/EOS again
    prompt_ids = tok(prompt_txt, add_special_tokens=False)["input_ids"]
    full_ids = tok(full_txt, add_special_tokens=False)["input_ids"]
    assert full_ids[:len(prompt_ids)] == prompt_ids, "template is not prefix-stable"
    labels = [-100] * len(prompt_ids) + full_ids[len(prompt_ids):]
    return {"input_ids": full_ids[:max_len], "labels": labels[:max_len]}

ex = build_example([
    {"role": "user", "content": "My card was charged twice for order 1182."},
    {"role": "assistant", "content": "Refund issued for the duplicate charge."},
])
n_trained = sum(l != -100 for l in ex["labels"])
print(len(ex["input_ids"]), "tokens,", n_trained, "trained on")

    Packing joins short examples into one sequence to avoid padding, resetting attention at boundaries. Set max_length near the 95th–99th percentile so long examples keep their answers.

    Data and hyperparameters

    Quality dominates: LIMA built a strong chat model from 1,000 curated examples. Keep eval and train sets free of near-duplicates.

                     train_dataset=ds["train"], eval_dataset=ds["eval"])
trainer.train()

    Catastrophic forgetting

    Catastrophic forgetting is the loss of earlier abilities after training on a narrow distribution. Qi et al. (2023) showed that fine-tuning on as few as 100 benign examples can weaken an aligned model's refusals.

    Mitigations, cheapest first: LoRA (it "learns less and forgets less"), a lower learning rate and fewer epochs, 5–20% general replay data, and a before/after general-abilities eval.

    Key ideas
    • SFT uses the pretraining loss on curated conversations, rendered with the model's exact chat template.
    • Mask non-assistant tokens with label -100; keep the end-of-turn token as a target so the model learns to stop.
    • A few hundred to a few thousand clean, consistent examples usually beat a large noisy set.
    • Evaluate checkpoints on the task and on general abilities; loss alone does not tell you which checkpoint to ship.
    • Forgetting is real: prefer LoRA, low learning rates, few epochs and replay data.
    Common mistakes
    • Training with one chat template and serving with another, which quietly degrades every response.
    • Dropping the end-of-turn token from the labels, producing a model that never stops generating.
    • Right-truncating long examples so their answers vanish from the loss.
    • Training five epochs on 300 examples and shipping the checkpoint with the lowest training loss.

    09.3 · Parameter-efficient fine-tuning

    LoRA & QLoRA

    Full fine-tuning rewrites every weight: 16.8 million numbers for one 4096 × 4096 matrix. LoRA freezes it and learns the change as two thin matrices, about 131 thousand numbers. QLoRA also stores the frozen base in 4 bits.

    Why it matters for AI engineers

    Most custom fine-tunes use LoRA. Adapters are tens of megabytes, training memory drops several times, and one server can host many adapters on a shared base.

    The low-rank idea

    LoRA (Hu et al., 2021) assumes the fine-tuning update has low intrinsic rank: the useful change lives in a few directions, so \(\Delta W = BA\) with a small inner dimension \(r\), the rank.

    \[ h = W_0 x + \Delta W x = W_0 x + \frac{\alpha}{r}\, B A x, \qquad W_0 \in \mathbb{R}^{d \times k},\; B \in \mathbb{R}^{d \times r},\; A \in \mathbb{R}^{r \times k},\; r \ll \min(d,k) \] \(W_0\) is frozen. Only \(A\) and \(B\) receive gradients. \(\alpha\) (lora_alpha) is a constant that scales the update.

    \(B\) starts at zero, so training begins exactly at the base model. The \(\alpha / r\) scale keeps update size stable across ranks (use \(\alpha = r\) or \(2r\)). Afterwards, merge \(W_0 + \frac{\alpha}{r}BA\) for zero overhead or hot-swap adapters.

    Counting parameters

    Each adapted \(d \times k\) matrix adds \(r(d + k)\) parameters. For Llama 3 8B (hidden 4096, MLP 14336, k/v projecting to 1024 because of grouped-query attention) at \(r = 16\):

    • q and o: \(16 \times (4096 + 4096) = 131{,}072\) each
    • k and v: \(16 \times (4096 + 1024) = 81{,}920\) each
    • gate, up and down: \(16 \times (4096 + 14336) = 294{,}912\) each

    That is 1.31M per layer and 41.9M over 32 layers: about 0.5% of the base, or an 84 MB bf16 adapter.

    LoRA parameter and memory calculator Try it

    Target choice matters more than rank. The original paper adapted only q and v; QLoRA found all linear layers were needed to match full fine-tuning, after which ranks 8 to 64 performed similarly.

    QLoRA: a frozen 4-bit base

    With LoRA the frozen base dominates memory. QLoRA (Dettmers et al., 2023) stores it as NF4, 4-bit levels at normal quantiles in blocks of 64, compresses the block scales (double quantisation) and pages optimiser state to CPU.

    Blocks are dequantised to bf16 for each matmul, so QLoRA is slower per step. It tuned a 65B model on one 48 GB GPU at 16-bit quality.

    import torch
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

bnb = BitsAndBytesConfig(
    load_in_4bit=True,
    bnb_4bit_quant_type="nf4",
    bnb_4bit_use_double_quant=True,
    bnb_4bit_compute_dtype=torch.bfloat16,   # matmuls run in bf16
)
model = AutoModelForCausalLM.from_pretrained("meta-llama/Llama-3.1-8B-Instruct",
                                             quantization_config=bnb, device_map="auto")
model = prepare_model_for_kbit_training(model)   # enables grad checkpointing, casts norms

lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                  target_modules="all-linear", task_type="CAUSAL_LM")
model = get_peft_model(model, lora)
model.print_trainable_parameters()
# trainable params: ~42M || all params: ~8B || trainable%: ~0.5

    PEFT also offers DoRA, rsLoRA and LoRA+. LoRA learns less than full fine-tuning on very different data, and forgets less.

    Key ideas
    • LoRA learns \(\Delta W = \frac{\alpha}{r}BA\) beside a frozen \(W_0\); each adapted matrix adds \(r(d+k)\) parameters.
    • B starts at zero, so training starts exactly at the base model.
    • The \(\alpha/r\) scale keeps update size stable across ranks; target modules matter more than rank.
    • QLoRA stores the base in NF4 with double quantisation and trains bf16 adapters, cutting base memory about 4×.
    • Adapters can be merged for zero overhead or hot-swapped to serve many fine-tunes on one base.
    Common mistakes
    • Using the full fine-tuning learning rate (2e-5) for LoRA and concluding that LoRA "doesn't learn".
    • Raising r without adjusting alpha consistently between experiments, so runs are not comparable.
    • Adapting only q and v and blaming LoRA for the quality gap.
    • Merging a QLoRA adapter into 4-bit weights, or shipping a merge without re-running evals.

    09.4 · Learning from comparisons and rewards

    RLHF, DPO & GRPO

    SFT teaches by showing a good answer. Preference tuning teaches by judging: "A is better than B" or "this answer passed the tests". That works when good answers are hard to write but easy to judge.

    Why it matters for AI engineers

    Every chat model was shaped by preference tuning. DPO fits user preference data; GRPO with verifiable rewards trains reasoning and checkable skills like SQL.

    RLHF: a reward model plus RL

    Humans pick the better of two responses. A reward model \(r_\phi\) learns those choices with the Bradley–Terry model, \(P(y_w \succ y_l) = \sigma(r_\phi(x,y_w) - r_\phi(x,y_l))\). Then PPO optimises the policy against it:

    \[ \max_{\pi_\theta}\; \mathbb{E}_{x \sim D,\, y \sim \pi_\theta(\cdot \mid x)}\big[r_\phi(x,y)\big] \;-\; \beta\, \mathbb{D}_{\mathrm{KL}}\big[\pi_\theta(y \mid x)\,\|\,\pi_{\text{ref}}(y \mid x)\big] \] The KL penalty, weighted by \(\beta\), stops the policy from drifting into strange text that the reward model happens to score highly (reward hacking).

    PPO keeps four models in memory and samples inside the loop, so it is heavy. Push too hard and the policy exploits reward-model blind spots, such as length.

    DPO: the reward model hiding inside the policy

    DPO (Rafailov et al., 2023) notes that the KL-constrained optimum is \(\pi^* \propto \pi_{\text{ref}}\exp(r/\beta)\), so any policy implies a reward \(r = \beta \log \frac{\pi}{\pi_{\text{ref}}} + \beta\log Z(x)\). Plug that into Bradley–Terry and \(Z(x)\) cancels, leaving a classification loss on pairs:

    \[ \mathcal{L}_{\text{DPO}}(\theta) = -\,\mathbb{E}_{(x,\,y_w,\,y_l)}\left[\log \sigma\!\left(\beta \log \frac{\pi_\theta(y_w \mid x)}{\pi_{\text{ref}}(y_w \mid x)} \;-\; \beta \log \frac{\pi_\theta(y_l \mid x)}{\pi_{\text{ref}}(y_l \mid x)}\right)\right] \] \(y_w\) is the chosen response, \(y_l\) the rejected one. Each log-probability is the sum over the response's tokens. \(\pi_{\text{ref}}\) is a frozen copy of the starting (SFT) model.

    The implicit reward \(\hat r(y) = \beta \log \frac{\pi_\theta(y\mid x)}{\pi_{\text{ref}}(y\mid x)}\) measures how far the policy raised a response. The loss is logistic on the margin \(\hat r(y_w) - \hat r(y_l)\), weighted by \(\sigma(-\text{margin})\), so solved pairs contribute little. \(\beta\) (0.05–0.5) ties the policy to the reference.

    DPO loss on one preference pair Try it

    Set both sliders negative with rejected lower: the loss falls while the chosen answer loses probability, so track both rewards. Variants: KTO (unpaired labels), ORPO and SimPO (no reference model).

    GRPO and reinforcement learning with verifiable rewards

    When a program can check the answer, use reinforcement learning with verifiable rewards (RLVR). GRPO (DeepSeekMath, DeepSeek-R1) samples \(G\) completions per prompt and scores each against its group:

    \[ \hat A_i = \frac{r_i - \operatorname{mean}(r_1,\dots,r_G)}{\operatorname{std}(r_1,\dots,r_G)} \] Completions better than their siblings get a positive advantage and become more likely; worse ones become less likely. The update uses a PPO-style clipped ratio, optionally with a KL penalty to the reference.

    The group mean replaces PPO's value network. Prompts the model always or never solves give zero advantage, so aim for 20–80% solve rates. The model optimises exactly what the checker checks.

    # DPO with TRL: rows need "prompt", "chosen", "rejected" (strings or chat messages)
from datasets import load_dataset
from trl import DPOConfig, DPOTrainer, GRPOConfig, GRPOTrainer

pairs = load_dataset("json", data_files="pairs.jsonl", split="train")
dpo = DPOTrainer(
    model="sft-support/checkpoint-best",      # start from your SFT model
    args=DPOConfig(output_dir="dpo-out", beta=0.1, learning_rate=5e-7,
                   per_device_train_batch_size=4, gradient_accumulation_steps=8, bf16=True),
    train_dataset=pairs,                        # reference model = frozen copy by default
)
dpo.train()

# GRPO with a verifiable reward. Extra dataset columns (here "answer") arrive as kwargs.
def exact_answer(completions, answer, **kwargs):
    return [1.0 if c.strip().split()[-1:] == [str(a)] else 0.0
            for c, a in zip(completions, answer)]

maths = load_dataset("json", data_files="maths.jsonl", split="train")  # "prompt", "answer"
grpo = GRPOTrainer(
    model="Qwen/Qwen2.5-1.5B-Instruct",
    reward_funcs=exact_answer,
    args=GRPOConfig(output_dir="grpo-out", num_generations=8,
                    max_completion_length=512, learning_rate=1e-6, bf16=True),
    train_dataset=maths,
)
grpo.train()

    Key ideas
    • Preference tuning learns from judgements that are easier to give than ideal answers are to write.
    • RLHF = Bradley–Terry reward model + PPO with a KL penalty to a reference model.
    • DPO's implicit reward is \(\beta\) times the policy/reference log-ratio; its loss is a logistic loss on the chosen-minus-rejected margin.
    • GRPO replaces the value network with a group-mean baseline and pairs naturally with verifiable rewards.
    • Whatever the reward measures, the model will optimise, including its loopholes.
    Common mistakes
    • Running DPO directly on a base model without SFT first; it needs a reasonable starting policy.
    • Using a learning rate suited to SFT; DPO typically needs one 10 to 100 times smaller.
    • Training GRPO on prompts that are always solved or never solved, which yield zero advantage.
    • Preference data where the chosen answer is systematically longer, which teaches verbosity.

    09.5 · Big model teaches small model

    Distillation & synthetic data

    Distillation trains a small student to imitate a large teacher, using the teacher's probability distributions or generated text as training data, to keep most of the quality at a fraction of the cost.

    Why it matters for AI engineers

    Many small open models are trained partly on synthetic data from bigger ones, and distillation is the standard way to cut cost once a large-model prototype works.

    Logit distillation

    A teacher's full distribution carries more information than the correct answer alone. If the teacher gives "Paris" 0.90 and "Lyon" 0.04, the student learns that Lyon is a plausible wrong answer. Hinton et al. (2015) called this "dark knowledge".

    \[ \mathcal{L}_{\text{KD}} = \lambda\, T^2\, \mathrm{KL}\!\left(\mathrm{softmax}(z_t/T)\,\|\,\mathrm{softmax}(z_s/T)\right) + (1-\lambda)\,\mathrm{CE}\!\left(y,\ \mathrm{softmax}(z_s)\right) \] \(z_t, z_s\) are teacher and student logits. Temperature \(T \gt 1\) softens both distributions so small probabilities matter; the \(T^2\) factor keeps gradient size comparable as \(T\) changes.

    Sequence-level distillation and synthetic data

    With only API access, distil through text: generate responses and run SFT on them, as the distilled DeepSeek-R1 models did with about 800k R1 samples. Check the teacher's terms of service first.

    Diversity is the hard part: seed from real logs or a taxonomy, vary personas and difficulty, and keep only verified outputs (rejection sampling). Keep real data in the mix to avoid model collapse (Shumailov et al., 2023).

    import torch.nn.functional as F

def kd_loss(student_logits, teacher_logits, labels, T=2.0, lam=0.5):
    # logits: (N, vocab) for N unmasked token positions; labels: (N,)
    soft = F.kl_div(F.log_softmax(student_logits / T, dim=-1),
                    F.log_softmax(teacher_logits / T, dim=-1),
                    log_target=True, reduction="batchmean") * T * T
    hard = F.cross_entropy(student_logits, labels)
    return lam * soft + (1 - lam) * hard

# Sequence-level: rejection-sample teacher outputs, keep verified, unique ones
import hashlib

def build_dataset(prompts, call_teacher, verify, n=4):
    seen, rows = set(), []
    for p in prompts:
        for out in (call_teacher(p) for _ in range(n)):   # call_teacher: your LLM API call
            key = hashlib.sha256(out.strip().lower().encode()).hexdigest()
            if key not in seen and verify(p, out):
                seen.add(key)
                rows.append({"prompt": p, "completion": out})
                break                                      # first verified sample per prompt
    return rows
    Key ideas
    • Logit distillation matches the teacher's softened distribution with a KL loss scaled by \(T^2\).
    • Sequence-level distillation is SFT on teacher-generated text and works through an API.
    • Synthetic data quality comes from filtering: verifiers, rejection sampling, dedup and decontamination.
    • Keep real data in the mix to avoid collapsing diversity.
    Common mistakes
    • Generating thousands of near-identical examples from one prompt template.
    • Skipping decontamination, so the eval set leaks into training and scores look inflated.
    • Using a teacher whose terms of service forbid training on its outputs.
    • Distilling a teacher that has never been evaluated on your task, copying its errors at scale.

    09.6 · From script to trained model

    Fine-tuning tooling

    Open-model fine-tuning runs on a layered Hugging Face stack: Transformers loads, PEFT adapts, bitsandbytes quantises, TRL trains and Accelerate scales out. Knowing the layers lets you debug a run instead of copying notebooks.

    Why it matters for AI engineers

    Most fine-tuning time goes into environment problems, out-of-memory errors and silent formatting bugs. Knowing the stack and doing the memory maths before you rent a GPU turns a week of trial and error into an afternoon.

    The stack

    Managed fine-tuning APIs from model providers and clouds hide all of this: upload JSONL, get a model ID. You trade control (hyperparameters, data inspection, weight access) for convenience.

    Will it fit?

    Full fine-tuning with mixed-precision Adam costs about 16 bytes per parameter before activations: an 8B model needs about 128 GB. LoRA keeps the base frozen at 2 bytes per parameter, and QLoRA drops that to about 0.5.

    Activations scale with tokens per micro-batch. Gradient checkpointing trades about 30% more compute for far less memory. Don't forget the logits: 4,096 tokens × 128k vocabulary in fp32 is about 2 GB.

    Full fine-tune vs LoRA vs QLoRA: GPU memory Try it

    An end-to-end QLoRA run

    import torch
from datasets import load_dataset
from peft import LoraConfig, AutoPeftModelForCausalLM
from transformers import AutoModelForCausalLM, BitsAndBytesConfig
from trl import SFTConfig, SFTTrainer

base = "meta-llama/Llama-3.1-8B-Instruct"
bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_use_double_quant=True, bnb_4bit_compute_dtype=torch.bfloat16)
model = AutoModelForCausalLM.from_pretrained(base, quantization_config=bnb, device_map="auto")

trainer = SFTTrainer(
    model=model,
    train_dataset=load_dataset("json", data_files="train.jsonl", split="train"),
    peft_config=LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05,
                           target_modules="all-linear", task_type="CAUSAL_LM"),
    args=SFTConfig(output_dir="qlora-out", learning_rate=2e-4, num_train_epochs=2,
                   per_device_train_batch_size=2, gradient_accumulation_steps=16,
                   gradient_checkpointing=True, optim="paged_adamw_8bit",
                   bf16=True, max_length=2048, report_to="none"),
)
trainer.train()
trainer.save_model("qlora-out/adapter")          # saves only the adapter (~tens of MB)

# Merge into a bf16 copy of the base for serving (older versions: torch_dtype=)
merged = AutoPeftModelForCausalLM.from_pretrained("qlora-out/adapter", dtype=torch.bfloat16)
merged = merged.merge_and_unload()
merged.save_pretrained("qlora-out/merged")
    Key ideas
    • Transformers loads, PEFT adapts, bitsandbytes quantises, TRL trains, Accelerate scales out.
    • Full fine-tuning costs about 16 bytes per parameter; LoRA about 2; QLoRA about 0.5, plus activations.
    • Gradient checkpointing and smaller micro-batches with gradient accumulation are the first fixes for out-of-memory.
    • Save adapters during training; merge into a bf16 base only for serving, then re-evaluate.
    Common mistakes
    • Renting a GPU before doing the memory maths, then fighting out-of-memory errors for a day.
    • Forgetting the logits tensor when estimating memory for large-vocabulary models.
    • Mixing library versions from different tutorials; pin versions per project.
    • Serving the merged model with a different chat template or generation config than training used.
