Retrieval-augmented generation

A language model only knows what was in its training data and what you put in its prompt. Retrieval-augmented generation (RAG) searches your own documents at question time and hands the best passages to the model, so answers are current, specific and citable. Most production LLM features that touch company knowledge are RAG systems underneath.

In this area

    Every RAG system has two pipelines. The ingest pipeline runs offline: it parses documents, splits them into chunks, embeds each chunk and writes it to an index. The query pipeline runs on every request: it rewrites the question, retrieves candidates from the indexes, reranks them and lets the model answer from the winners. Each box below is a subtopic on this page, and evaluation measures both halves.

    07.1 · Meaning as geometry

    Embeddings & semantic search

    An embedding model turns a piece of text into a fixed-length list of numbers, such as 384 or 1,536 of them, so that texts with similar meaning land close together. Semantic search embeds the question with the same model and returns the stored vectors nearest to it. "I forgot my login" and "Reset your password" share no words, yet their vectors sit side by side.

    Why it matters for AI engineers

    Retrieval quality caps answer quality: if the right passage is not in the top results, no prompt can fix the answer. The same vectors also power deduplication, clustering, recommendations and classification.

    From text to vector

    The encoder is a transformer that outputs one vector per token. Pooling (usually the mean) collapses them into one vector. The model was trained with contrastive learning: matching question–passage pairs are pulled together and other passages in the batch are pushed apart, so distance comes to mean "relevance".

    Closeness is an angle

    \[ \cos(q,d) = \frac{q \cdot d}{\lVert q \rVert\,\lVert d \rVert} \qquad \lVert q-d \rVert^2 = 2 - 2\cos(q,d) \;\text{ for unit vectors} \] Normalize every vector to length 1 and cosine becomes a plain dot product. Euclidean distance then gives the same ranking.
    Drag the query through embedding space Try it

    Drag the query point (or use the slider). Moving it outward without turning changes nothing, because cosine ignores length. Real embeddings have hundreds of dimensions, but the geometry works the same way.

    In practice

    from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("all-MiniLM-L6-v2")      # 384-dim, small and fast
docs = ["Reset your password from the login page.",
        "Refunds take 5-7 business days.",
        "We ship to 40 countries."]
D = model.encode(docs, normalize_embeddings=True)   # shape (3, 384), done once at ingest
q = model.encode(["I forgot my login"], normalize_embeddings=True)[0]
scores = D @ q                                      # cosine, because vectors are unit length
for i in np.argsort(-scores)[:2]:
    print(f"{scores[i]:.3f}  {docs[i]}")

    Storage adds up fast: 1 million chunks × 1,536 dimensions × 4 bytes is about 6 GB of float32. Pick a model from a public benchmark such as MTEB, then confirm it on your own queries.

    Key ideas
    • Embeddings map meaning to direction; nearby vectors mean related text.
    • Use the same model, and the same query/passage prefixes if the model requires them, for queries and documents.
    • With unit vectors, cosine similarity, dot product and Euclidean distance all rank the same.
    • Chunk vectors are computed once; only the query is embedded per request.
    Common mistakes
    • Swapping the embedding model without re-embedding the whole corpus. Vectors from different models are not comparable.
    • Trusting semantic search for exact identifiers like error codes and SKUs. Pair it with keyword search (07.4).
    • Treating a cosine of 0.8 as a universal "relevant" threshold. Score ranges differ by model.

    07.2 · Units of retrieval

    Chunking

    One vector cannot summarize a 40-page manual, and the whole manual will not fit in a cheap prompt. So you split documents into chunks and embed, index and retrieve each one on its own. A good chunk is about one thing and still makes sense when read alone.

    Why it matters for AI engineers

    Chunking is the cheapest change with the largest effect on retrieval. Chunks that are too big blur several topics into one vector; chunks that are too small lose the context that makes them findable and useful.

    Size, overlap and stride

    \[ n_{\text{chunks}} = \left\lceil \frac{N - O}{S - O} \right\rceil \qquad \text{overhead} = \frac{O}{S-O} \] \(N\) document tokens, \(S\) chunk size, \(O\) overlap. A 10,000-token report with \(S=500, O=100\) gives 25 chunks and stores 25% extra text.
    Split a document Try it

    Colours mark chunks; an amber underline marks words stored twice because of overlap. Turn on snapping and watch the count of cut sentences drop to zero while chunk sizes become uneven.

    Strategies

    A sensible default is recursive splitting at 300 to 800 tokens with 10 to 20% overlap, then structure-aware rules for Markdown, HTML, code and tables. Store metadata with every chunk: source, page, heading path and date. A parent–child setup indexes small chunks for precise matching but returns the larger parent section to the model.

    from langchain_text_splitters import RecursiveCharacterTextSplitter

splitter = RecursiveCharacterTextSplitter(
    chunk_size=1200,          # characters, roughly 300 tokens of English
    chunk_overlap=150,
    separators=["\n\n", "\n", ". ", " ", ""],   # try paragraph, line, sentence, word
)
chunks = splitter.split_text(manual_text)
records = [{"id": f"manual-{i}", "text": c, "source": "manual.pdf"}
           for i, c in enumerate(chunks)]
    Key ideas
    • Chunk size trades precision (small) against context (large); test a few sizes on your eval set.
    • Overlap protects text near boundaries at the cost of extra storage and duplicate hits.
    • Split along the document's structure whenever it has one.
    • Metadata travels with each chunk so you can filter and cite.
    Common mistakes
    • Splitting tables and code blocks mid-way, which makes both halves useless.
    • Chunking beyond the embedding model's input limit, so the tail is silently truncated.
    • Mixing up characters and tokens when setting sizes.

    07.3 · Fast nearest neighbours

    Vector databases

    A vector database stores each chunk's embedding, text and metadata, and answers one question fast: which k vectors are closest to this one? Comparing the query with every vector is exact but slow: 10 million vectors × 768 dimensions is about 7.7 billion multiply-adds per query. Approximate nearest neighbour (ANN) indexes skip most of that work and give up a little recall in exchange.

    Why it matters for AI engineers

    Index type and parameters set your latency, memory bill and recall ceiling. Metadata filtering decides whether multi-tenant and permission-aware search actually works.

    HNSW: a graph you descend

    HNSW (Hierarchical Navigable Small World) links each vector to about M neighbours (often 16 to 32). A larger efSearch keeps more candidates during the descent, raising recall and latency together. HNSW gives high recall at low latency but keeps vectors and graph links in RAM.

    IVF: search only nearby cells

    IVF (inverted file) runs k-means to cut the space into nlist cells. A query scans only the nprobe cells whose centroids are closest. Pair it with product quantization (PQ), which compresses a 768-dim float32 vector from 3,072 bytes to, say, 96 bytes, and a billion vectors fit on one machine.

    IVF: probe more cells, find more true neighbours Try it

    Click anywhere to move the query. Near a cell boundary, nprobe = 1 misses true neighbours that sit just across the line. Raising nprobe buys recall with more scanning.

    import faiss, numpy as np

d = 384
xb = np.random.rand(100_000, d).astype("float32")
faiss.normalize_L2(xb)                               # unit vectors: inner product = cosine

hnsw = faiss.IndexHNSWFlat(d, 32, faiss.METRIC_INNER_PRODUCT)   # M = 32
hnsw.hnsw.efConstruction = 200
hnsw.add(xb)
hnsw.hnsw.efSearch = 64                              # raise for recall, lower for speed

quant = faiss.IndexFlatIP(d)
ivf = faiss.IndexIVFFlat(quant, d, 1024, faiss.METRIC_INNER_PRODUCT)   # nlist = 1024
ivf.train(xb); ivf.add(xb)
ivf.nprobe = 16

scores, ids = hnsw.search(xb[:1], 5)                # top-5 for one query
    Key ideas
    • ANN indexes trade a small, tunable recall loss for orders-of-magnitude speed.
    • HNSW: graph descent; tune M, efConstruction, efSearch. Memory-hungry.
    • IVF: cluster then probe; tune nlist and nprobe. Add PQ to compress.
    • Measure ANN recall against exact search on a sample before trusting settings.
    Common mistakes
    • Post-filtering a small top-k with a selective filter and getting empty results.
    • Forgetting deletes and updates: stale chunks keep being retrieved after a document changes.
    • Adding a dedicated vector DB when a few hundred thousand vectors fit in pgvector or in memory.

    07.4 · Recall first, precision second

    Hybrid search & reranking

    Vector search understands paraphrase but fumbles exact tokens such as error code E1043, part numbers and names. Keyword search nails exact tokens but misses paraphrase. Hybrid search runs both and fuses the two ranked lists. A reranker then reads the top few dozen candidates closely and puts the best ones first.

    Why it matters for AI engineers

    Hybrid retrieval plus reranking is the most reliable upgrade over plain vector search in production RAG. It costs one extra index and one small model call per query.

    BM25: keyword scoring

    \[ \text{BM25}(D,Q) = \sum_{t \in Q} \text{IDF}(t)\cdot \frac{f(t,D)\,(k_1+1)}{f(t,D) + k_1\left(1 - b + b\,\frac{|D|}{\text{avgdl}}\right)} \] \(f(t,D)\) is how often term \(t\) appears in document \(D\). Rare terms get a high IDF. \(k_1 \approx 1.2\) caps the reward for repeats; \(b \approx 0.75\) penalizes long documents.

    Reciprocal rank fusion

    BM25 scores run from 0 to about 30 and cosine from −1 to 1, so adding raw scores is meaningless. Reciprocal rank fusion (RRF) ignores scores and uses only positions. The constant \(k = 60\) from the original paper flattens the gap between rank 1 and rank 5.

    \[ \text{RRF}(d) = \sum_{\text{lists } \ell} \frac{w_\ell}{k + \text{rank}_\ell(d)} \] A document missing from a list contributes 0 from that list. Weights \(w_\ell\) default to 1.
    Reciprocal rank fusion calculator Try it

    Documents that appear in both lists (d3, d7) win even if neither list put them first. Drop k to 1 and the top rank of each list starts to dominate.

    Cross-encoder reranking

    import numpy as np
from rank_bm25 import BM25Okapi
from sentence_transformers import CrossEncoder

def rrf(rankings, k=60):
    scores = {}
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] = scores.get(doc_id, 0.0) + 1.0 / (k + rank)
    return sorted(scores, key=scores.get, reverse=True)

bm25 = BM25Okapi([d.lower().split() for d in docs])
bm25_rank = np.argsort(-bm25.get_scores(query.lower().split()))[:50].tolist()
vec_rank = vector_search(query, k=50)                 # ids from your vector index

candidates = rrf([bm25_rank, vec_rank])[:50]
reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
scores = reranker.predict([(query, docs[i]) for i in candidates])
top5 = [candidates[i] for i in np.argsort(-scores)[:5]]
    Key ideas
    • BM25 and vectors fail on different queries, so combining them raises recall.
    • RRF fuses by rank, so no score normalization is needed.
    • Retrieve wide (50 to 100) with cheap methods, then rerank narrow (5 to 10) with an expensive one.
    • Cross-encoders score a query–document pair jointly and cannot be precomputed.
    Common mistakes
    • Adding raw BM25 and cosine scores together.
    • Reranking only the top 5: the reranker cannot promote a document that was never a candidate.
    • Tokenizing differently at index and query time for BM25 (case, stemming, stop words).

    07.5 · Ask the index the right question

    Query rewriting

    Users type short, vague questions full of pronouns that point back at earlier chat turns. Documents are written in complete, formal sentences. Query rewriting uses a fast LLM call to turn the raw input into one or more queries that look like the text you want to find.

    Why it matters for AI engineers

    In chat products, follow-up questions like "what about for teams?" retrieve nothing useful unless you rewrite them. A rewrite step often fixes more failures than a better embedding model.

    The techniques

    The toy retriever counts shared keywords across an 8-document help centre. The raw question matches a project-sharing page about "adding people"; rewrites pull the real answer, d2, to the top.

    REWRITE_PROMPT = """Rewrite the user's last message as {n} different, self-contained
search queries for a help-centre search engine. Use the chat history to resolve
pronouns. Return one query per line.

History:
{history}

Last message: {question}"""

def multi_query_search(llm, search, history, question, n=3, k=50):
    text = llm(REWRITE_PROMPT.format(n=n, history=history, question=question))
    queries = [q.strip() for q in text.splitlines() if q.strip()][:n]
    rankings = [search(q, k=k) for q in queries]    # each returns a list of ids
    return rrf(rankings)                              # rrf() from 07.4
    Key ideas
    • Always rewrite follow-up questions into standalone ones in chat RAG.
    • Multiple query variants raise recall; fuse their results with RRF.
    • HyDE moves a short query into the region where answers live.
    • Each rewrite adds an LLM call; use a small, fast model and measure the gain.
    Common mistakes
    • Showing the rewritten query to the answer model instead of the user's real question.
    • Rewrites that drop exact identifiers such as error codes. Keep the original query as one of the variants.
    • Adding rewriting everywhere without measuring; it adds latency to every request.

    07.6 · Fixes for known failures

    Advanced RAG patterns

    Naive RAG (chunk, embed, take the top k, stuff the prompt) fails in predictable ways. Chunks lose the context that made them findable, broad questions need facts spread across hundreds of documents, and hard questions need several rounds of searching. Each advanced pattern targets one of these failures.

    Why it matters for AI engineers

    Knowing which failure you have tells you which pattern to add. Adding all of them at once makes a slow, expensive system that is hard to debug.

    Contextual retrieval

    A chunk such as "Revenue grew 3% over the previous quarter" does not say which company or quarter. Contextual retrieval asks an LLM, at ingest, to write one or two sentences placing each chunk in its document, and prepends them before embedding and BM25 indexing. Anthropic reported that this cut top-20 retrieval failures by roughly half, and by about two-thirds with reranking. Prompt caching keeps the cost down because the full document is the shared prefix for all of its chunks.

    Add context to chunks Try it
    off 

    CONTEXT_PROMPT = """<document>
{document}
</document>
Here is a chunk from that document:
<chunk>
{chunk}
</chunk>
Write one or two sentences that situate this chunk within the document
(company, period, section) to improve search retrieval. Answer with the context only."""

def contextualize(llm, document, chunks):
    # the document is identical for every chunk: cache it as the prompt prefix
    return [llm(CONTEXT_PROMPT.format(document=document, chunk=c)) + "\n" + c
            for c in chunks]

    GraphRAG and agentic RAG

    GraphRAG has an LLM extract entities and relationships from every chunk, clusters the graph into communities and summarizes each one. Global questions run map-reduce over the summaries; local questions start from an entity and walk its neighbours. Indexing costs LLM calls over the whole corpus, so reserve it for corpora that get broad, thematic questions.

    Agentic RAG gives the model search as a tool. It decides whether to retrieve, which source to query, reads results and searches again until it has enough evidence. Variants such as Self-RAG and Corrective RAG grade retrieved passages and retry when they are weak. Expect higher quality on multi-hop questions and two to five times the latency, so cap the number of steps.

    Key ideas
    • Diagnose first: missing context, global questions or multi-hop reasoning each need a different fix.
    • Contextual retrieval repairs chunks that are ambiguous out of context; it is cheap with prompt caching.
    • GraphRAG suits "what are the themes across everything?" questions.
    • Agentic RAG trades latency and tokens for multi-step search.
    • Long context windows complement RAG; they do not replace search over large, changing or permissioned corpora.
    Common mistakes
    • Reaching for GraphRAG or agents before hybrid search and reranking are tuned.
    • Letting an agentic loop run without a step or token budget.
    • Regenerating chunk contexts on every ingest instead of only for changed documents.

    07.7 · Measure both halves

    Evaluating RAG

    A RAG answer can be wrong for two separate reasons: retrieval missed the right passage, or the model misused the passage it got. So you measure retrieval and generation separately. Retrieval metrics ask whether the right chunks came back near the top; generation metrics ask whether the answer is supported by those chunks and actually answers the question.

    Why it matters for AI engineers

    Every chunk size, model swap and reranker in this area is a guess until you have an eval set. Separate metrics tell you which component to fix, and a fixed eval set catches regressions before users do.

    Retrieval metrics

    \[ \text{recall@}k = \frac{|\text{relevant} \cap \text{top-}k|}{|\text{relevant}|} \qquad \text{MRR} = \frac{1}{|Q|}\sum_{q} \frac{1}{\text{rank of first relevant}} \] \[ \text{nDCG@}k = \frac{\text{DCG@}k}{\text{IDCG@}k}, \qquad \text{DCG@}k = \sum_{i=1}^{k} \frac{\text{rel}_i}{\log_2(i+1)} \] Recall ignores order inside the top k. MRR only cares about the first hit. nDCG rewards putting the most relevant results highest and uses graded relevance; IDCG is the DCG of the ideal ordering.
    Retrieval metrics calculator Try it

    Click a result to cycle its relevance grade from 0 to 3 (or focus it and press Enter). Move a relevant result from rank 6 to rank 1 and watch nDCG and RR jump while recall@10 stays the same.

    Generation metrics and the eval set

    Faithfulness (or groundedness) is the share of claims in the answer that the retrieved context supports. A judge LLM splits the answer into claims and checks each one against the context. Calibrate any judge against 50 or so human labels before trusting it.

    Build the eval set from 50 to 200 real user questions, each labelled with the chunk ids that answer it. Synthetic questions generated from chunks fill gaps. Slice results by question type and run the suite in CI on every change.

    import math

def recall_at_k(ranked, relevant, k):
    return len(set(ranked[:k]) & relevant) / len(relevant)

def reciprocal_rank(ranked, relevant):
    for i, doc in enumerate(ranked, start=1):
        if doc in relevant:
            return 1.0 / i
    return 0.0

def ndcg_at_k(ranked, grades, k):              # grades: {doc_id: 0..3}
    dcg = sum(grades.get(d, 0) / math.log2(i + 1) for i, d in enumerate(ranked[:k], 1))
    ideal = sorted(grades.values(), reverse=True)[:k]
    idcg = sum(g / math.log2(i + 1) for i, g in enumerate(ideal, 1))
    return dcg / idcg if idcg else 0.0

# MRR over a test set
mrr = sum(reciprocal_rank(r, rel) for r, rel in runs) / len(runs)
    Key ideas
    • Evaluate retrieval and generation separately so failures point at one component.
    • recall@k tells you if the answer is reachable; MRR and nDCG tell you how high it ranks.
    • Faithfulness catches answers that sound right but are not supported by the context.
    • A small labelled eval set run on every change beats a large one run once.
    Common mistakes
    • Judging the whole system only by end-to-end answer quality, which hides whether retrieval or generation broke.
    • Trusting an LLM judge that was never checked against human labels.
    • Building the eval set only from synthetic questions that copy the chunk's wording, which flatters retrieval.
