Inference & optimization

Training a model happens once. Inference happens on every request, so it is where most of the money, latency and hardware planning goes. This area teaches you why generating tokens is slow, which tricks make it fast and cheap, and how to estimate memory and speed before you rent a single GPU.

In this area

    Every LLM request has two phases. Prefill reads the whole prompt in one parallel pass and fills the KV cache. Decode then produces one token per step, and each step has to stream the model weights and the cache out of GPU memory. Almost every optimization in this area attacks one of those costs: quantization shrinks the bytes per weight, the KV cache and PagedAttention manage the memory that grows with context, batching shares each weight read across many users, and speculative decoding produces several tokens per expensive step. Serving engines package all of this, GPU memory math tells you what fits, and running models locally applies the same ideas to a laptop.

    11.1 · Fewer bits per weight

    Quantization

    Quantization stores each weight in 8 or 4 bits instead of 16 by snapping it to the nearest point on a small grid. Weights get slightly less precise; the model gets two to four times smaller and faster to decode.

    Why it matters for AI engineers

    Quantization decides what fits where: a 70B model needs about 140 GB in 16-bit (two 80 GB GPUs) and 35–40 GB in 4-bit (one). You will choose between variants named FP8, AWQ, GPTQ and Q4_K_M.

    How a number gets fewer bits

    In symmetric quantization you take a block of weights, set the scale to the largest absolute value divided by the largest storable integer (7 for signed 4-bit), and store round(w / scale). To use a weight you dequantize: integer × scale. The gap between the two is the rounding error, at most half a grid step.

    \[ s = \frac{\max_i |w_i|}{2^{b-1}-1}, \qquad q_i = \operatorname{clamp}\!\left(\operatorname{round}\!\left(\frac{w_i}{s}\right),\, -2^{b-1},\, 2^{b-1}-1\right), \qquad \hat{w}_i = s\, q_i \] \(b\) is the bit width, \(s\) the scale shared by the block, \(q_i\) the stored integer and \(\hat{w}_i\) the value the kernel actually multiplies with. Each extra bit halves the grid step and roughly quarters the mean squared error.

    Outliers, groups and the named methods

    One large weight stretches the scale and squashes its neighbours onto a few levels. The fix is one scale per group of 32–128 weights (about 4.13 bits per weight at 4-bit). The named post-training quantization methods add smarter rounding:

    GPTQ

    Column by column, nudging the remaining weights to cancel the error. INT4 for GPUs.

    AWQ

    Protects the ~1% of channels hit by large activations by scaling them up before rounding.

    GGUF k-quants

    llama.cpp's file format: Q4_K_M, Q8_0; the digit is roughly bits per weight.

    FP8 / FP4

    Hardware float formats (Hopper, Blackwell) that also speed up the math.

    Snap weights to a grid Try it

    With outliers and one scale per tensor, 4-bit weights collapse onto a few levels; per-group scales confine the damage.

    What you gain, what you risk

    Kernels dequantize 4-bit weights in registers: the math is unchanged, bytes read per token drop 4×, and decoding speeds up two to three times.

    # Group-wise symmetric quantization, the core of most 4-bit formats
import numpy as np

def quantize(w, bits=4, group=64):
    qmax = 2 ** (bits - 1) - 1
    g = w.reshape(-1, group)                         # one scale per group
    scale = np.abs(g).max(axis=1, keepdims=True) / qmax
    scale[scale == 0] = 1.0
    q = np.clip(np.round(g / scale), -qmax - 1, qmax).astype(np.int8)
    return q, scale.astype(np.float16)

def dequantize(q, scale):
    return (q * scale.astype(np.float32)).reshape(-1)

w = np.random.randn(4096 * 64).astype(np.float32) * 0.02
for b in (8, 4, 3):
    q, s = quantize(w, bits=b)
    err = np.mean((w - dequantize(q, s)) ** 2)
    sqnr = 10 * np.log10(np.mean(w ** 2) / err)
    print(f"{b}-bit: SQNR {sqnr:.1f} dB")         # roughly 6 dB per bit

    Bigger models tolerate quantization better, so a 4-bit 70B usually beats a 16-bit 8B. Math, code, long context and non-English text show damage first: evaluate on your own tasks.

    Key ideas
    • Quantization stores an integer per weight plus a shared scale per block; dequantize = integer × scale.
    • Weight-only 4-bit speeds up decoding because decoding is limited by bytes read, not by arithmetic.
    • Outliers stretch the scale; group-wise scales and methods like GPTQ and AWQ keep error low.
    • 8-bit is near-lossless, 4-bit is the usual sweet spot, below 4 bits quality drops fast.
    • A larger model at 4-bit often beats a smaller model at 16-bit in the same memory.
    Common mistakes
    • Comparing quantized variants only on perplexity and shipping one that fails on your actual task (code, JSON, long context).
    • Expecting weight-only INT4 to speed up a heavily batched, compute-bound server as much as it speeds up a single user.
    • Using a quantized checkpoint with an engine or GPU that has no fast kernel for it, so it falls back to slow dequantization.
    • Calibrating GPTQ or AWQ on data unlike your traffic (for example English prose for a code model).

    11.2 · Memory that grows with context

    KV cache

    To generate token 500, attention needs keys and values for all 499 earlier tokens. The model stores them once in the KV cache and appends one row per step, trading recomputation for GPU memory that grows with context and users.

    Why it matters for AI engineers

    The KV cache, more than the weights, decides how many users a GPU serves and how long their contexts can be.

    Prefill and decode

    Prefill runs the whole prompt through the model in one pass. Each loaded weight is used for every prompt token, so prefill is compute-bound; it fills the cache and sets the time to first token (TTFT).

    Decode then makes one token per step: compute q, k, v for the newest token, append k and v, attend over the cache. Each weight byte read is used for only about two FLOPs, so decode is memory-bandwidth-bound. One step is the time per output token (TPOT).

    How big is the cache?

    Every token stores, in every layer, one key and one value vector per key-value head:

    \[ \text{KV bytes} = 2 \times L \times n_{kv} \times d_{head} \times T \times B \times \text{bytes per element} \] The 2 is for keys and values. \(L\) = layers, \(n_{kv}\) = key-value heads, \(d_{head}\) = head dimension, \(T\) = tokens in context (prompt plus generated), \(B\) = concurrent sequences, and bytes per element is 2 for FP16/BF16 or 1 for an FP8 cache.

    Llama 3.1 8B (32 layers, 8 KV heads, head dim 128, BF16): 2 × 32 × 8 × 128 × 2 = 128 KiB per token. One 8k conversation is 1 GiB; thirty-two of them are 32 GiB, twice the 16 GB of weights.

    Grouped-query attention (GQA) lets several query heads share one key-value head, shrinking the cache by the group factor. DeepSeek's MLA caches a compressed latent instead.

    PagedAttention, prefix caching and other cache tricks

    Early servers reserved a max-length slab per request and wasted 60–80% of KV memory. PagedAttention (diagram above, right) allocates 16-token blocks on demand through a block table; waste falls under 4%.

    Requests sharing a system prompt can point at the same blocks and skip that prefill: prefix caching (SGLang: RadixAttention). An FP8 cache (--kv-cache-dtype fp8 in vLLM) halves memory again.

    # Read a model's architecture and compute KV-cache size per token
from transformers import AutoConfig

cfg = AutoConfig.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
layers = cfg.num_hidden_layers
kv_heads = getattr(cfg, "num_key_value_heads", cfg.num_attention_heads)
head_dim = getattr(cfg, "head_dim", None) or cfg.hidden_size // cfg.num_attention_heads

def kv_bytes(tokens, batch=1, bytes_per_elem=2):
    return 2 * layers * kv_heads * head_dim * tokens * batch * bytes_per_elem

per_token = kv_bytes(1)
print(f"{per_token / 1024:.0f} KiB per token")                  # 56 KiB
print(f"{kv_bytes(32_768, batch=8) / 2**30:.1f} GiB for 8 x 32k")  # 14.0 GiB
    Key ideas
    • Prefill is compute-bound and sets TTFT; decode is memory-bound and sets time per output token.
    • KV bytes = 2 × layers × KV heads × head dim × tokens × batch × bytes per element.
    • GQA and MQA shrink the cache by sharing key-value heads across query heads.
    • PagedAttention allocates the cache in small blocks, nearly eliminating waste and enabling prefix sharing.
    • Shared prefixes (system prompts, tool definitions) can skip prefill entirely with prefix caching.
    Common mistakes
    • Using the number of attention heads instead of key-value heads in the formula, overestimating GQA models by 4–8×.
    • Budgeting only for the weights and discovering at load time that a long max context leaves room for two concurrent users.
    • Putting per-user data (a timestamp, the user's name) at the start of the prompt, which breaks prefix-cache hits for everyone.
    • Setting the maximum context to the model's limit "just in case" when real traffic never exceeds 8k tokens.

    11.3 · Share every weight read

    Batching & throughput

    Each decode step reads every weight from memory. With sixty-four users waiting, that one read can produce sixty-four tokens for almost the same cost, which is why self-hosting only gets cheap when the GPU is busy.

    Why it matters for AI engineers

    Cost per token is GPU-hour price divided by tokens per hour, which depends mostly on batch size. Bigger batches cost less but make each user wait longer per token.

    Why decode wastes the GPU at batch size 1

    Arithmetic intensity is FLOPs done per byte read. Batch-1 decode does 2 FLOPs per 2-byte weight: about 1 FLOP/byte. An H100 needs about 295 to keep its tensor cores busy. The roofline chart shows the consequence: below that ridge, speed is capped by memory bandwidth.

    \[ \text{intensity}_{\text{decode}} \approx \frac{2 \cdot P \cdot B}{P \cdot b_w} = \frac{2B}{b_w}\ \text{FLOP/byte}, \qquad t_{\text{step}} \approx \max\!\left(\frac{P\,b_w + B\,\text{KV}_{seq}}{\text{BW}},\ \frac{2PB}{\text{FLOPS}}\right) \] \(P\) parameters, \(b_w\) bytes per weight, \(B\) sequences in the batch, \(\text{KV}_{seq}\) cache bytes per sequence. Batching multiplies the work done per weight byte by \(B\). The KV term does not amortize, because each sequence reads its own cache.

    At small batches the weight term dominates, so adding sequences is nearly free. Then each sequence's own KV reads, and eventually compute, take over: throughput flattens and per-token latency climbs.

    The demo assumes 80% of peak bandwidth and 50% of peak compute. KV reads, not compute, end the free lunch.

    Static vs continuous batching

    Static batching runs a fixed group until its longest member finishes, so slots sit idle. Continuous batching (in-flight or iteration-level batching, from the Orca system) reschedules after every decode step: finished sequences leave and waiting ones join immediately.

    The metrics you report

    A long prompt joining the batch stalls everyone's next token, so engines use chunked prefill to interleave it with decode steps. Large deployments sometimes split prefill and decode onto separate GPU pools (disaggregated serving).

    Report p50/p95/p99 at a stated concurrency and prompt/output mix. A throughput number without its latency tells you little.

    # Measure TTFT, TPOT and throughput against any OpenAI-compatible server (vLLM, SGLang, llama-server...)
import asyncio, time
from openai import AsyncOpenAI

client = AsyncOpenAI(base_url="http://localhost:8000/v1", api_key="unused")
MODEL = "meta-llama/Llama-3.1-8B-Instruct"

async def one_request(prompt):
    t0 = time.perf_counter(); first = None; chunks = 0
    stream = await client.chat.completions.create(
        model=MODEL, messages=[{"role": "user", "content": prompt}],
        max_tokens=256, stream=True)
    async for chunk in stream:
        if chunk.choices and chunk.choices[0].delta.content:
            first = first or time.perf_counter()
            chunks += 1                       # roughly one chunk per token
    end = time.perf_counter()
    return first - t0, (end - first) / max(chunks - 1, 1), chunks

async def sweep():
    for concurrency in (1, 8, 32, 128):
        t0 = time.perf_counter()
        res = await asyncio.gather(*[one_request("Explain KV caching.") for _ in range(concurrency)])
        wall = time.perf_counter() - t0
        ttft = sorted(r[0] for r in res)
        tpot = sum(r[1] for r in res) / len(res)
        print(f"c={concurrency:3d}  p50 TTFT {ttft[len(ttft) // 2] * 1e3:6.0f} ms  "
              f"TPOT {tpot * 1e3:5.1f} ms  throughput {sum(r[2] for r in res) / wall:6.0f} tok/s")

asyncio.run(sweep())
    Key ideas
    • Decode at batch 1 has an arithmetic intensity near 1 FLOP/byte; GPUs need hundreds to be compute-bound.
    • Batching reuses each weight read across many sequences, so throughput rises almost for free at first.
    • Per-sequence KV reads do not amortize, so throughput flattens and per-token latency rises at large batches.
    • Continuous batching schedules per decode step; chunked prefill keeps long prompts from stalling everyone.
    • Report TTFT, TPOT and throughput together, as percentiles, at a stated concurrency.
    Common mistakes
    • Benchmarking a server with one request at a time and concluding self-hosting is too expensive.
    • Quoting peak throughput measured at a concurrency where p95 latency is unacceptable.
    • Testing with short prompts and short outputs when production traffic has 10k-token RAG contexts.
    • Running a hand-written model.generate() loop in production instead of an engine with continuous batching.

    11.4 · Several tokens per big step

    Speculative decoding

    A batch-1 decode step barely uses the GPU's compute, so checking five tokens costs about the same as producing one. Speculative decoding exploits that: a cheap guesser drafts a few tokens, the big model verifies them all in one pass, and every correct guess is a token you got for free. With the right acceptance rule the output distribution is exactly the big model's.

    Why it matters for AI engineers

    It is one of the few latency optimizations with no quality cost, typically 2–3× faster single-stream decoding. Serving engines ship it as a configuration option, and it is especially strong for code editing and RAG, where outputs copy text from the prompt.

    Draft, verify, accept

    Each draft token \(x\) is accepted with probability \(\min(1, p(x)/q(x))\), where \(p\) is the target's probability and \(q\) the draft's. On rejection, the replacement is sampled from the leftover distribution \(\max(0, p-q)\), normalized. This rejection-sampling rule makes the output exactly as if the target had sampled alone. With greedy decoding it reduces to "accept while the tokens match".

    How much faster?

    \[ \mathbb{E}[\text{tokens per round}] = \frac{1-\alpha^{\gamma+1}}{1-\alpha}, \qquad \text{speed-up} = \frac{1-\alpha^{\gamma+1}}{(1-\alpha)(\gamma c + 1)} \] \(\alpha\) = probability each draft token is accepted, \(\gamma\) = tokens drafted per round, \(c\) = cost of one draft step relative to one target step (Leviathan et al.). Assumes acceptances are independent.

    Where the draft comes from

    Small draft model

    A smaller model from the same family with the same tokenizer (e.g. 0.5B drafting for 7B). Simple; costs extra memory.

    Medusa / EAGLE heads

    Extra lightweight heads trained on the target's hidden states predict several tokens ahead. Higher acceptance, needs trained heads.

    N-gram / prompt lookup

    Copy the continuation of a matching n-gram from the prompt. Free, and excellent for code edits and RAG answers that quote sources.

    Multi-token prediction

    Models trained with MTP heads (e.g. DeepSeek-V3) can use them as a built-in drafter.

    Speed-ups shrink at high batch sizes: the GPU is no longer idle, so verifying rejected tokens costs real compute. Engines often disable speculation under heavy load.

    # Assisted generation in Hugging Face transformers
import torch
from transformers import AutoModelForCausalLM, AutoTokenizer

tok = AutoTokenizer.from_pretrained("Qwen/Qwen2.5-7B-Instruct")
target = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-7B-Instruct", torch_dtype=torch.bfloat16, device_map="auto")
draft = AutoModelForCausalLM.from_pretrained("Qwen/Qwen2.5-0.5B-Instruct", torch_dtype=torch.bfloat16, device_map="auto")

inputs = tok("Explain the KV cache in two sentences.", return_tensors="pt").to(target.device)
out = target.generate(**inputs, assistant_model=draft, max_new_tokens=120)    # draft-model speculation
out = target.generate(**inputs, prompt_lookup_num_tokens=10, max_new_tokens=120)  # n-gram lookup, no draft model
print(tok.decode(out[0], skip_special_tokens=True))
    Key ideas
    • Verifying several tokens costs about the same as generating one when decode is memory-bound.
    • The min(1, p/q) acceptance rule keeps the output distribution identical to the target model's.
    • Expected tokens per round = (1 − α^(γ+1)) / (1 − α); acceptance rate matters more than draft length.
    • Gains are largest at low batch sizes and for outputs that copy from the input.
    Common mistakes
    • Pairing a draft and target with different tokenizers, or a draft from an unrelated family with low acceptance.
    • Setting γ large "for more speed" when acceptance is mediocre, which wastes draft and verify compute.
    • Benchmarking speculation at batch 1 and enabling it on a saturated, high-throughput server.

    11.5 · The software that runs it all

    Serving engines

    A serving engine is the program between your HTTP request and the GPU. It accepts requests, decides every few milliseconds which sequences run together, manages KV-cache blocks, and calls optimized kernels. Everything earlier on this page, from paged caches to continuous batching to speculation, reaches you as engine features and flags.

    Why it matters for AI engineers

    Picking an engine, and configuring its context length, memory share and parallelism, is often the first infrastructure decision when you self-host. The same model on the same GPU can differ several-fold in throughput between a naive loop and a tuned engine.

    Inside an engine

    Engines expose an OpenAI-compatible HTTP API, so client code does not change when you swap engines or move between a hosted API and your own server. The key knobs are the maximum context length (which caps KV per sequence), the fraction of GPU memory the engine may claim, and tensor parallelism across GPUs.

    # vLLM: serve a model with an OpenAI-compatible API on port 8000
pip install vllm
vllm serve Qwen/Qwen2.5-7B-Instruct --max-model-len 16384 --gpu-memory-utilization 0.90

# SGLang: same idea, port 30000
python -m sglang.launch_server --model-path Qwen/Qwen2.5-7B-Instruct --port 30000

# llama.cpp: a GGUF file, all layers on the GPU, 8k context
llama-server -m qwen2.5-7b-instruct-q4_k_m.gguf -c 8192 -ngl 99 --port 8080

    11.6 · Back-of-envelope sizing

    GPU memory math

    Before you rent hardware, two pieces of arithmetic tell you almost everything: whether the model fits, and how fast it can possibly decode. Memory is weights plus KV cache plus overhead. Speed is capped by how many times per second the GPU can read the weights.

    Why it matters for AI engineers

    "Can we run this model on that GPU, for how many users, at what speed?" comes up in every self-hosting discussion. Five minutes of arithmetic saves days of trial-and-error with out-of-memory errors.

    What fills the GPU

    \[ M_{\text{GPU}} \approx \underbrace{P \cdot b_w}_{\text{weights}} + \underbrace{2 L\, n_{kv} d_{head}\, T B\, b_{kv}}_{\text{KV cache}} + \underbrace{\sim 1\text{–}3\ \text{GB}}_{\text{runtime, activations}} \] Weights: 7–8B in BF16 ≈ 14–16 GB; 70B ≈ 140 GB in BF16, ≈ 70 GB in FP8, ≈ 35–42 GB in 4-bit. Training is far heavier: about 16 bytes per parameter with Adam in mixed precision, before activations.

    Engines claim most of the GPU up front: vLLM takes 90% by default (--gpu-memory-utilization), loads the weights, and turns the remainder into KV blocks. If the remainder cannot hold even one maximum-length sequence, startup fails. For models larger than one GPU, tensor parallelism splits every weight matrix (and the KV cache) across GPUs, so 70B in BF16 runs on 2×80 GB.

    Will it fit on my GPU? Try it

    The speed ceiling

    Each decode step reads every weight once, so a single stream can never exceed memory bandwidth ÷ weight bytes tokens per second. Real systems reach roughly 60–80% of this. It also explains why quantization speeds up decoding and why Apple Silicon, with high-bandwidth unified memory, runs local models well.

    \[ \text{tokens/s}_{\text{max, one stream}} \approx \frac{\text{memory bandwidth}}{P \cdot b_w} \qquad \text{e.g. } \frac{3.35\ \text{TB/s}}{16\ \text{GB}} \approx 209 \] 
    def fits(params_b, bytes_w, layers, kv_heads, head_dim, ctx, batch,
         vram_gb, n_gpus=1, kv_bytes=2, overhead_gb=2.0, util=0.90):
    weights = params_b * 1e9 * bytes_w
    kv = 2 * layers * kv_heads * head_dim * ctx * batch * kv_bytes
    need = weights + kv + overhead_gb * 1e9 * n_gpus
    have = vram_gb * 1e9 * n_gpus * util
    return need / 1e9, have / 1e9, need <= have

# Llama 3.1 70B, FP8 weights, 8 users x 8k context, on 1 vs 2 H100s
print(fits(70.6, 1, 80, 8, 128, 8192, 8, vram_gb=80))           # (~94.1, 72.0, False)
print(fits(70.6, 1, 80, 8, 128, 8192, 8, vram_gb=80, n_gpus=2)) # (~96.1, 144.0, True)
    Key ideas
    • Weights = parameters × bytes per weight; 1B parameters ≈ 2 GB in BF16, 1 GB in FP8, ~0.5 GB in 4-bit.
    • What remains after weights and overhead is the KV pool that users and context lengths share.
    • Single-stream decode speed ≤ memory bandwidth ÷ weight bytes.
    • Tensor parallelism splits weights and KV across GPUs when one is not enough.
    Common mistakes
    • Sizing for weights only and forgetting the KV cache and runtime overhead.
    • Mixing GB (10⁹) and GiB (2³⁰); the 7% gap matters when you are close to the limit.
    • Estimating speed from TFLOPS instead of memory bandwidth for single-user decoding.
    • Using training memory rules (16 bytes/param) for inference, or inference rules for fine-tuning.

    11.7 · Your own machine

    Running models locally

    A quantized 8B model is about 5 GB, which fits on a gaming GPU, a recent Mac or even plain RAM. Running models locally means no API bill, no data leaving the machine and no rate limits, in exchange for smaller models and your own hardware's speed. The same rules apply as in the datacenter: quantization decides what fits, bandwidth decides speed.

    Why it matters for AI engineers

    Local models are handy for offline development, private data, cheap bulk jobs and testing against an OpenAI-compatible endpoint without spending money. They are also how you build intuition for everything on this page, on hardware you can poke.

    Pick a file size

    Local runtimes use GGUF files named by quantization. Q4_K_M is the common default; Q5_K_M or Q6_K buy a little quality if memory allows. Leave 1–2 GB plus the KV cache free on top of the file size.

    When it doesn't fit: partial offload

    llama.cpp can put some layers on the GPU and run the rest from system RAM (-ngl sets the GPU layer count). Every token still passes through every layer, so the slow RAM part dominates. Apple Silicon avoids the split: the GPU reads unified memory directly at 270–550 GB/s on Pro and Max chips.

    Tools

    Ollama

    ollama run pulls and runs a model; serves REST and OpenAI-compatible APIs on port 11434. Raise num_ctx for long prompts.

    llama.cpp

    The engine underneath much of the ecosystem: CLI, llama-server, quantization tools, full control of offload and context.

    LM Studio / MLX

    LM Studio is a desktop app with a local server. MLX is Apple's array framework; mlx-lm runs models natively on Apple Silicon.

    # Terminal:  ollama pull llama3.1:8b   (a ~4.9 GB Q4_K_M download)
from openai import OpenAI

client = OpenAI(base_url="http://localhost:11434/v1", api_key="ollama")  # key is required but ignored
resp = client.chat.completions.create(
    model="llama3.1:8b",
    messages=[{"role": "user", "content": "Explain PagedAttention in one sentence."}],
)
print(resp.choices[0].message.content)
    Key ideas
    • Q4_K_M GGUF puts an 8B model in about 5 GB; Q5/Q6 trade memory for a little quality.
    • Local speed is bandwidth-bound: VRAM and Apple unified memory are fast, system RAM is slow.
    • Partial offload runs bigger models, but the RAM-resident layers dominate token time.
    • Ollama, llama-server and LM Studio expose OpenAI-compatible endpoints, so app code stays the same.
    Common mistakes
    • Leaving the default context window small and wondering why long documents get truncated.
    • Judging a model family by a Q2 or Q3 build of its smallest size.
    • Downloading a model file that barely fits, leaving no room for the KV cache or the rest of the system.
