Transformers & LLMs

A large language model turns text into tokens, tokens into vectors, mixes those vectors with attention, and predicts the next token, over and over. This area takes that loop apart piece by piece, then follows the training recipe and the model choices you make on the job.

    05.1 · Text to integers

    Tokenization

    A model cannot read characters. A tokenizer chops text into pieces from a fixed vocabulary (typically 32k to 256k entries) and maps each piece to an integer id. Common words become one token; rare words are built from several smaller pieces.

    Why it matters for AI engineers

    You pay per token, context limits are counted in tokens, and many odd model failures (miscounting letters, shaky arithmetic, weaker non-English output) trace back to how text was split. A useful rule of thumb for English: about 4 characters or 0.75 words per token.

    The pipeline

    Text is first normalized and pre-split, usually on spaces and punctuation, with the leading space kept as part of the next word. Then learned merge rules glue bytes into larger pieces, and each final piece is looked up in the vocabulary.

    How BPE learns its vocabulary

    Byte-pair encoding (BPE) starts with single bytes, so any string can be encoded and nothing is ever "unknown". It counts every adjacent pair across the corpus, merges the most frequent pair into a new token, and repeats until the vocabulary hits its target size. Step through it below on a tiny corpus.

    BPE merge stepper Try it

    Encoding new text replays the learned merges in the same order. WordPiece (BERT) and Unigram (SentencePiece) choose merges by likelihood instead of raw counts, but the output looks the same: subword pieces with ids.

    # Minimal BPE training loop (whitespace-split words, counts per word)
from collections import Counter

def train_bpe(text, num_merges):
    words = Counter(text.split())
    splits = {w: list(w) for w in words}          # start from characters
    merges = []
    for _ in range(num_merges):
        pairs = Counter()
        for w, n in words.items():
            s = splits[w]
            for a, b in zip(s, s[1:]):
                pairs[(a, b)] += n
        if not pairs:
            break
        best = max(pairs, key=pairs.get)          # most frequent pair
        merges.append(best)
        for w in words:                           # apply the merge everywhere
            s, out, i = splits[w], [], 0
            while i < len(s):
                if i + 1 < len(s) and (s[i], s[i + 1]) == best:
                    out.append(s[i] + s[i + 1]); i += 2
                else:
                    out.append(s[i]); i += 1
            splits[w] = out
    return merges, splits

import tiktoken
enc = tiktoken.get_encoding("cl100k_base")
print(len(enc.encode("Tokenization isn't trivial.")))

    Where tokenization bites

    Key ideas
    • Tokens are subword pieces from a fixed vocabulary; ids are just row numbers.
    • Byte-level BPE can encode any string because it falls back to single bytes.
    • Merges are learned from corpus frequency and replayed in order at encode time.
    • A tokenizer is tied to its model: never mix one model's tokenizer with another's weights.
    Common mistakes
    • Estimating cost or context use with word counts instead of a real tokenizer.
    • Stripping or adding whitespace casually; "␣word" and "word" are different tokens.
    • Assuming every language or code style costs the same tokens per character.

    05.2 · Ids to vectors

    Embeddings & positional encoding

    Each token id selects one row of a big learned table, the embedding matrix, giving a vector of a few thousand numbers. Training pushes tokens used in similar ways toward similar vectors. Because attention by itself ignores order, the model also needs a signal that says where each token sits.

    Why it matters for AI engineers

    The embedding table is a large chunk of a small model's parameters, and the position scheme decides how well a model handles long contexts. When a provider "extends context" to millions of tokens, they are usually adjusting the positional encoding (RoPE scaling) and training further on long documents.

    Lookup, then add position

    The table has shape vocabulary × width. With a 128k vocabulary and width 4,096 that is 524M parameters, about 1 GB in fp16. Looking up a row is the same as multiplying a one-hot vector by the matrix, so it trains with ordinary gradients.

    Three ways to encode position

    The original transformer added fixed sine and cosine waves of different frequencies. GPT-2 learned one vector per position instead, which cannot extend past the trained length. Most current open LLMs use rotary position embeddings (RoPE): they rotate pairs of query and key dimensions by an angle proportional to position, so the attention score depends on the distance between tokens.

    \[ PE_{(pos,\,2i)} = \sin\!\left(\frac{pos}{10000^{2i/d}}\right), \qquad PE_{(pos,\,2i+1)} = \cos\!\left(\frac{pos}{10000^{2i/d}}\right) \] Low dimension pairs (small \(i\)) oscillate fast; high pairs oscillate slowly. Together they give every position a unique pattern, like the hands of a clock.
    Sinusoidal positional encoding Try it 

    import math, torch, torch.nn as nn

vocab, d = 50_000, 512
embed = nn.Embedding(vocab, d)                 # a learnable V x d table
ids = torch.tensor([[1820, 3428, 395]])        # batch of 1, 3 tokens
x = embed(ids)                                 # shape (1, 3, 512)

def sinusoidal(n_pos, d):
    pos = torch.arange(n_pos).unsqueeze(1)                     # (n_pos, 1)
    freq = torch.exp(-math.log(10000.0) * torch.arange(0, d, 2) / d)
    pe = torch.zeros(n_pos, d)
    pe[:, 0::2] = torch.sin(pos * freq)
    pe[:, 1::2] = torch.cos(pos * freq)
    return pe

x = x + sinusoidal(3, d)                       # broadcast over the batch
    Key ideas
    • An embedding is a row lookup in a learned V × d matrix.
    • Attention is order-blind, so position must be injected explicitly.
    • RoPE encodes relative position by rotating Q and K; it is the default in most current open models.
    • Many models tie the input embedding and the output projection to save parameters.
    Common mistakes
    • Confusing token embeddings (inside the LLM) with sentence embeddings from an embedding model (used for search in RAG).
    • Assuming a model works well at any length up to its advertised limit; quality often drops well before it.
    • Forgetting that a learned absolute position table cannot go beyond its trained length.

    05.3 · The core mechanism

    Self-attention

    Self-attention lets every token look at the other tokens and pull in what it needs. In "the animal didn't cross the street because it was tired", the vector for "it" should absorb information from "animal". Attention computes, for each token, a weighted average of the other tokens' information, where the weights come from learned similarity.

    Why it matters for AI engineers

    Attention explains why cost and memory grow with context length (the score matrix is n × n), why long prompts slow down the first token, why a KV cache exists, and why "lost in the middle" effects happen. Inference tricks such as FlashAttention, grouped-query attention and prefix caching all target this one operation.

    Queries, keys and values

    Each token vector is projected three ways. The query says what this token is looking for, the key says what it offers, and the value is the content it hands over. A query-key dot product scores relevance; softmax turns a row of scores into weights; the weights mix the values.

    \[ \text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{QK^{\top}}{\sqrt{d_k}} + M\right)V, \qquad M_{ij} = \begin{cases} 0 & j \le i \\ -\infty & j > i \end{cases} \] \(Q = XW_Q\), \(K = XW_K\), \(V = XW_V\). Dividing by \(\sqrt{d_k}\) keeps dot products from growing with dimension and saturating the softmax. The causal mask \(M\) stops token \(i\) from seeing future tokens, so \(e^{-\infty} = 0\) weight.

    A worked example, by hand

    Take three tokens with \(d_k = 2\), so \(\sqrt{d_k} \approx 1.414\). Suppose the projections produced \(Q = [[1,0],[0,1],[1,1]]\), \(K = [[1,0],[1,1],[0,1]]\) and \(V = [[1,0],[0,2],[3,1]]\). Follow the grids from left to right.

    Many heads, quadratic cost

    Multi-head attention runs h heads in parallel, each with \(d_k = d/h\) (for example 32 heads of 128 dims when d = 4,096), then concatenates their outputs and applies \(W_O\). Different heads specialize in different relations. The score matrix is n × n per head, so doubling the context quadruples attention compute. Grouped-query attention shares K and V across groups of query heads to shrink the KV cache.

    import numpy as np

def causal_attention(Q, K, V):
    n, d_k = Q.shape
    scores = Q @ K.T / np.sqrt(d_k)                     # (n, n)
    mask = np.triu(np.ones((n, n), dtype=bool), k=1)    # True above the diagonal
    scores = np.where(mask, -np.inf, scores)
    scores -= scores.max(axis=1, keepdims=True)         # numerical stability
    w = np.exp(scores)
    w /= w.sum(axis=1, keepdims=True)
    return w @ V, w

Q = np.array([[1, 0], [0, 1], [1, 1]], float)
K = np.array([[1, 0], [1, 1], [0, 1]], float)
V = np.array([[1, 0], [0, 2], [3, 1]], float)
out, w = causal_attention(Q, K, V)
print(w.round(2))    # [[1. 0. 0.] [0.33 0.67 0.] [0.25 0.5 0.25]]
print(out.round(2))  # [[1. 0.] [0.33 1.34] [0.99 1.26]]

# In PyTorch, use the fused kernel (FlashAttention-style when available):
# torch.nn.functional.scaled_dot_product_attention(q, k, v, is_causal=True)
    Key ideas
    • Attention output for token i is a weighted average of value vectors; the weights are softmax of scaled query-key dot products.
    • The \(\sqrt{d_k}\) scale keeps the softmax from saturating as dimensions grow.
    • The causal mask sets future positions to −∞ before softmax, giving them exactly zero weight.
    • Compute and score memory grow as n² in sequence length.
    Common mistakes
    • Applying the mask after softmax (weights no longer sum to 1) or masking with 0 instead of −∞.
    • Forgetting the max-subtraction trick and getting overflow in a hand-written softmax.
    • Reading attention weights as a faithful explanation of model decisions; they are one signal among many.

    05.4 · The repeating unit

    The transformer block

    An LLM is the same block stacked N times (12 for GPT-2 small, 32 for a typical 7B model, 80 or more for the largest dense models). Each block does two things: attention lets tokens exchange information, then an MLP processes each token on its own. Both write their result back into a shared running vector called the residual stream.

    Why it matters for AI engineers

    Block shape sets parameter count, memory, and speed. Knowing that the parameters are about 12·L·d² lets you sanity-check any model card, estimate GPU memory, and understand what quantization, LoRA and pruning actually touch.

    Inside one block

    Modern LLMs use the pre-norm layout: normalize, run the sublayer, add the result back to the input. The additions keep a clean path for gradients through dozens of layers. Most current models use RMSNorm (scale only, no mean subtraction) and a gated MLP such as SwiGLU.

    Where the parameters live

    Attention has four d × d matrices (Q, K, V, O), so 4d² per layer. A standard MLP has two d × 4d matrices, so 8d². That gives roughly 12·L·d² plus the embedding tables. The MLP holds two thirds of the weights, and interpretability work suggests much factual recall is stored there.

    Parameter and memory calculator Try it 

    import torch, torch.nn as nn

class Block(nn.Module):
    """Pre-norm decoder block: x + Attn(Norm(x)), then x + MLP(Norm(x))."""
    def __init__(self, d, n_heads, mult=4):
        super().__init__()
        self.ln1 = nn.LayerNorm(d)
        self.attn = nn.MultiheadAttention(d, n_heads, batch_first=True)
        self.ln2 = nn.LayerNorm(d)
        self.mlp = nn.Sequential(nn.Linear(d, mult * d), nn.GELU(), nn.Linear(mult * d, d))

    def forward(self, x):                       # x: (batch, n, d)
        n = x.size(1)
        causal = torch.triu(torch.ones(n, n, dtype=torch.bool, device=x.device), 1)
        h = self.ln1(x)
        x = x + self.attn(h, h, h, attn_mask=causal, need_weights=False)[0]
        x = x + self.mlp(self.ln2(x))
        return x

blk = Block(d=768, n_heads=12)
print(sum(p.numel() for p in blk.parameters()))   # about 7.1M, close to 12 * 768**2
    Key ideas
    • Block = attention sublayer + MLP sublayer, each wrapped in norm and a residual add.
    • The residual stream is the model's working memory; every sublayer reads from it and writes to it.
    • Dense parameters ≈ 12·L·d² + embeddings; fp16 weights need 2 bytes per parameter.
    • Attention mixes across tokens; the MLP transforms each token independently.
    Common mistakes
    • Estimating serving memory from weights alone; the KV cache and activations add a lot at long contexts.
    • Assuming the block is post-norm as in the 2017 paper; nearly all modern LLMs are pre-norm.
    • Forgetting that GQA and gated MLPs change the 12·L·d² rule of thumb a little.

    05.5 · Three wirings of one block

    Encoder, decoder & encoder–decoder

    The same block can be wired three ways. The difference is mostly which tokens each token may attend to. An encoder sees the whole input in both directions, a decoder sees only the past so it can generate, and an encoder–decoder reads the input with an encoder and writes the output with a decoder that looks back at it.

    Why it matters for AI engineers

    Chat and generation models are decoder-only. Embedding models and rerankers used in RAG are usually encoders, which are small, fast and good at producing one vector per text. Some translation, speech and summarization systems still use encoder–decoders. Picking the right family can cut cost by orders of magnitude.

    • The three families share the block; they differ in masks and in what the output is used for.
    • Encoders give rich per-token or per-text vectors but do not generate text naturally.
    • Decoder-only models dominate general LLMs because next-token prediction scales and matches generation.
    • Cross-attention lets a decoder query an encoder's output.
    Common mistakes
    • Using a large chat model for a job a small encoder classifier or embedding model does faster and cheaper.
    • Expecting an encoder like BERT to write fluent text.
    • Assuming "transformer" means decoder-only; the original paper was an encoder–decoder.

    05.6 · Where the weights come from

    Pretraining → instruction tuning → RLHF

    A chat assistant is built in stages. Pretraining on trillions of tokens of text produces a base model that is good at continuing documents. Supervised fine-tuning (SFT) on example conversations teaches it to answer instead of ramble. Preference tuning (RLHF, DPO and relatives) then nudges it toward the answers people, or automated graders, prefer.

    Why it matters for AI engineers

    Each stage explains a behavior you will see: base models continue text instead of following instructions, chat models follow a chat template, preference tuning causes both politeness and over-refusal, and RL on verifiable tasks produced today's reasoning models. It also tells you which stage your own fine-tuning (Area 09) imitates.

    The pipeline

    Pretraining compute is roughly \(6ND\) floating-point operations for N parameters and D tokens. The Chinchilla study found about 20 tokens per parameter is compute-optimal for a fixed training budget, but models that will serve heavy traffic are often trained far longer, because a smaller, over-trained model is cheaper to run.

    How preference tuning works

    \[ \mathcal{L}_{RM} = -\log \sigma\big(r(x, y_w) - r(x, y_l)\big) \qquad \max_{\pi}\; \mathbb{E}\big[r(x,y)\big] - \beta\, \mathrm{KL}\big(\pi \,\|\, \pi_{\text{ref}}\big) \] \(y_w\) is the preferred ("winning") response and \(y_l\) the rejected one; \(\sigma\) is the sigmoid. The right-hand objective is what PPO-style RLHF maximizes. 
    import torch.nn.functional as F

def dpo_loss(pi_w, pi_l, ref_w, ref_l, beta=0.1):
    """Direct Preference Optimization.
    Each argument is a tensor of summed log-probs of a full response
    (w = chosen, l = rejected) under the policy (pi) or the frozen reference (ref)."""
    margin = (pi_w - ref_w) - (pi_l - ref_l)   # how much more the policy prefers w than ref does
    return -F.logsigmoid(beta * margin).mean()
    Key ideas
    • Pretraining builds knowledge and skills; post-training (SFT and preferences) shapes behavior.
    • Training compute ≈ 6·N·D FLOPs; ~20 tokens per parameter is compute-optimal, but serving costs favor smaller models trained longer.
    • RLHF = reward model from comparisons + RL with a KL penalty; DPO gets a similar effect with a simple classification-style loss.
    • RL with automatically checkable rewards (tests pass, answer matches) is how reasoning models are trained.
    Common mistakes
    • Prompting a base model like a chat model, or sending a chat model text without its chat template.
    • Believing fine-tuning reliably adds new factual knowledge; it mostly changes behavior and format.
    • Ignoring reward hacking: optimizing hard against an imperfect reward makes outputs longer, more flattering, or wrong in ways the reward misses.

    05.7 · From probabilities to text

    Decoding & sampling

    The model only outputs a probability for every token in the vocabulary. Decoding is the rule that picks one: take the most likely token (greedy), or reshape the distribution and draw from it at random (sampling). The chosen token is appended and the model runs again, one token at a time.

    Why it matters for AI engineers

    Temperature, top-k and top-p are the knobs you most often see in APIs and serving engines. The wrong settings cause repetitive loops, invented details, or broken JSON. Generating one token per forward pass is also why output tokens cost more and take longer than input tokens.

    The generation loop

    Temperature, top-k and top-p

    Temperature divides the logits before softmax: below 1 sharpens the distribution, above 1 flattens it, and near 0 approaches greedy. Top-k keeps only the k most likely tokens. Top-p (nucleus sampling) keeps the smallest set whose probabilities add up to p, so the set grows when the model is unsure and shrinks when it is confident.

    \[ p_i = \frac{e^{z_i / T}}{\sum_j e^{z_j / T}} \qquad \text{top-}p:\ \text{keep the fewest tokens with } \textstyle\sum p_i \ge p,\ \text{then renormalize} \]
    Reshape the next-token distribution Try it

    Greedy is not the most likely sentence

    Greedy picks the best token at each step, which can miss a better overall sequence. Beam search keeps the b best partial sequences and is still used for translation and speech, but for open-ended text it tends to produce bland, repetitive output, so chat models sample.

    import numpy as np

def sample(logits, temperature=1.0, top_k=None, top_p=None, rng=np.random.default_rng()):
    if temperature == 0:
        return int(np.argmax(logits))                     # greedy
    z = logits / temperature
    p = np.exp(z - z.max()); p /= p.sum()
    order = np.argsort(p)[::-1]                           # most likely first
    keep = np.ones_like(p, dtype=bool)
    if top_k is not None:
        keep[order[top_k:]] = False
    if top_p is not None:
        cum = np.cumsum(p[order])
        cutoff = np.searchsorted(cum, top_p) + 1          # smallest set reaching top_p
        keep[order[cutoff:]] = False
    p = np.where(keep, p, 0.0); p /= p.sum()
    return int(rng.choice(len(p), p=p))
    TaskTypical settingWhy
    Extraction, classification, JSONgreedy or T ≈ 0–0.2one right answer; randomness only adds errors
    Code, factual Q&AT ≈ 0.2–0.5slight variety, stays on the likely path
    Chat, writing, brainstormingT ≈ 0.7–1.0, top-p ≈ 0.9–0.95natural variety without the junk tail
    Many candidates to rerank or voteT ≈ 0.8–1.0, n samplesdiversity matters more than any one sample
    Key ideas
    • The model gives a distribution; decoding turns it into text one token per forward pass.
    • Temperature rescales logits; top-k and top-p cut the unlikely tail and renormalize.
    • Top-p adapts to the model's confidence; top-k does not.
    • Greedy and beam search maximize probability; sampling trades a little probability for variety.
    Common mistakes
    • Expecting temperature 0 to be perfectly reproducible on a hosted API; batching and floating-point order can still change outputs.
    • Raising temperature to "make the model smarter"; it only makes it more random.
    • Tuning temperature and top-p at the same time without measuring; change one at a time.
    • Assuming every API accepts these knobs; some hosted reasoning models fix sampling and reject custom values.

    05.8 · Beyond the dense text model

    MoE, multimodal & reasoning models

    Three changes to the basic recipe define today's large models. Mixture-of-experts (MoE) stores many MLPs but runs only a few per token. Multimodal models turn images and audio into token-like vectors so the same transformer can read them. Reasoning models are trained to spend extra output tokens thinking before they answer.

    Why it matters for AI engineers

    These change your cost and latency math. An MoE model needs memory for all its parameters but compute for only the active ones. An image can cost hundreds or thousands of tokens. A reasoning model may produce thousands of hidden thinking tokens that you pay for and wait for, in exchange for much better results on hard problems.

    Mixture-of-experts

    In an MoE layer, the single MLP is replaced by E expert MLPs and a small router. The router scores the experts for each token, keeps the top k (often 1 or 2 of 8, or a handful out of dozens or hundreds), and mixes their outputs by the router weights. Attention layers stay shared.

    MoE routing: total vs active parameters Try it

    Multimodal input

    A vision encoder cuts an image into patches (often 14 or 16 pixels square), turns each into a vector, and a small projector maps those vectors into the LLM's embedding space. The LLM then attends over image vectors and text tokens together. Audio works the same way with short time slices.

    Reasoning models

    Reasoning models are trained with reinforcement learning on problems with checkable answers, which teaches them to write a long chain of thought, check their work and backtrack before giving a final answer. Accuracy on hard math, code and planning rises with the thinking budget. This is called test-time compute scaling.

    import torch, torch.nn as nn

class MoE(nn.Module):
    """Top-k mixture-of-experts MLP (no load-balancing loss, for clarity)."""
    def __init__(self, d, n_experts=8, k=2, mult=4):
        super().__init__()
        self.k = k
        self.router = nn.Linear(d, n_experts, bias=False)
        self.experts = nn.ModuleList(
            nn.Sequential(nn.Linear(d, mult * d), nn.GELU(), nn.Linear(mult * d, d))
            for _ in range(n_experts))

    def forward(self, x):                          # x: (tokens, d)
        w, idx = self.router(x).topk(self.k, dim=-1)
        w = w.softmax(dim=-1)                      # renormalize over chosen experts
        out = torch.zeros_like(x)
        for slot in range(self.k):
            for e, expert in enumerate(self.experts):
                sel = idx[:, slot] == e
                if sel.any():
                    out[sel] += w[sel, slot, None] * expert(x[sel])
        return out
    Key ideas
    • MoE decouples capacity (total parameters, which set memory) from per-token compute (active parameters).
    • Images and audio become sequences of vectors in the LLM's embedding space; they cost context like text.
    • Reasoning models trade output tokens and latency for accuracy on hard, checkable problems.
    • All three are still the same transformer block underneath.
    Common mistakes
    • Sizing GPU memory for an MoE model by its active parameters; all experts must be loaded.
    • Ignoring image token cost when sending many or very large images.
    • Using maximum reasoning effort on simple, latency-sensitive requests.

    05.9 · From theory to a decision

    Choosing a model

    There is no best model, only the cheapest model that passes your bar on your task. Model choice is a trade-off between quality, latency, cost and where the data may go, and the right answer changes every few months as new models ship. Think in model classes, shortlist two or three, and let an evaluation on your own examples decide.

    Why it matters for AI engineers

    Model choice is often the biggest single lever on a product's unit economics and speed. Prices across model tiers commonly differ by 10× to 100× per token, and a small model that is good enough can also respond several times faster.

    Start from the hard constraints

    Rule things out before you rank anything. Privacy and deployment rules come first, because they can remove whole categories. Then task difficulty, then latency and volume. Only after that should you look at leaderboards.

    Model-class helper Try it

    The helper scores five generic classes with simple rules of thumb. Use it to see how constraints interact, for example how a strict data rule overrides a need for top quality.

    The quality–cost frontier

    Plot candidates by cost per task and quality on your eval, and keep only those on the frontier: no other model is both cheaper and better. Cost per task matters more than price per token, because a stronger model that finishes in one attempt can beat a cheap one that needs retries.

    Let an eval decide

    import time, statistics

def compare(models, cases, call_model, is_correct, price_per_call):
    """models: list of model ids; cases: list of (prompt, expected).
    call_model(model_id, prompt) -> text is your own wrapper around the provider SDK."""
    for m in models:
        passed, latencies = 0, []
        for prompt, expected in cases:
            t0 = time.perf_counter()
            out = call_model(m, prompt)
            latencies.append(time.perf_counter() - t0)
            passed += is_correct(out, expected)
        p95 = statistics.quantiles(latencies, n=20)[18]
        print(f"{m:24s} pass={passed / len(cases):.0%}  p95={p95:.2f}s  "
              f"cost/1k calls=${1000 * price_per_call[m]:.2f}")

    Key ideas
    • Apply hard constraints (privacy, deployment, modality) first; they remove whole classes.
    • Choose the cheapest model that clears your quality bar on your own eval, measured per completed task.
    • Route by difficulty: a small model for easy requests and a stronger one for hard ones often beats any single choice.
    • Model rankings change fast; a reusable eval harness keeps your choice current.
    Common mistakes
    • Picking from a public leaderboard without testing on your own data.
    • Comparing price per token instead of cost per successful task, including retries and thinking tokens.
    • Self-hosting to save money at low volume, where idle GPUs usually cost more than API calls.
    • Hard-coding one model id everywhere, which makes switching or routing painful.
