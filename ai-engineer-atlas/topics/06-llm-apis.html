Building with LLM APIs

Most AI products are built on a hosted model behind an HTTP API. This area covers the engineering around that one call: writing prompts that hold up, getting machine-readable output, letting the model call your code, streaming answers, and keeping cost, latency and failure rates under control.

In this area

    Every feature in this area hangs off a single request and response. You write a prompt (6.1), optionally attach an output schema (6.2) and tool definitions (6.3), and send it over HTTPS. The model streams tokens back (6.4); if it asks for a tool, your code runs it and the loop repeats. Each response reports token usage, which is what you pay for and what caching reduces (6.5). Around the whole exchange sits a reliability layer that retries, times out, and falls back when the provider has a bad minute (6.6). Learn them in order: each one builds on the request shape introduced before it.

    06.1 · The first lever

    Prompt engineering

    A prompt is the full specification you hand a capable colleague who knows nothing about your product. The model acts only on what is in the request, so prompt engineering means writing that specification clearly and proving, with tests, that it works on inputs you have not seen.

    Why it matters for AI engineers

    A prompt change is the cheapest change you can ship: no training run, no new infrastructure. It often closes most of a quality gap before retrieval or fine-tuning is needed, and it deserves version control and regression tests like any other code.

    Anatomy of a request

    Chat APIs take a system prompt plus a list of user and assistant messages. The API is stateless: every call resends the whole conversation, so turn ten pays for turns one to nine again.

    Order content from stable to variable. The model reads top to bottom, and an unchanged prefix can be cached by the provider (6.5).

    Reasons let the model apply a rule to cases you never listed. Tags keep it from obeying instructions hidden inside documents or user text.

    import anthropic

client = anthropic.Anthropic()   # reads ANTHROPIC_API_KEY from the environment

SYSTEM = """You triage support tickets for a payroll SaaS product.
A good triage lets the on-call engineer act in under a minute.

Rules:
- Pick exactly one category from: billing, bug, how-to, security.
- Mark priority "high" only if payroll runs are blocked, because those
  have legal deadlines.
- If the ticket mentions leaked credentials, the category is security,
  whatever else it says.

Reply in this format:
category: <one word>
priority: <low|medium|high>
summary: <one sentence for the engineer>"""

EXAMPLES = """<examples>
<ticket>Can't find where to download last year's W-2s.</ticket>
category: how-to
priority: low
summary: User needs the path to annual tax forms.
</examples>"""

def triage(ticket: str) -> str:
    resp = client.messages.create(
        model="your-model-id",
        max_tokens=300,
        system=SYSTEM,
        messages=[{
            "role": "user",
            "content": f"{EXAMPLES}\n\n<ticket>{ticket}</ticket>",
        }],
    )
    # content is a list of blocks; take the text ones
    return "".join(b.text for b in resp.content if b.type == "text")

print(triage("Payroll run stuck at 'processing' since 9am, 400 employees unpaid"))

    Test prompts like code

    Run old and new versions over a fixed set of 20 to 50 real inputs, change one thing at a time, and log the prompt version with every request.

    Two older tricks are fading. Some newer models reject temperature/top_p and assistant prefill (writing the start of the reply yourself), and temperature 0 never guaranteed identical outputs. Use structured output (6.2) for format control.

    Key ideas
    • The API is stateless; the request is the model's whole world.
    • Order content from stable to variable and keep the question last.
    • Give reasons for rules and wrap data in tags.
    • Judge prompt changes on an eval set, never on a few hand-picked inputs.
    Common mistakes
    • Pasting user text into the system prompt, which lets users rewrite your rules.
    • Contradictory rules, such as "be concise" plus "explain every step".
    • Relying on temperature 0 or prefill with models that may not support them.

    06.2 · Text in, data out

    Structured output

    Your users read prose; your code reads data. When a model's answer feeds a database, a UI or the next pipeline step, it must parse every time with the fields and types you expect. Structured output turns a text generator into a function that returns typed values.

    Why it matters for AI engineers

    Extraction, classification, routing and agent planning all depend on parseable output. A parser that fails on 2% of responses means 2% of users hit an error page, or worse, a silent bad write.

    What goes wrong without constraints

    Inject a failure, see who catches it Try it

    Asking nicely works most of the time; at scale you meet every failure above. JSON mode fixes only syntax. Schema-constrained decoding prevents shape errors, and only your own checks catch truncation and wrong-but-valid answers.

    How constrained decoding works

    The provider compiles your JSON Schema into a grammar. At each step it zeroes the probability of every token that would break the grammar, renormalises, and samples from what is left.

    Shape is guaranteed; content is not. Generation runs left to right, so put a reasoning field before the decision fields if you want the model to think first.

    import anthropic
from typing import Literal
from pydantic import BaseModel

client = anthropic.Anthropic()

class Triage(BaseModel):
    reasoning: str
    category: Literal["billing", "bug", "how-to", "security"]
    priority: Literal["low", "medium", "high"]
    summary: str

SCHEMA = {
    "type": "object",
    "properties": {
        "reasoning": {"type": "string", "description": "Two sentences max."},
        "category":  {"type": "string", "enum": ["billing", "bug", "how-to", "security"]},
        "priority":  {"type": "string", "enum": ["low", "medium", "high"]},
        "summary":   {"type": "string"},
    },
    # reasoning comes first so the model thinks before it labels
    "required": ["reasoning", "category", "priority", "summary"],
    "additionalProperties": False,
}

def triage(ticket: str) -> Triage:
    resp = client.messages.create(
        model="your-model-id",
        max_tokens=1024,
        system="You triage support tickets for a payroll SaaS product.",
        messages=[{"role": "user", "content": f"<ticket>{ticket}</ticket>"}],
        output_config={"format": {"type": "json_schema", "schema": SCHEMA}},
    )
    if resp.stop_reason == "max_tokens":
        raise RuntimeError("Output was cut off; raise max_tokens")  # truncated JSON will not parse
    text = next(b.text for b in resp.content if b.type == "text")
    return Triage.model_validate_json(text)   # typed object, plus a second check

    Fallbacks and schema design

    Without native support, define one tool whose input_schema is your schema, or run a validate-and-repair loop that feeds the error back. Keep schemas shallow, prefer enums, and add an "unknown" option so the model never has to invent a value.

    import json
from pydantic import ValidationError

def triage_with_repair(ticket: str, attempts: int = 3) -> Triage:
    schema_text = json.dumps(SCHEMA, indent=2)
    messages = [{"role": "user", "content":
                 f"Return only JSON matching this schema:\n{schema_text}\n<ticket>{ticket}</ticket>"}]
    for _ in range(attempts):
        resp = client.messages.create(model="your-model-id", max_tokens=1024, messages=messages)
        text = "".join(b.text for b in resp.content if b.type == "text")
        try:
            return Triage.model_validate_json(text)
        except ValidationError as err:
            # show the model its own output and the exact error
            messages += [
                {"role": "assistant", "content": text},
                {"role": "user", "content": f"That failed validation:\n{err}\nReturn corrected JSON only."},
            ]
    raise ValueError("No valid output after retries")
    ApproachGuaranteesUse when
    Instructions onlyNothingPrototypes, human-read output
    JSON modeValid JSON syntaxLoose shapes, provider lacks schemas
    Schema-constrained outputValid JSON matching your schemaProduction extraction and classification
    Single forced-format toolSchema-valid arguments (with strict mode)Provider supports tools but not output schemas
    Validate and repair loopEventually valid, or a clear errorAny model, including local ones
    Key ideas
    • Constrained decoding masks tokens that would break the schema, so output always parses.
    • A valid shape is not a correct answer; validate business rules in code.
    • Field order is generation order: reasoning before decisions.
    • No native schemas? Use a single tool as the schema or a repair loop.
    Common mistakes
    • Ignoring stop_reason; a reply cut off at max_tokens is half a JSON object.
    • No "unknown" option, so the model fabricates a label for ambiguous input.
    • Stripping code fences with regexes in production.

    06.3 · Let the model call your code

    Tool use / function calling

    Tool use lets the model ask your program to do things: look up an order, query a database, send an email. You describe the functions; the model replies with a structured request to call one; your code runs it and returns the result. The model never executes anything itself.

    Why it matters for AI engineers

    Tool use connects models to live data and real actions. It is the core mechanism of every agent in Area 08, so getting the loop, errors and security boundaries right here pays off later.

    The loop

    When the model wants a tool, the response ends with stop_reason == "tool_use". Append the whole assistant message, run each requested function, and send back one tool_result per call. Repeat until end_turn.

    Step through a tool-call loop Try it
    1 / 6 

    import json
import anthropic

client = anthropic.Anthropic()

TOOLS = [{
    "name": "get_weather",
    "description": "Current weather for a city. Use when the user asks about "
                   "weather, temperature or whether to bring an umbrella.",
    "input_schema": {
        "type": "object",
        "properties": {"city": {"type": "string", "description": "City name, e.g. Paris"}},
        "required": ["city"],
    },
}]

def get_weather(city: str) -> dict:
    return {"city": city, "temp_c": 18, "conditions": "light rain"}   # call a real API here

HANDLERS = {"get_weather": get_weather}

def run(user_text: str, max_steps: int = 8) -> str:
    messages = [{"role": "user", "content": user_text}]
    for _ in range(max_steps):                      # hard cap: never loop forever
        resp = client.messages.create(
            model="your-model-id", max_tokens=2048, tools=TOOLS, messages=messages,
        )
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")

        messages.append({"role": "assistant", "content": resp.content})
        results = []
        for block in resp.content:
            if block.type != "tool_use":
                continue
            try:
                output = HANDLERS[block.name](**block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": json.dumps(output)})
            except Exception as exc:                  # report failures, do not drop them
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": f"Error: {exc}", "is_error": True})
        messages.append({"role": "user", "content": results})   # all results in ONE message
    raise RuntimeError("Tool loop did not finish")

print(run("Do I need an umbrella in Paris today?"))

    How the pieces connect

    The description is what the model reads to choose a tool, so say what it does, when to use it and when not to. Every definition costs input tokens on every call, so keep tools few and distinct.

    Several tool_use blocks can arrive at once: run them concurrently and return all results in one user message. Report failures with is_error and a message the model can act on.

    Safety boundaries

    RiskControl
    The model chooses the argumentsValidate them like a public API request
    Tool runs with broad credentialsRun with the end user's permissions only
    Destructive or irreversible actionRequire human confirmation
    Tool results contain attacker textTreat as untrusted input (prompt injection, Area 14)
    Model keeps calling a failing toolHard cap on loop iterations

    Some newer models reject the forcing tool_choice options (any or a named tool). When you need guaranteed JSON, use structured output (6.2) and steer tool choice through the prompt.

    Key ideas
    • The model writes a call request; your code executes it and answers by tool_use_id.
    • Loop until stop_reason is no longer tool_use, with an iteration cap.
    • Return all results of a turn in one message; report errors with is_error.
    • Arguments and results are untrusted: validate, limit permissions, confirm destructive actions.
    Common mistakes
    • Appending only the assistant's text and dropping its tool_use blocks.
    • Silently dropping a failed call, which makes the next request invalid.
    • Giving a tool admin credentials "for convenience".

    06.4 · Perceived latency

    Streaming

    A model writes its answer one token at a time. Without streaming, the user waits for the last token; with streaming, each token is forwarded as soon as it exists, so text appears in well under a second. Total time stays the same, and the wait people feel shrinks dramatically.

    Why it matters for AI engineers

    Time to first token is the latency users feel, and streaming is the biggest single improvement to it. It also keeps long generations from hitting HTTP timeouts, which is why SDKs recommend streaming for large max_tokens.

    Two clocks

    Time to first token (TTFT) covers network, queueing and prefill, when the model reads every input token. After that, output speed in tokens per second sets the pace.

    \[ T_{\text{total}} \approx \text{TTFT} + \frac{N_{\text{out}}}{\text{tokens per second}} \] Example: TTFT 0.6 s, 300 output tokens at 50 tokens/s gives 0.6 + 6.0 = 6.6 s. Blocking shows nothing for 6.6 s; streaming shows text after 0.6 s.

    What travels over the wire

    Streams use server-sent events (SSE): one long HTTP response made of small typed records. SDKs parse them for you and still assemble the final message, usage included.

    import time
import anthropic

client = anthropic.Anthropic()

start = time.perf_counter()
first = None
with client.messages.stream(
    model="your-model-id",
    max_tokens=2048,
    messages=[{"role": "user", "content": "Explain SSE in three short paragraphs."}],
) as stream:
    for text in stream.text_stream:          # yields text fragments as they arrive
        if first is None:
            first = time.perf_counter() - start
        print(text, end="", flush=True)
    final = stream.get_final_message()       # full message, assembled by the SDK

total = time.perf_counter() - start
out_tok = final.usage.output_tokens
print(f"\nTTFT {first:.2f}s | total {total:.2f}s | "
      f"{out_tok / (total - first):.0f} tokens/s after first token")

    Streaming through your backend

    Never call the provider from the browser; that exposes your API key. Relay the stream from your backend, and disable proxy buffering or the stream arrives all at once.

    import json
from fastapi import FastAPI
from fastapi.responses import StreamingResponse

app = FastAPI()

@app.get("/chat")
def chat(q: str):
    def events():
        with client.messages.stream(
            model="your-model-id", max_tokens=1024,
            messages=[{"role": "user", "content": q}],
        ) as stream:
            for text in stream.text_stream:
                yield f"data: {json.dumps({'text': text})}\n\n"   # one SSE record per fragment
        yield "data: [DONE]\n\n"
    return StreamingResponse(events(), media_type="text/event-stream",
                             headers={"X-Accel-Buffering": "no"})

    Errors can arrive after a 200 status and some text, so the UI needs a half-finished state. Cancel the upstream request when the user leaves, and run a streamed tool call only once its JSON is complete.

    Key ideas
    • Streaming leaves generation speed unchanged and moves the first visible text from the end to TTFT.
    • TTFT grows with input length; total time grows with output length.
    • A stream is SSE: start, many deltas, a delta with stop reason and usage, stop.
    • Relay through your backend and cancel upstream when the user leaves.
    Common mistakes
    • Measuring only total latency and missing TTFT.
    • A buffering proxy that turns the stream back into one blob.
    • Treating HTTP 200 as success when the stream can still end with an error event.

    06.5 · The unit economics

    Tokens, caching & cost

    You pay per token: a price per million input tokens and a higher one per million output tokens. The biggest line item is often the same long system prompt resent on every call. Prompt caching lets the provider reuse that work, so the repeated prefix costs a fraction and the first token arrives sooner.

    Why it matters for AI engineers

    Cost and latency decide whether a feature ships. Estimating a design's cost on a napkin and cutting it with caching, batching or a smaller model is a core skill and a common interview question.

    Counting tokens

    English prose averages about 4 characters, or 0.75 words, per token; code, JSON and many other languages need more. Tokenizers differ between model families, so compare models on cost per request. The usage object on each response gives exact counts.

    Input means everything you send: system prompt, tool definitions, all earlier messages and the new question. Hidden reasoning tokens are billed as output.

    The cost formula, worked

    \[ \text{cost} = \frac{p_{\text{in}}\left(N_{\text{in}} + m_w N_{\text{write}} + m_r N_{\text{read}}\right) + p_{\text{out}}\,N_{\text{out}}}{10^6} \] \(p\) is price per million tokens, \(N_{\text{in}}\) uncached input tokens, \(N_{\text{write}}\) tokens written to the cache, \(N_{\text{read}}\) tokens read from it, \(N_{\text{out}}\) output tokens. The multipliers are provider-specific; on Anthropic a 5-minute cache write is about \(m_w = 1.25\) and a cache read about \(m_r = 0.1\) of the base input price.

    How prompt caching works

    During prefill the model computes key and value tensors for every input token. If the next request starts with the same tokens, the provider reuses them. Matching runs from the first token and stops at the first difference.

    So put stable content first and keep timestamps and IDs out of the system prompt. Entries expire after minutes, and prefixes below a minimum length (often around a thousand tokens) are not cached. On Anthropic you opt in with cache_control and verify hits in usage.

    import anthropic

client = anthropic.Anthropic()
DOCS = open("product_docs.md").read()          # large and identical on every call

def answer(question: str):
    resp = client.messages.create(
        model="your-model-id",
        max_tokens=600,
        system=[
            {"type": "text", "text": "You answer questions about our product."},
            {"type": "text", "text": DOCS,
             "cache_control": {"type": "ephemeral"}},   # cache everything up to here
        ],
        messages=[{"role": "user", "content": question}],   # volatile part goes last
    )
    u = resp.usage
    print("uncached in:", u.input_tokens,
          "| cache write:", u.cache_creation_input_tokens,
          "| cache read:", u.cache_read_input_tokens,
          "| out:", u.output_tokens)
    return resp

def cost_usd(u, p_in=3.0, p_out=15.0, m_w=1.25, m_r=0.1):   # EXAMPLE prices per million tokens
    return (p_in * (u.input_tokens
                    + m_w * (u.cache_creation_input_tokens or 0)
                    + m_r * (u.cache_read_input_tokens or 0))
            + p_out * u.output_tokens) / 1e6
    LeverSavesTrade-off
    Prompt cachingMost of the repeated-prefix cost; lower TTFTNeeds a stable prefix and steady traffic
    Shorter outputs (instructions, max_tokens, terse formats)Output cost and generation timeRisk of cutting useful content
    Smaller or cheaper model per routeOften 5 to 20× per tokenQuality must be checked on your eval set

    Trim context (fewer documents, summarised history)Input cost and TTFTMay drop information the model needed

    Key ideas
    • Cost is input tokens times input price plus output tokens times a higher output price.
    • Caching is a byte-exact prefix match: stable first, volatile last.
    • Output length usually dominates latency and, after caching, a large share of cost.
    • Log usage on every response; it is the ground truth.
    Common mistakes
    • A timestamp at the top of the system prompt, giving a 0% hit rate with no error.
    • Comparing price per token across models with different tokenizers.
    • Estimating from demo prompts instead of real input and output lengths.

    06.6 · When things go wrong

    Errors, retries & routing

    At scale you will see rate limits, overloaded servers, network resets, slow tails and 200 responses that are cut off. Reliability work means classifying each failure, retrying only what a retry can fix, spacing retries out, and having somewhere else to send traffic.

    Why it matters for AI engineers

    Your uptime is capped by your weakest dependency, and a hosted model is one you do not control. Retry storms can turn a provider's brief slowdown into your own outage.

    Classify, then act

    The status code tells you whether a retry can help. Client errors (4xx except 408, 409 and 429) fail the same way forever; rate limits, server errors and timeouts are usually transient.

    SignalMeaningRetry?Action
    400Invalid requestNoFix the request; log and alert
    401 / 403Bad key or no permissionNoPage someone; check secrets
    404Unknown model or endpointNoCheck the model id (retired models disappear)
    413Request too largeNoTrim context or chunk the input
    429Rate limitedYesWait for retry-after, then back off; smooth traffic
    500 / 502 / 503Server-side errorYesBack off with jitter; fall back after a few tries
    529 (Anthropic)API temporarily overloadedYesBack off; consider another model or region
    Connection error / timeoutNetwork or slow responseUsuallyRetry once or twice within a total deadline
    200 with stop_reason max_tokensOutput truncatedAdjustRaise max_tokens or ask for shorter output
    200 but fails validationWrong shape or contentRepairValidate-and-repair loop (6.2), then fall back

    Backoff with jitter

    Exponential backoff doubles the wait after each failure, up to a cap. Jitter randomises each wait, so clients that failed together do not retry together (the thundering herd).

    \[ \text{sleep}_k = \text{uniform}\!\left(0,\ \min\!\left(\text{cap},\ \text{base}\cdot 2^{k}\right)\right) \] \(k\) is the retry number starting at 0. If the server sends a retry-after value, wait at least that long.
    Backoff timeline for clients that failed together Try it

    Set a total deadline for user-facing calls. Know your SDK's defaults: the Anthropic Python SDK retries twice (max_retries=2) with a 10-minute timeout, so wrapping it in three retries of your own allows up to nine calls.

    import random
import time
import anthropic

# Own the retry policy: no hidden SDK retries, a timeout that suits interactive use.
client = anthropic.Anthropic(max_retries=0, timeout=30.0)
RETRYABLE = {408, 409, 429, 500, 502, 503, 504, 529}

def _retry_after(err) -> float:
    try:
        return float(err.response.headers.get("retry-after", 0))
    except (TypeError, ValueError):
        return 0.0

def create_with_backoff(*, attempts=5, base=0.5, cap=8.0, deadline_s=25.0, **kwargs):
    start = time.monotonic()
    for k in range(attempts):
        try:
            return client.messages.create(**kwargs)
        except anthropic.APIConnectionError:            # network failure or timeout
            wait_floor = 0.0
            if k == attempts - 1:
                raise
        except anthropic.APIStatusError as err:         # RateLimitError is a subclass
            if err.status_code not in RETRYABLE or k == attempts - 1:
                raise
            wait_floor = _retry_after(err)
        delay = max(wait_floor, random.uniform(0, min(cap, base * 2 ** k)))   # full jitter
        if time.monotonic() - start + delay > deadline_s:
            raise TimeoutError("retry budget exhausted")
        time.sleep(delay)

def answer(messages, models=("your-primary-model-id", "your-fallback-model-id")):
    last_err = None
    for model in models:                                # fallback chain
        try:
            return create_with_backoff(model=model, max_tokens=1024, messages=messages)
        except anthropic.APIStatusError as err:
            if err.status_code < 500 and err.status_code not in RETRYABLE:
                raise                                   # our bug: another model will not help
            last_err = err
        except (anthropic.APIConnectionError, TimeoutError) as err:
            last_err = err
    raise last_err

    Fallbacks and routing

    Every fallback needs the same eval set as the primary, because a prompt tuned for one model can behave differently on another, and caches do not carry across models.

    Routing uses the same plumbing on purpose: send easy requests to a cheap model and escalate when validation fails. Retrying a model call is safe; retrying a tool that charges a card is not, so give such tools idempotency keys.

    Key ideas
    • Classify first: 4xx client errors never succeed on retry.
    • Back off exponentially with full jitter, honour retry-after, stop at a deadline.
    • Know your SDK's built-in retries so you do not multiply attempts.
    • Circuit breakers and evaluated fallbacks keep the product up during incidents.
    Common mistakes
    • Retrying 400 errors in a loop, burning quota and hiding a bug.
    • Backoff without jitter, so clients retry in lockstep.
    • Hitting rate limits constantly instead of smoothing traffic with a limiter or queue.
