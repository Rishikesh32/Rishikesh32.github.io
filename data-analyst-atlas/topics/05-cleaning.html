Data cleaning & preparation

Real exports arrive with blanks, repeated customers, impossible values, three date formats and five spellings of the same city. Cleaning turns that mess into a table whose numbers you can defend. Most analysts spend a large share of every project here, and the decisions you make quietly change every result downstream.

In this area

    Every cleaning job follows the same path. You profile the raw export to see what is wrong, fix each kind of problem with a rule you can explain (missing values, duplicates, outliers, types and dates, messy text), and then run automated checks before anyone uses the table. When a check fails, you go back and fix the rule, not the number. The six lessons below follow that path, using one running example: a customer and order export from an online store's CRM.

    05.1 · Blanks have a story

    Missing values

    A blank cell is a fact about how the data was collected. Before you fill or drop anything, ask why the value is missing, because the answer decides which fix keeps your averages honest and which one quietly bends them.

    Why it matters for analysts

    Pandas, SQL and spreadsheets all skip blanks in AVG by default, so a column with 20% missing values silently becomes an average of the other 80%. If the missing rows are your biggest customers, every revenue-per-customer number you report will be too low.

    Three reasons a value goes missing

    Statisticians name three patterns. MCAR (missing completely at random) means the gaps are pure accident, like a form that crashed now and then. MAR (missing at random) means the gaps depend on another column you can see, such as enterprise accounts that are invoiced offline. MNAR (missing not at random) means the gap depends on the hidden value itself, such as people with high incomes skipping the income field.

    Count before you fix

    Always measure the damage per column first. A column with 0.3% blanks and one with 40% blanks need different treatment, and a sudden jump in blanks after a release is often a tracking bug, not customer behaviour.

    import pandas as pd

customers = pd.read_csv("crm_export.csv")
# share of missing values per column, worst first
print(customers.isna().mean().sort_values(ascending=False).round(3))

# is missingness linked to another column? (MAR check)
print(customers["annual_spend"].isna().groupby(customers["plan"]).mean())

# fill within each plan, and keep a flag so the fill stays visible
customers["spend_was_missing"] = customers["annual_spend"].isna()
customers["annual_spend"] = customers["annual_spend"].fillna(
    customers.groupby("plan")["annual_spend"].transform("median"))
    -- COUNT(col) skips NULLs, so the difference is the number of blanks
SELECT plan,
       COUNT(*)                       AS customers,
       COUNT(*) - COUNT(annual_spend) AS missing_spend,
       ROUND(AVG(annual_spend), 0)    AS avg_spend_known_only
FROM crm_customers
GROUP BY plan;

    Below, 25 customers have a known true annual_spend, but the export lost 5 values. Three of the five are Enterprise accounts. Switch strategies and watch the mean, median and spread move compared with the truth, which you never get to see in real life.

    What each fill does to your numbers

    Every fill trades one distortion for another. Mean and median fills keep row counts but pile values onto one number, which shrinks the spread and weakens correlations. Filling with 0 is right only when blank truly means zero, such as "no refunds".

    StrategyUse whenCost
    Drop rowsFew blanks (under ~5%) and MCARSmaller sample; biased if not MCAR
    Fill with 0 or a constantBlank really means "none"Wrong anywhere else
    Mean / medianQuick model input, MCARShrinks spread, adds a spike
    Group medianMAR on a column you haveNeeds enough rows per group
    Flag + fillMissingness itself might matterOne more column to explain
    Leave null, report itMNAR or a key business figureHonest but less convenient
    Key ideas
    • Measure blanks per column and per segment before choosing a fix.
    • MCAR, MAR and MNAR describe why values are missing, and that decides which fix is safe.
    • AVG, mean() and spreadsheet AVERAGE silently ignore blanks.
    • Mean and median fills keep rows but shrink spread; group-wise fills use the column that explains the gap.
    • A was_missing flag keeps the fix visible to anyone who uses the table later.
    Common mistakes
    • Filling with 0 when blank means "unknown", which drags averages down.
    • Dropping rows without checking who gets dropped (often your biggest or newest customers).
    • Treating the strings "N/A", "-" or "" as real values instead of nulls.
    • Filling before splitting train and test data for a model, which leaks information.

    05.2 · One row per thing

    Duplicates & keys

    Every table should have a grain: a sentence that says what one row is, such as "one row per customer" or "one row per order line". The key is the column, or set of columns, that makes each row unique at that grain. Duplicates are rows that break the grain, and they inflate every count and sum built on top.

    Why it matters for analysts

    A CRM where sales reps re-enter the same customer will report more customers than you have. Worse, joining orders to a customer table with duplicate keys multiplies order rows, so revenue doubles on the dashboard without anyone noticing.

    Exact duplicates and fuzzy duplicates

    Exact duplicates are identical rows, usually from an export or load that ran twice. Fuzzy duplicates are the same real-world entity typed differently: ANA.LOPEZ@mail.com and ana.lopez@mail.com . To catch those you normalize the key first, then group, then keep one survivor per group with an explicit rule such as "most recently updated".

    -- 1. Is customer_id really unique? Any row returned breaks the grain.
SELECT customer_id, COUNT(*) AS n
FROM crm_customers
GROUP BY customer_id
HAVING COUNT(*) > 1;

-- 2. Keep one survivor per normalized email: the latest update wins
WITH ranked AS (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY LOWER(TRIM(email))
           ORDER BY updated_at DESC, customer_id
         ) AS rn
  FROM crm_customers
)
SELECT * FROM ranked WHERE rn = 1;
    df["email_key"] = df["email"].str.strip().str.lower()
print(df.duplicated(subset="email_key").sum(), "duplicate rows")

clean = (df.sort_values("updated_at")
           .drop_duplicates(subset="email_key", keep="last"))
assert clean["email_key"].is_unique

    Pick the key, see what collapses

    Ten rows from the CRM describe six real people. Two different people are both called Alex Kim. Choose which columns form the key and whether to normalize text, then check which rows merge. The right key merges every true duplicate and never merges two different people.

    Dedupe-key chooser Try it

    Duplicate keys multiply joins

    A duplicate on the "one" side of a join turns every matching row on the "many" side into two. The query still runs, the totals just grow. Check key uniqueness before every join you did not build yourself.

    Key ideas
    • Write the grain of every table in one sentence, then test that the key is unique at that grain.
    • Normalize text keys (trim, lowercase) before comparing them.
    • Choose the survivor with an explicit rule such as latest updated_at, and log merged ids.
    • A key that is too loose (name only) merges different people; one that is too strict (raw email) misses duplicates.
    • Duplicate keys on the "one" side of a join silently multiply sums.
    Common mistakes
    • Running SELECT DISTINCT * and calling it deduplicated; fuzzy duplicates survive.
    • Deduplicating on name alone, which merges different people with common names.
    • Letting nulls match each other: two blank phone numbers are not the same phone.
    • Keeping the first row in export order instead of a reproducible rule.

    05.3 · Errors or extremes

    Outliers

    An outlier is a value far from the rest. Some are errors (a price typed in cents, an age of 212) and should be fixed. Others are real and important (a B2B customer who orders 40 laptops) and should be kept. A rule can find candidates; only you can decide which kind each one is.

    Why it matters for analysts

    In the example below, one order of 12,500 plus two large B2B orders push the average order value of forty orders to 519, while the median stays at 97. Report that mean and the business thinks customers spend five times what they do. Delete the B2B orders by reflex and you hide your most valuable segment.

    Two standard rules

    The IQR rule flags values more than \(k\) interquartile ranges beyond the middle half of the data. It uses quartiles, so the outliers themselves barely move the fences. The z-score rule flags values many standard deviations from the mean. It is simple but fragile, because a huge outlier inflates the standard deviation and hides itself and its neighbours.

    \[ \text{fences} = \big[\,Q_1 - k\cdot\text{IQR},\;\; Q_3 + k\cdot\text{IQR}\,\big], \qquad \text{IQR} = Q_3 - Q_1, \qquad z_i = \frac{x_i - \bar{x}}{s} \] Tukey's convention is \(k = 1.5\) for "outlier" and \(k = 3\) for "far out". A common z-score cut-off is \(|z| > 3\). 
    amt = orders["amount"]
q1, q3 = amt.quantile([0.25, 0.75])
iqr = q3 - q1
lo, hi = q1 - 3 * iqr, q3 + 3 * iqr           # k = 3: "far out" only

orders["amount_outlier"] = ~amt.between(lo, hi)
print(orders.loc[orders["amount_outlier"], ["order_id", "customer_id", "amount"]])

# robust summary that outliers barely move
print(amt.median(), amt.clip(lower=lo, upper=hi).mean())   # capped (winsorized) mean
    WITH q AS (
  SELECT PERCENTILE_CONT(0.25) WITHIN GROUP (ORDER BY amount) AS q1,
         PERCENTILE_CONT(0.75) WITHIN GROUP (ORDER BY amount) AS q3
  FROM orders
)
SELECT o.order_id, o.amount
FROM orders o CROSS JOIN q
WHERE o.amount > q.q3 + 3 * (q.q3 - q.q1)
   OR o.amount < q.q1 - 3 * (q.q3 - q.q1);

    Switch the rule, watch what gets caught

    The 40 orders below include a suspected cents bug (12,500) and two genuine B2B orders. Try each rule and threshold. Notice that the z-score rule struggles: the 12,500 order inflates the standard deviation so much that the B2B orders look normal.

    Decide what each outlier is

    Investigate every flagged value before acting. Look at the raw row, the customer and the source system. The decision then follows from what you found, not from the rule.

    Key ideas
    • Outliers are either errors to fix or real extremes to keep; a rule cannot tell which.
    • IQR fences use quartiles, so they are robust; z-scores use the mean and standard deviation, which outliers distort.
    • Capping (winsorizing) limits influence without deleting rows, but changes the data, so say so.
    • Report the median or a segment split when a few large values dominate the mean.
    Common mistakes
    • Dropping every value beyond 1.5 × IQR on skewed data such as revenue, which removes your best customers.
    • Trusting |z| > 3 when one giant value has inflated the standard deviation (masking).
    • Removing outliers until the result looks the way you expected.
    • Silently capping values in a table that others will use for totals.

    05.4 · Make the computer agree

    Types, dates & parsing

    A CSV is just text. Until you parse each column into a real type (number, date, boolean, category), sums fail, sorts go alphabetical and dates compare as strings. Dates are the hardest: the same characters can mean two different days, and the same moment falls on different days in different time zones.

    Why it matters for analysts

    Daily revenue, signups per week and "orders on Black Friday" all depend on which day a timestamp belongs to. Parse 03/04/2026 the wrong way and March becomes April. Ignore time zones and your daily totals disagree with finance's by every late-evening order.

    One string, two dates

    US systems usually write month first (MM/DD/YYYY); most of the rest of the world writes day first. For the first 12 days of every month both readings are valid, so a parser that guesses will not raise an error. Tell it the format explicitly, and store results in ISO 8601 (YYYY-MM-DD), which has only one reading.

    Time zones move orders between days

    A timestamp without a zone is a guess. Store event times in UTC, keep the source zone, and convert only when you report. Then decide, and write down, which zone defines "a day" for each report.

    # explicit format: never let the parser guess
orders["ordered_at"] = (
    pd.to_datetime(orders["ordered_at_raw"], format="%m/%d/%Y %H:%M", errors="coerce")
      .dt.tz_localize("America/New_York")      # the zone the CRM wrote in
      .dt.tz_convert("UTC"))                    # store in UTC
print(orders["ordered_at"].isna().sum(), "rows failed to parse")

# "$1,299.00" and "N/A" to numbers; failures become NaN you can count
orders["amount"] = pd.to_numeric(
    orders["amount_raw"].str.replace(r"[$,]", "", regex=True), errors="coerce")
orders["zip"] = orders["zip"].astype("string")  # keep leading zeros: "02139"
    -- PostgreSQL: parse text, attach the source zone, report by New York day
SET TIME ZONE 'UTC';   -- so the ::timestamp cast keeps the wall-clock text
SELECT (TO_TIMESTAMP(ordered_at_raw, 'MM/DD/YYYY HH24:MI')::timestamp
          AT TIME ZONE 'America/New_York')            AS ordered_at_utc,
       ((TO_TIMESTAMP(ordered_at_raw, 'MM/DD/YYYY HH24:MI')::timestamp
          AT TIME ZONE 'America/New_York')
          AT TIME ZONE 'America/New_York')::date      AS ny_day
FROM raw_orders;

    Key ideas
    • Parse every column into an explicit type and count the values that failed.
    • Give date parsers the exact format; ambiguous dates parse wrongly without an error.
    • Store timestamps in UTC with the source zone known; convert only for reporting.
    • Decide which zone defines "a day" for each report and write it on the chart.
    • Keep IDs, ZIP codes and phone numbers as text.

    • Using errors="coerce" and never checking how many values became NaN or NaT.
    • Treating naive timestamps from different systems as if they share a zone.
    • Applying a fixed offset across a daylight-saving change instead of a named zone like America/New_York.
    • Sorting dates stored as DD/MM/YYYY text, which sorts by day number.

    05.5 · Same thing, many spellings

    Cleaning text & categories

    Free-text fields collect every variation people can type: New York, new york, NYC, N.Y. and New York with stray spaces. To a GROUP BY those are five different cities. Cleaning text means mapping every variant to one canonical value with rules you can review.

    Why it matters for analysts

    Split categories change rankings. In the example below, the raw data says Los Angeles is the top city; after cleaning, New York has 76 customers against Los Angeles' 56. Any "top regions" slide built on raw text would have been wrong.

    A pipeline of small, ordered steps

    Apply cheap, safe steps first: trim spaces, lowercase, strip punctuation. Only then look values up in an alias map, a reviewed table from variant to canonical value. Order matters: an alias map keyed on nyc never matches NYC unless you lowercased first.

    ALIASES = {"ny": "new york", "nyc": "new york",
           "la": "los angeles", "sf": "san francisco"}

city = (df["city"].str.strip()
                  .str.lower()
                  .str.replace(r"[^\w\s]", "", regex=True)   # drop . , - etc.
                  .str.replace(r"\s+", " ", regex=True))     # collapse inner spaces
df["city_clean"] = city.replace(ALIASES).str.title()

# what is still unmapped? review the long tail by hand
print(df["city_clean"].value_counts().tail(20))
    -- a reviewed mapping table beats a 200-line CASE statement
SELECT COALESCE(m.canonical, INITCAP(c.city_norm)) AS city,
       COUNT(*)                                     AS customers
FROM (SELECT LOWER(TRIM(REGEXP_REPLACE(city, '[^A-Za-z ]', '', 'g'))) AS city_norm
      FROM crm_customers) c
LEFT JOIN city_aliases m ON m.variant = c.city_norm
GROUP BY 1
ORDER BY customers DESC;

    Normalize a city column

    Here are 188 customers whose city was typed by hand. Turn the steps on one at a time and watch the categories merge. The fuzzy-match slider merges near-identical spellings such as typos. Push it too far and it merges Newark, a different city, into New York.

    Cleaning can change the answer

    Key ideas
    • Run cheap, safe steps first (trim, lowercase, punctuation), then the alias map.
    • Keep the alias map as reviewed data, and report how many rows it changed.
    • Fuzzy matching catches typos but can merge distinct values; always review its merges.
    • Keep the raw column next to the clean one so anyone can audit the mapping.
    Common mistakes
    • Applying the alias map before lowercasing, so half the variants never match.
    • Setting a loose fuzzy threshold that merges different entities (Newark into New York, Austria into Australia).
    • Overwriting the raw column, which makes mistakes impossible to undo.
    • Fixing variants by hand in a spreadsheet, so next month's export needs the same work again.
    In practice

    In spreadsheets, =PROPER(TRIM(SUBSTITUTE(A2,".",""))) handles the safe steps, and an XLOOKUP against an alias tab handles the rest. OpenRefine's clustering feature is a good way to discover variants in a new column.

    05.6 · Trust, but verify

    Data quality checks

    Cleaning once is not enough, because next week's export will bring new problems. Data quality checks are small automated tests that run every time the data loads. Each one states a rule the table must obey ("order_id is unique", "shipped after ordered") and returns the rows that break it.

    Why it matters for analysts

    Stakeholders lose trust after one wrong number, and they rarely forgive it quickly. A check that fails before the dashboard refreshes turns "why is revenue doubled?" in a leadership meeting into a quiet alert you fix on Tuesday morning.

    Six kinds of check

    Most useful checks fall into six families. Start with uniqueness and not-null on keys, because they catch the most damaging problems for the least effort, then add rules that encode business logic.

    -- Each check returns the failing rows. Zero rows = pass.
-- validity, with a business exception for refunds
SELECT order_id, amount, status
FROM orders
WHERE amount < 0 AND status <> 'refunded';

-- consistency between two columns
SELECT order_id, ordered_at, shipped_at
FROM orders
WHERE shipped_at < ordered_at;          -- NULL shipped_at is not a failure
    # dbt: the same rules as declarative tests (models/schema.yml)
models:
  - name: orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: customer_id
        data_tests:
          - not_null
          - relationships: {to: ref('customers'), field: customer_id}
      - name: status
        data_tests:
          - accepted_values: {values: ['paid', 'shipped', 'refunded', 'cancelled']}

    Run a checklist on a table

    This 11-row orders table hides five planted problems across six rows. Row 9 is a legitimate refund with a negative amount. Turn checks on and off. A good set of checks catches every bad row and raises no false alarms.

    Data-quality checklist runner Try it

    Checks as a gate

    Run checks between loading and publishing. Errors block the publish and move failing rows to a quarantine table; warnings publish but alert the owner. Either way, someone named gets told.

    Key ideas
    • A check is a rule plus a query that returns the rows breaking it; zero rows means pass.
    • Start with unique and not-null on keys, then add validity, consistency, freshness and volume.
    • Encode real business exceptions (refunds) so checks do not cry wolf.
    • Run checks before publishing, quarantine failures and alert a named owner.
    Common mistakes
    • Writing checks so strict that they fail every day, until everyone ignores the alerts.
    • Checking only the final dashboard numbers, which tells you something is wrong but not where.
    • Deleting failing rows instead of quarantining them, which loses the evidence.
    • Never adding a check after an incident, so the same bug returns.
