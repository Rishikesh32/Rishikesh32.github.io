Data engineering for analysts

Every dashboard and analysis sits on plumbing: a warehouse, pipelines that copy data into it, SQL models that clean it, a scheduler that runs it every morning and tests that stop bad numbers from shipping. You don't need to become a data engineer, but you do need to read, change and debug that plumbing yourself.

In this area

    Follow one order from the moment a customer clicks "Buy" to the revenue chart on Monday's dashboard. A pipeline extracts it from the app database and loads it into a warehouse. SQL models in dbt clean it and shape it into fact and dimension tables. An orchestrator runs the whole chain before the working day starts, and tests at each layer stop broken data before anyone sees it. The six lessons below take each stage in turn.

    14.1 · Where analytics data lives

    Data warehouses

    Your app's database is tuned to read and write one order at a time, thousands of times a second. Analysis does the opposite: it reads millions of orders at once to answer "revenue by month". A data warehouse is a database built for that second job. It stores data by column, splits big tables into partitions and charges you for the data your queries touch.

    Why it matters for data analysts

    Almost every analyst query runs in a warehouse such as Snowflake, BigQuery, Redshift or Databricks. How you write the query decides whether it reads 200 MB or 700 GB, which is the difference between a 2-second answer and a costly, slow one. Running heavy queries on the production app database can also slow the app down for customers.

    OLTP versus OLAP

    The app database is an OLTP system (online transaction processing): short queries such as UPDATE orders SET status = 'paid' WHERE order_id = 1042. The warehouse is an OLAP system (online analytical processing): long scans such as SUM(amount) GROUP BY month. The biggest design difference is how rows sit on disk.

    Columnar storage and compression

    Because one column holds values of one type, often repeated, it compresses well: a status column with five distinct values shrinks to a fraction of a byte per row. So a columnar scan reads only the columns you name, and those columns are small. SELECT * throws that advantage away.

    What does your query scan? Try it

    The example table holds two years of orders at 2 million rows a day (1.46 billion rows). Column widths and compression ratios are illustrative. Try the query "revenue per day for the last 30 days": it only needs order_date and amount.

    Partitions and clustering

    A partition splits a table into separate chunks by a column, usually a date. When your WHERE clause filters on that column, the engine skips every partition that cannot match. This is called partition pruning. Clustering (or sort keys) orders rows inside each partition so the engine can also skip blocks whose min and max values rule them out.

    -- BigQuery syntax: partition by day, cluster by customer inside each day
CREATE TABLE analytics.orders
PARTITION BY DATE(created_at)
CLUSTER BY customer_id AS
SELECT * FROM raw.orders;

-- Good: names two columns and filters on the partition column
SELECT DATE(created_at) AS order_date, SUM(amount) AS revenue
FROM analytics.orders
WHERE created_at >= TIMESTAMP_SUB(CURRENT_TIMESTAMP(), INTERVAL 30 DAY)
GROUP BY order_date;

-- Costly: every column, every partition. LIMIT does not reduce the scan.
SELECT * FROM analytics.orders LIMIT 10;

    Storage and compute are separate

    Modern cloud warehouses keep data in cheap object storage and spin up compute only while queries run. You pay for storage and for compute (or bytes scanned), so the cost of a query depends on how much it reads, not on how many rows it returns.

    EngineHow you pay for queriesHow it skips data
    SnowflakeCompute time of a "virtual warehouse" (credits)Automatic micro-partitions, optional clustering keys
    BigQueryBytes scanned (on-demand) or reserved capacityPartitioned and clustered tables
    RedshiftProvisioned nodes or serverless computeSort keys and zone maps
    Databricks SQLCompute time of a SQL warehouseDelta tables: partitions, data skipping, clustering
    PostgreSQLYour own serverIndexes; row store, fine up to modest sizes
    Key ideas
    • OLTP databases serve the app one row at a time; OLAP warehouses scan many rows for analysis.
    • Columnar storage reads only the columns a query names, and those columns compress well.
    • Partition pruning skips whole chunks when you filter on the partition column.
    • Query cost follows bytes read or compute time, not rows returned.
    Common mistakes
    • Running SELECT * "just to look" at a billion-row table, then adding LIMIT and expecting a cheap query.
    • Wrapping the partition column in a function the engine can't prune on, or filtering on a different date column.
    • Pointing heavy reports at the production app database instead of the warehouse or a read replica.

    14.2 · Moving the data

    ETL & ELT pipelines

    A pipeline copies data from where it is created (the app database, a payments provider, a CRM) to where you analyse it. It does three things: extract the data, load it into the warehouse and transform it into clean tables. The order of the last two letters is the big design choice.

    Why it matters for data analysts

    When a number looks wrong, the cause is often in the pipeline: a load that ran twice, a late update that was never picked up, or business logic buried in an extraction script nobody can read. With ELT, most of that logic becomes SQL in the warehouse, which you can read and change yourself.

    ETL versus ELT

    ETL transforms data on the way in, so the warehouse only ever sees finished tables. ELT loads a raw, untouched copy first and transforms it later with SQL inside the warehouse. Cheap cloud storage and fast warehouses made ELT the default for analytics, because the raw copy lets you rebuild any table without going back to the source.

    Design the nightly load Try it

    The example orders table has 18 million rows. Each night about 140,000 rows are new or changed, and a few thousand updates arrive late, committed after the previous load had already read past them. Lookback only applies to incremental loads.

    Full versus incremental extraction

    A full load copies the whole table every night: simple, always correct, and slow once tables grow. An incremental load copies only rows changed since the last run, using a high-water mark such as the largest updated_at already loaded. Re-reading a few days behind the mark (a lookback window) catches rows that were committed late. Change data capture (CDC) tools read the database's change log instead and see every insert, update and delete.

    # Incremental extract with a lookback window (pandas + SQLAlchemy)
import pandas as pd
from sqlalchemy import create_engine, text

src = create_engine("postgresql://readonly@app-replica/shop")   # read replica, not the primary
wh = create_engine("postgresql://loader@warehouse/analytics")

with wh.connect() as c:
    mark = c.execute(text("SELECT max(updated_at) FROM raw.orders")).scalar()

since = mark - pd.Timedelta(days=3)                               # lookback for late commits
changes = pd.read_sql(text("SELECT * FROM orders WHERE updated_at > :since"),
                      src, params={"since": since})
changes["_loaded_at"] = pd.Timestamp.now(tz="UTC")
changes.to_sql("orders_changes", wh, schema="raw", if_exists="replace", index=False)

    Make every load idempotent

    A load is idempotent when running it twice gives the same result as running it once. Pipelines get retried and re-run all the time, so an INSERT that appends the same rows again will quietly double your revenue. Upsert by the primary key with MERGE, or delete and replace the whole date range you are reloading.

    -- Upsert the night's changes: safe to run twice
MERGE INTO raw.orders AS t
USING raw.orders_changes AS s
  ON t.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET
  status = s.status, amount = s.amount, updated_at = s.updated_at, _loaded_at = s._loaded_at
WHEN NOT MATCHED THEN INSERT (order_id, customer_id, status, amount, updated_at, _loaded_at)
  VALUES (s.order_id, s.customer_id, s.status, s.amount, s.updated_at, s._loaded_at);
    Extraction patternHow it finds new dataGood forWatch out for
    Full copyReads the whole tableSmall tables, lookupsRuntime and source load grow with the table
    Incremental by timestampupdated_at > high-water markLarge tables with a reliable updated_atLate commits, hard deletes are invisible
    Change data captureReads the database change logLarge, busy tables; deletes matterMore setup, needs log access
    SaaS connectorVendor API, managed by an EL toolStripe, CRM, ad platformsAPI limits, schema changes upstream
    Key ideas
    • ELT loads a raw copy first and transforms it in the warehouse with SQL; ETL transforms before loading.
    • Keeping raw data lets you rebuild any table when business logic changes.
    • Incremental loads use a high-water mark; a lookback window catches late-arriving rows.
    • Every load should be idempotent: upsert by key or replace whole partitions.
    Common mistakes
    • Appending with plain INSERT, so a retried job duplicates rows.
    • Trusting updated_at without checking that every code path in the app actually sets it.
    • Forgetting hard deletes: a timestamp-based incremental load never sees rows that were removed.
    • Extracting from the primary app database at peak hours instead of a replica.

    14.3 · Shaping tables for questions

    Dimensional modeling

    App tables are shaped for the app: dozens of small, normalized tables joined in complicated ways. Dimensional modeling, popularized by Ralph Kimball, reshapes them for questions. Business events go into fact tables (one row per order line, with amounts you can add up) and the context you slice by goes into dimension tables (customer, product, date). Drawn out, it looks like a star.

    Why it matters for data analysts

    A good star schema makes most questions a single join and a GROUP BY, and BI tools such as Power BI and Looker expect it. Knowing a table's grain stops you from double counting, and knowing how a dimension tracks history tells you whether last year's revenue by region will change when a customer moves.

    Facts, dimensions and grain

    Start by declaring the grain: exactly what one row of the fact table means. "One row per order line" is a grain; "orders and some returns" is not. The fact holds numeric measures and foreign keys. Each dimension holds descriptive attributes and a surrogate key, a warehouse-generated id that stays stable even if the source id changes.

    -- One fact, three dimensions, one GROUP BY
SELECT d.month, p.category, SUM(f.amount) AS revenue
FROM fct_orders AS f
JOIN dim_date    AS d ON f.date_key   = d.date_key
JOIN dim_product AS p ON f.product_sk = p.product_sk
JOIN dim_channel AS c ON f.channel_key = c.channel_key
WHERE c.channel = 'app'
GROUP BY d.month, p.category
ORDER BY d.month, revenue DESC;

    Three kinds of fact table

    Fact typeOne row perExampleTypical measures
    TransactionEventfct_orders: each order lineamount, quantity
    Periodic snapshotEntity per periodfct_subscriptions_daily: each subscription each dayMRR, seats (not additive over time)
    Accumulating snapshotProcess instance, updated as it movesfct_order_fulfilment: ordered, packed, shipped datesdays between milestones

    Slowly changing dimensions

    Dimension attributes change: customers move, products change category. A slowly changing dimension (SCD) policy says what happens. Type 1 overwrites the old value, so history is restated with today's attributes. Type 2 closes the old row and adds a new one with its own surrogate key and validity dates, so each fact keeps the attributes that were true when it happened. (Type 0 never changes the value; Type 3 keeps a "previous value" column.)

    Step through a customer move Try it

    Two customers in Leeds place orders, then Ana moves to Bristol and orders again. Watch what the "revenue by city" report says about January under each policy.

    -- Type 2: the fact stored the surrogate key that was current at load time
SELECT c.city, SUM(f.amount) AS revenue
FROM fct_orders f
JOIN dim_customer c ON f.customer_sk = c.customer_sk      -- historical city
GROUP BY c.city;

-- Same dimension, but report everyone by where they live today
SELECT cur.city, SUM(f.amount) AS revenue
FROM fct_orders f
JOIN dim_customer hist ON f.customer_sk = hist.customer_sk
JOIN dim_customer cur  ON cur.customer_id = hist.customer_id AND cur.is_current
GROUP BY cur.city;
    Key ideas
    • Declare the grain of every fact table before choosing its columns.
    • Facts hold additive measures and keys; dimensions hold descriptive attributes.
    • Surrogate keys decouple the warehouse from source ids and make Type 2 history possible.
    • Type 1 restates history with current values; Type 2 preserves the values at the time of each fact.
    Common mistakes
    • Mixing grains in one fact table, such as order headers and order lines, then summing and double counting.
    • Joining a Type 2 dimension on the natural customer_id alone, which multiplies every fact by the number of versions.
    • Summing a periodic snapshot measure (such as account balance) across days.

    14.4 · Transformations as code

    dbt & analytics engineering

    dbt (data build tool) turns the "T" of ELT into a software project. Each table is a .sql file containing one SELECT. dbt wraps it in the right CREATE TABLE or CREATE VIEW, works out the build order from the ref() calls between files, runs tests and generates documentation. Analytics engineering is the job of building these models with software habits: version control, code review and automated tests.

    Why it matters for data analysts

    dbt is plain SQL, so it is often the first piece of the data stack an analyst owns. Moving a metric definition out of twenty dashboards and into one tested dbt model is how a team stops arguing about whose revenue number is right.

    A model is a SELECT

    A staging model reads a raw table through source(), renames and casts columns, and does nothing else. Later models read earlier ones through ref(). The config() block sets how the result is stored.

    -- models/staging/stg_orders.sql
select
    id                         as order_id,
    user_id                    as customer_id,
    lower(trim(status))        as status,
    amount_cents / 100.0       as amount,
    created_at::date           as order_date,
    updated_at
from {{ source('app', 'orders') }}

-- models/marts/fct_orders.sql
{{ config(materialized='incremental', unique_key='order_id') }}

select o.order_id, o.customer_id, o.order_date, o.status, p.amount_paid
from {{ ref('stg_orders') }} as o
left join {{ ref('int_order_payments') }} as p using (order_id)
{% if is_incremental() %}
  -- only rows changed since the last build, with a 3-day lookback
  where o.updated_at > (select max(updated_at) - interval '3 days' from {{ this }})
{% endif %}

    ref() builds the DAG

    When dbt compiles a model, ref('stg_orders') becomes the real table name for the current environment (your dev schema or production). It also records an edge in a DAG (directed acyclic graph) of models. That graph is how dbt knows to build stg_orders before fct_orders, and it is the lineage graph in the generated docs.

    Layers: staging, intermediate, marts

    Most dbt projects follow three layers. Staging models map one-to-one to source tables and only clean them. Intermediate models combine and reshape. Marts are the facts and dimensions that BI tools and analysts query.

    Change a model: what rebuilds? Try it

    Click any model in the graph (or pick it from the list). The + after a name selects everything downstream, and a + before it selects everything upstream. Build times are illustrative.

    Materializations

    MaterializationWhat dbt createsUse for
    viewA view; the query runs whenever someone reads itStaging models, light logic
    tableA table rebuilt in full on every runMarts that are read often
    incrementalA table where each run only inserts or merges new rowsLarge event and order facts
    ephemeralNothing; the SQL is inlined as a CTE where it's referencedSmall reusable steps

    The analytics engineering workflow

    You develop in your own schema, open a pull request, and continuous integration builds only the models you changed plus everything downstream. Production runs the whole project on a schedule.

    dbt build --select stg_orders              # build and test one model
dbt build --select stg_orders+             # ...and everything downstream of it
dbt build --select +fct_orders             # fct_orders and everything it depends on
dbt build --select state:modified+ --state prod-artifacts/   # CI: only what this PR changed
dbt source freshness                       # are the raw tables up to date?
dbt docs generate && dbt docs serve        # browse docs and the lineage graph
    Key ideas
    • A dbt model is a SELECT statement; dbt handles the DDL, the order and the environment.
    • ref() and source() resolve table names and build the DAG at the same time.
    • Staging cleans, intermediate combines, marts serve BI.
    • Graph selectors such as model+ rebuild exactly the affected part of the project.
    Common mistakes
    • Hard-coding analytics.prod.stg_orders instead of using ref(), which breaks lineage and dev environments.
    • Putting business logic in staging models, so the same rule is repeated in several marts.
    • Changing a model and building only that model, leaving downstream tables stale.
    • Making a large fact incremental without a unique_key or lookback, so updates duplicate or go missing.

    14.5 · Running it every morning

    Scheduling & orchestration

    A pipeline is several steps that must run in order: extract three sources, build the dbt models, refresh the dashboard. An orchestrator such as Airflow, Dagster or Prefect runs those steps on a schedule, starts each one only when the steps it depends on have succeeded, retries failures and alerts someone when it gives up.

    Why it matters for data analysts

    When the 9 a.m. dashboard shows yesterday's numbers, the answer is in the orchestrator: which task failed, whether it retried, and what was skipped because of it. Reading a run, re-running a task and asking for a backfill are everyday analyst skills.

    From cron times to dependencies

    The simplest schedule is a set of cron jobs at fixed times: extract at 05:00, dbt at 06:00, dashboard at 06:30. It works until the extract runs long one morning and dbt starts on half-loaded data. An orchestrator replaces guessed start times with explicit dependencies, a DAG of tasks.

    # Airflow 2.x style; Airflow 3 moves these imports to airflow.sdk and the standard provider
from datetime import datetime, timedelta
from airflow import DAG
from airflow.operators.bash import BashOperator

with DAG(
    dag_id="morning_analytics",
    schedule="0 5 * * *",                  # 05:00 every day
    start_date=datetime(2026, 1, 1),
    catchup=False,
    default_args={"retries": 2, "retry_delay": timedelta(minutes=10)},
) as dag:
    extract = [BashOperator(task_id=f"extract_{s}",
                            bash_command=f"python extract.py {s} {{{{ ds }}}}")
               for s in ("orders", "payments", "crm")]
    dbt_build = BashOperator(task_id="dbt_build", bash_command="dbt build --target prod")
    refresh = BashOperator(task_id="refresh_dashboard", bash_command="python refresh_bi.py")

    extract >> dbt_build >> refresh          # all extracts, then dbt, then the dashboard

    Task states, retries and alerts

    Every task run moves through states. A failure with retries left waits retry_delay and runs again, which fixes transient problems such as a timeout. A persistent problem, such as a renamed column, fails every attempt. When a task finally fails, its downstream tasks are marked upstream_failed and never run, which is exactly what you want: no partial data reaches the dashboard.

    Simulate this morning's run Try it

    The run starts at 05:00 and the sales team opens the dashboard at 07:00. A payments timeout lasts the full 15-minute task, and each retry waits the retry delay first. Durations are illustrative.

    Backfills and idempotent tasks

    Each run processes a logical date (Airflow's {{ ds }}), not "whatever time it is now". That lets you backfill: re-run last Tuesday after fixing a bug and get exactly Tuesday's data. It only works if each task is idempotent, as in 14.2: running it twice for the same date replaces that date's data instead of appending.

    OptionWhat it isFits when
    cronFixed start times on one machineOne or two independent scripts
    AirflowPython DAGs of tasks, large ecosystem of operatorsMany sources and teams, existing data platform
    DagsterOrchestrates data assets (tables) rather than tasksdbt-heavy projects that want lineage and asset checks
    PrefectPython functions turned into flowsPython-first teams wanting light setup
    dbt platform jobsScheduled dbt build runsLoading is handled by a managed EL tool
    Key ideas
    • Orchestrators run tasks by dependency, not by guessed clock times.
    • Retries fix transient failures; persistent failures need a code or data fix.
    • A failed task blocks its downstream tasks (upstream_failed), so bad data does not spread.
    • Runs process a logical date, which makes idempotent backfills possible.
    Common mistakes
    • Chaining jobs by start time ("dbt at 06:00 should be late enough").
    • Setting many retries with long delays, so a real failure is discovered after the deadline.
    • Using now() inside tasks instead of the run's logical date, which breaks backfills.
    • No alert on failure, so the first person to notice is the stakeholder.

    14.6 · Trusting the numbers

    Data quality & testing

    Code tests check that logic is right. Data tests check that the data itself is right, every time it loads: no duplicate order ids, no orders without a customer, only known status values, and a load that actually happened today. Each test is a query that looks for bad rows. Zero rows means pass.

    Why it matters for data analysts

    Trust in a dashboard takes months to build and one wrong number to lose. A failed test at 05:30 that you fix before anyone looks is far cheaper than a sales director spotting doubled revenue in a meeting. Tests also document what "correct" means for each table.

    Four tests that catch most problems

    Most real incidents are caught by a handful of generic tests. unique and not_null on primary keys catch duplicate loads and broken joins. accepted_values catches typos and new categories the app introduced without telling you. freshness catches the silent killer: a load that stopped, leaving yesterday's data on display.

    # models/staging/_stg_app.yml  (dbt 1.8+ uses data_tests; older versions use tests)
sources:
  - name: app
    schema: raw
    loaded_at_field: _loaded_at
    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: orders

models:
  - name: stg_orders
    columns:
      - name: order_id
        data_tests: [unique, not_null]
      - name: customer_id
        data_tests:
          - not_null
          - relationships:
              to: ref('stg_customers')
              field: customer_id
      - name: status
        data_tests:
          - accepted_values:
              values: ['pending', 'paid', 'shipped', 'refunded']
              config:
                severity: warn          # alert, but don't stop the run
    Run the tests on tonight's load Try it
    Problems in the load:
    Severity:

    Untick a problem to "fix" it upstream, or change a test's severity. A failing test with severity error stops the build, so the dashboard keeps yesterday's good data. A failing warn test lets the build publish and posts an alert.

    Where to test, and what a failure does

    Test at every layer, but test different things. Check freshness on sources before spending compute on stale data. Check keys and accepted values in staging, where problems are closest to their cause. Check relationships and business rules (row counts, revenue within a sane range) in marts. Choose a severity per test: error for anything that would make a number wrong, warn for things a human should look at.

    -- Roughly what dbt runs for the unique test on stg_orders.order_id.
-- The test passes when this returns zero rows.
select order_id, count(*) as n_records
from analytics.stg_orders
where order_id is not null
group by order_id
having count(*) > 1;

    Dimensions of data quality

    DimensionQuestionExample test
    CompletenessIs anything missing?not_null, row count vs yesterday
    UniquenessIs anything counted twice?unique on the grain
    ValidityAre values allowed?accepted_values, amount >= 0
    ConsistencyDo tables agree?relationships, mart total equals source total
    TimelinessIs it up to date?source freshness
    Key ideas
    • A data test is a query for bad rows; zero rows means pass.
    • unique, not_null, accepted_values, relationships and freshness catch most incidents.
    • Test each layer for the problems that start there.
    • Severity decides what a failure does: error blocks, warn alerts.
    Common mistakes
    • Testing only the final mart, so you learn something broke but not where.
    • Setting everything to warn until the alert channel is noise nobody reads.
    • No freshness check, so a stopped load shows stale data that passes every other test.
    • Fixing a failing test by deleting it instead of fixing the data or the logic.
