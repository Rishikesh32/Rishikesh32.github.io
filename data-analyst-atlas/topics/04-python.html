Python for data

Python with pandas is the analyst's workbench for anything too big, too messy or too repetitive for a spreadsheet. You will go from core Python and NumPy to DataFrames, joins and reshapes, then learn to keep notebooks honest and turn one-off cells into analysis code you can rerun every week.

In this area

    Every analysis in Python follows the same path. Raw files come in, you load them into a pandas DataFrame (which sits on top of NumPy arrays and plain Python), you clean, join and reshape them into the table the question needs, and you hand back a number, a chart or a report. Notebooks are where you explore that path; functions and modules are how you make it repeatable. The six lessons follow the path from the inside out.

    04.1 · The language underneath

    Python essentials

    You don't need all of Python to analyse data. You need values and their types, two containers (the list, an ordered sequence, and the dict, a set of key-value pairs), loops, comprehensions and small functions. Almost every pandas line you write later is these pieces in disguise.

    Why it matters for analysts

    API responses arrive as lists of dicts, config lives in dicts, and file names come in lists. When a pandas call fails, the error message talks about these basic types. Knowing them lets you read the traceback instead of guessing.

    Records: a list of dicts

    A natural way to hold a few orders in plain Python is a list where each item is a dict. You reach an order by its position (starting at 0) and a field by its key. This "list of records" shape is exactly what pd.DataFrame(records) turns into a table.

    Each value has a type, and the type decides what operations make sense. The classic analyst bug is a number stored as text: "42" + "8" gives "428", not 50.

    TypeExampleAnalyst useWatch out for
    int, float3, 42.5Counts, amounts0.1 + 0.2 is 0.30000000000000004
    str"paid"Categories, ids, namesNumbers read as text
    boolTrueFlags, filtersTrue counts as 1 in a sum
    list[42, 18.5]Ordered items, file listsMutable: changes are shared
    dict{"Ana": 42}Lookups, records, configKeys must be unique
    NoneNoneMissing valueBecomes NaN in pandas

    Loops and comprehensions

    A comprehension builds a new list or dict from an existing one in a single expression. It reads left to right as "give me this, for each item, if a condition holds". It does the same work as a loop with append, in one line.

    Step through the six orders below. Switch to a dict comprehension keyed by customer and watch what happens when Ana appears twice.

    Comprehension stepper Try it

    Functions wrap a few lines you use more than once, with a name and parameters. f-strings format numbers for output: f"{x:,.2f}" prints 1234.5 as 1,234.50.

    orders = [
    {"id": 101, "customer": "Ana", "amount": 42.0,  "status": "paid"},
    {"id": 102, "customer": "Ben", "amount": 18.5,  "status": "refunded"},
    {"id": 103, "customer": "Ana", "amount": 75.0,  "status": "paid"},
]

# list comprehension: amounts of paid orders
paid = [o["amount"] for o in orders if o["status"] == "paid"]      # [42.0, 75.0]

# dict comprehension: duplicate keys keep the LAST value
last_by_customer = {o["customer"]: o["amount"] for o in orders}     # {'Ana': 75.0, 'Ben': 18.5}

# to total per customer, accumulate instead
totals = {}
for o in orders:
    totals[o["customer"]] = totals.get(o["customer"], 0) + o["amount"]

def with_vat(amount, rate=0.20):
    """Return amount including VAT, rounded to cents."""
    return round(amount * (1 + rate), 2)

print(f"Paid revenue: {sum(paid):,.2f}")                            # Paid revenue: 117.00
    Key ideas
    • A list is ordered and indexed from 0; a dict maps unique keys to values.
    • A list of dicts is a table: one dict per row, one key per column.
    • A comprehension is expression, loop and optional filter in one line.
    • In a dict comprehension, a repeated key silently overwrites the earlier value.
    • Types matter: text that looks like a number does not add like one.
    Common mistakes
    • Off-by-one indexing: orders[1] is the second order, not the first.
    • Building a dict keyed by a non-unique field and losing rows without any error.
    • Using a mutable default such as def f(rows=[]); the same list is reused across calls.
    • Writing loops over millions of rows in plain Python when pandas or NumPy can do it in one vectorized call.

    04.2 · Fast arrays

    NumPy

    NumPy gives Python one new object, the ndarray: a grid of numbers that all share one type, stored side by side in memory. Because of that, one line like prices * units multiplies a million pairs in compiled code, with no Python loop in sight. pandas columns are NumPy arrays underneath.

    Why it matters for analysts

    Every fast pandas operation is a NumPy operation. Knowing arrays, axes and broadcasting explains why df["amount"] * 1.2 is instant, why .apply with a Python function is slow, and what "shapes (3,4) (3,)" means in an error.

    Why arrays are fast

    A Python list stores pointers to separate number objects scattered in memory, and a loop handles them one at a time. An array stores raw 8-byte numbers in one block, so a single compiled loop can sweep through it. Applying one operation to the whole array at once is called vectorization.

    Axes and broadcasting

    A 2-D array has axis 0 (down the rows) and axis 1 (across the columns). units.sum(axis=0) collapses the rows and gives one total per column. Broadcasting lets arrays of different shapes combine: NumPy lines the shapes up from the right, and each pair of sizes must be equal or 1. A size-1 dimension is stretched to match, without copying data.

    Pick two shapes and see whether they broadcast. A is units sold per store and quarter; B is a multiplier such as price per quarter or a per-store adjustment.

    Broadcasting shapes Try it
    A * B

    In real code you rarely write loops over arrays. You use vectorized arithmetic, reductions along an axis, boolean masks to filter, and np.where for if-else on every element.

    import numpy as np

units = np.array([[12, 15, 11, 18],      # store A, quarters 1-4
                  [ 8,  9, 10,  7],      # store B
                  [20, 22, 19, 25]])     # store C
price = np.array([2.0, 3.0, 2.0, 4.0])   # one price per quarter, shape (4,)

revenue = units * price                  # (3, 4) * (4,) broadcasts to (3, 4)
revenue.sum(axis=1)                      # per store:   [163.  91. 244.]
revenue.sum(axis=0)                      # per quarter: [ 80. 138.  80. 200.]

uplift = np.array([1.0, 1.1, 0.9])       # one factor per store, shape (3,)
adjusted = revenue * uplift[:, None]     # reshape to (3, 1) first, or you get an error

big = revenue[revenue > 50]              # boolean mask keeps matching cells (1-D result)
flag = np.where(revenue > 50, "high", "low")
centered = units - units.mean(axis=0)    # subtract each column's mean: (3, 4) - (4,)
    Key ideas
    • An ndarray is one type, one contiguous block, any number of dimensions.
    • Vectorized operations run in compiled code; Python loops over elements are slow.
    • axis=0 collapses rows (one result per column); axis=1 collapses columns.
    • Broadcasting right-aligns shapes; sizes must match or be 1.
    • Use [:, None] or .reshape(-1, 1) to turn a vector into a column.
    Common mistakes
    • Mixing up axes: sum(axis=0) gives column totals, not row totals.
    • Expecting a length-3 vector to line up with 3 rows; it lines up with the last axis.
    • Storing mixed types in one array, which turns everything into slow object or text.
    • Using == to find missing values: np.nan == np.nan is False; use np.isnan.

    04.3 · Tables in code

    pandas fundamentals

    A pandas DataFrame is a table: an index that labels the rows, column names, and one typed column (a Series) per field. You load a file into one, then filter rows, pick columns, add calculated columns, group and sort, each as one readable line.

    Why it matters for analysts

    pandas is where SQL thinking meets Python: WHERE becomes a boolean filter, SELECT becomes a column list, GROUP BY becomes groupby. It handles millions of rows on a laptop and connects to every chart, stats and ML library you will use.

    Anatomy of a DataFrame

    Every column has one dtype: int64, float64, datetime64, bool or object (usually text). Check dtypes first after every load. An amount column with dtype object means something like "$1,204.50" slipped in, and sums will fail or concatenate.

    Filter, select, sort

    Filtering uses a boolean mask: df["status"] == "paid" gives True or False per row, and df[mask] keeps the True rows. Combine conditions with & and |, each wrapped in parentheses. A list of names selects columns, and sort_values orders rows. Try the three on a mini orders table.

    DataFrame operations on orders Try it

    Selecting by label or by position

    Square brackets cover the common cases. For anything more precise, use .loc (by labels and masks) or .iloc (by integer position). Write new values with .loc too, so pandas changes the original DataFrame rather than a temporary copy.

    You wantWriteNote
    One columndf["amount"]Returns a Series
    Several columnsdf[["customer", "amount"]]A list inside the brackets
    Rows matching a conditiondf[df["amount"] >= 50]Boolean mask
    Rows and columns by labeldf.loc[mask, ["customer", "amount"]]Slices include the end label
    Rows and columns by positiondf.iloc[:10, :3]Slices exclude the end, like Python
    Set values safelydf.loc[mask, "flag"] = TrueAvoids chained assignment

    Chains: from file to answer

    Most analyses are a short chain of verbs. Writing them as a method chain, one verb per line, reads top to bottom like a recipe and leaves no half-finished variables lying around.

    import pandas as pd

df = pd.read_csv("orders.csv", parse_dates=["order_date"])
df.info()                      # rows, columns, dtypes, non-null counts
df.head()                      # first 5 rows
df["status"].value_counts()    # how many paid, pending, refunded

by_region = (
    df
    .query('status == "paid" and amount >= 50')
    .assign(net=lambda d: d["amount"] - d["discount"])
    .groupby("region", as_index=False)
    .agg(revenue=("net", "sum"), orders=("order_id", "count"))
    .sort_values("revenue", ascending=False)
)

# the same filter without query()
mask = (df["status"] == "paid") & (df["amount"] >= 50)    # parentheses are required
df.loc[mask, ["customer", "amount"]].sort_values("amount", ascending=False)
    Key ideas
    • A DataFrame is an index plus named, typed columns; each column is a Series.
    • Check df.info() and dtypes right after loading.
    • Filter with boolean masks, select with a list of names, order with sort_values.
    • Use .loc for label-based access and for every assignment.
    • Method chains keep a transformation readable and free of stray variables.
    Common mistakes
    • Writing df[df.a > 1 and df.b < 2]; use & with parentheses around each condition.
    • Chained assignment like df[mask]["flag"] = 1, which may change a copy and leave df untouched.
    • Summing an object column of text numbers; convert with pd.to_numeric first.
    • Forgetting that groupby drops rows whose key is missing unless you pass dropna=False.

    04.4 · Combine and reshape

    Merging & reshaping

    Real questions span several tables, and the table you have is rarely the shape you need. merge joins tables on a key, like SQL JOIN. pivot_table turns a long list of facts into a grid, and melt turns a grid back into a long list.

    Why it matters for analysts

    A bad join is the most common way an analysis silently goes wrong: revenue doubles because a lookup table had duplicate keys, or orders vanish because an inner join dropped unknown customers. Reshaping is how you get data into the form a chart or a model expects.

    Join types and row counts

    how= decides which unmatched rows survive. inner keeps only matches, left keeps every left row, right every right row, outer everything. Unmatched cells become NaN. Always compare row counts before and after a merge.

    The real danger is a duplicate key on the side you expected to be unique. Every matching order is repeated once per duplicate, so sums inflate. Pass validate="m:1" and pandas raises an error instead.

    Merge visualizer Try it
    5 rows

    Long and wide

    Long (tidy) data has one row per fact: region, month, revenue. Wide data spreads one variable across columns: a row per region, a column per month. Long is best for grouping, plotting with seaborn and storing. Wide is best for reading and for spreadsheets.

    pivot only rearranges, so it fails if two rows land in the same cell. pivot_table aggregates those rows with aggfunc (mean by default, so pass "sum" for revenue).

    Pivot and melt Try it
    2 × 3 

    import pandas as pd

# join: every order keeps its row, customer columns are added
merged = orders.merge(
    customers, on="customer_id", how="left",
    validate="m:1",          # raise if customers has duplicate ids
    indicator=True,          # adds _merge: both / left_only / right_only
)
assert len(merged) == len(orders)
merged["_merge"].value_counts()          # how many orders had no customer?

# stack files with the same columns (e.g. one export per month)
all_months = pd.concat([jan, feb, mar], ignore_index=True)

# long -> wide
wide = sales.pivot_table(index="region", columns="month",
                         values="revenue", aggfunc="sum", fill_value=0)

# wide -> long
long = wide.reset_index().melt(id_vars="region", var_name="month",
                               value_name="revenue")
    Key ideas
    • how sets which unmatched rows survive: inner, left, right or outer.
    • Duplicate keys multiply rows; validate="m:1" turns that into an error.
    • indicator=True shows where each row came from.
    • Long data suits grouping and plotting; wide data suits reading.
    • pivot fails on duplicates; pivot_table aggregates them.
    Common mistakes
    • Using an inner join by default and silently dropping orders with unknown customers.
    • Merging on keys with different dtypes ("1" against 1) and getting no matches.
    • Forgetting that pivot_table averages by default when you wanted a sum.
    • Not checking len() before and after every merge.

    04.5 · Hidden state

    Notebooks & reproducibility

    A Jupyter notebook mixes code, output and notes, which makes it perfect for exploring. Behind the page sits a kernel, a running Python process that remembers every variable from every cell you ran, in the order you ran them. The page shows the code; the kernel holds the truth. When the two drift apart, your numbers stop being reproducible.

    Why it matters for analysts

    A number in a deck has to be reproducible next month by you or a colleague. A notebook that only works when cells run in one forgotten order produces numbers nobody can defend. "Restart and run all" is the cheapest audit you will ever run.

    Execution order is state

    The number in In [n] next to a cell is the order it ran. If those numbers don't increase from top to bottom, the outputs on the page came from a history you can't see. A cell that changes data in place, such as adding VAT to a column, gives a different answer every time you rerun it.

    Run the cells below in any order you like. Rerun the VAT cell, run the total before the VAT, or print before computing anything, and watch the kernel's memory.

    Make it reproducible

    Reproducible means someone else, on another day, gets the same numbers from the same inputs. Four habits get you most of the way, and a scripted "restart and run all" proves it.

    # first cell: everything the notebook depends on, in one place
from pathlib import Path
import numpy as np
import pandas as pd

DATA = Path("data/raw")              # relative to the project, never your home folder
VAT_RATE = 0.20
rng = np.random.default_rng(42)      # fixed seed: the same sample every run

# never modify a column in place twice: derive a new one instead
df = pd.read_csv(DATA / "orders.csv")
df = df.assign(amount_gross=df["amount"] * (1 + VAT_RATE))   # safe to rerun

# from a terminal: rerun the whole notebook in a fresh kernel
#   pip freeze > requirements.txt
#   jupyter nbconvert --to notebook --execute report.ipynb
    Key ideas
    • The kernel remembers everything you ran, in the order you ran it, including deleted cells.
    • Execution counts that jump or go backwards mean the page doesn't describe the state.
    • Cells that modify data in place are not safe to rerun; derive new columns instead.
    • "Restart and run all" before sharing is a fast reproducibility test.
    • Pin the environment, use relative paths, keep raw data read-only and fix seeds.
    Common mistakes
    • Deleting a cell that defined a variable, which keeps working until the next restart.
    • Sharing a notebook whose outputs came from an older version of the code.
    • Hard-coding absolute file paths that only exist on your laptop.
    • Overwriting the raw export with cleaned data, so you can never redo the cleaning.

    04.6 · From cells to tools

    Writing reusable analysis code

    The first time you answer a question, a notebook cell is fine. The third time you copy that cell and change one word, you have three versions to keep in sync. Turning the repeated block into a function with parameters gives you one place to read, test and fix, and a report you can rerun on next week's file in seconds.

    Why it matters for analysts

    Most analyst work is recurring: weekly KPIs, monthly reviews, the same cut for a new region. Reusable functions cut that work to a single call, and they make your numbers consistent because every report runs the same logic.

    Copy-paste versus a function

    Look for the parts that change between copies: a region name, a threshold, a date range. Those become parameters. Everything else becomes the function body. A bug fixed in the body is fixed for every report at once.

    From notebook to module

    Once functions settle, move them into a .py file and import them. The notebook shrinks to a short story of calls and charts, the functions can be tested, and a scheduler can run the same code without a notebook at all.

    # src/analysis.py
import pandas as pd

def revenue_report(df: pd.DataFrame, region: str, min_total: float = 100, top_n: int = 3) -> pd.DataFrame:
    """Top customers in one region by total paid revenue.

    Customers below min_total are dropped. Returns columns customer, total.
    """
    totals = (
        df.loc[(df["region"] == region) & (df["status"] == "paid")]
          .groupby("customer", as_index=False)["amount"].sum()
          .rename(columns={"amount": "total"})
    )
    return (totals.loc[totals["total"] >= min_total]
                  .nlargest(top_n, "total")
                  .reset_index(drop=True))

# tests/test_analysis.py  (run with: pytest)
def test_min_total_is_inclusive():
    df = pd.DataFrame({"region": ["West"] * 2, "status": ["paid"] * 2,
                       "customer": ["Ivy", "Jo"], "amount": [100.0, 99.0]})
    out = revenue_report(df, "West", min_total=100)
    assert out["customer"].tolist() == ["Ivy"]
    Key ideas
    • Copy the code a second time? Make it a function the third time at the latest.
    • Whatever differs between copies becomes a parameter, ideally with a sensible default.
    • Functions should take a DataFrame and return a new one, without changing the input.
    • A docstring and a tiny test document what the function promises.
    • Move stable functions into a module that notebooks and scheduled jobs both import.
    Common mistakes
    • Functions that read global variables from the notebook instead of taking parameters.
    • Mutating the input DataFrame inside a function, so calling it twice changes results.
    • One giant function that loads, cleans, plots and emails; keep each step small.
    • Abstracting too early: write it once plainly, refactor when the second copy appears.
    In practice

    While you develop a module in a notebook, run %load_ext autoreload and %autoreload 2 so edits to analysis.py are picked up without restarting the kernel.
