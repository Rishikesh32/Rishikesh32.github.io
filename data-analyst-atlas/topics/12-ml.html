Machine learning for analysts

Machine learning turns past rows with known outcomes into a function that scores new rows, such as which subscribers are likely to cancel next month. As an analyst you rarely need deep learning. You need to frame the question, build an honest training table, read a confusion matrix, segment customers, explain a prediction and know when a SQL query beats a model.

In this area

    Every ML project an analyst runs starts with a business question and ends with someone acting on the output. First you decide whether the question needs a model at all (lessons 01 and 06). If it does, you either predict a labelled outcome with a classifier (02) or find groups without labels with clustering (03). Then you measure the model against a simple baseline on future data (04), explain what drives its scores (05), and check that acting on them actually changes the business number. One running example ties it together: a subscription app's subscribers table and the question "who is about to cancel?"

    12.1 · Framing

    How ML differs from analysis

    Analysis answers a question once: what happened, and why. Machine learning builds a function that answers the same narrow question again and again, one row at a time, for cases where nobody knows the answer yet. "Why did churn rise in March?" is analysis. "Which of today's 50,000 subscribers will cancel in the next 30 days?" is a prediction problem, and that is where ML earns its place.

    Why it matters for analysts

    Stakeholders ask for "a model" when they need a pivot table, and ask for "a report" when they need a score in the CRM. Framing the question correctly is the most valuable ML skill you can bring, and it is mostly an analyst's skill.

    Two different jobs

    An analysis ends with a person reading a number and deciding something. A model ends with a column of scores that a process uses every week, often without a person reading each one. That changes what "good" means: an analysis has to be correct and convincing, a model has to keep being right on rows it has never seen.

    Four kinds of question

    Most business questions fall into one of four shapes. Only two of them usually call for ML, and even those often start as plain analysis.

    ShapeExampleUsual toolOutput
    DescribeHow many subscribers cancelled last month?SQL, pivot tableA number or chart
    ExplainDid the price rise cause more cancellations?A/B test, regression, cohort comparisonAn effect with an interval
    PredictWhich subscribers will cancel next month?Classifier (supervised ML)A score per row
    SegmentWhat natural groups of listeners do we have?Clustering (unsupervised ML)A group label per row

    The shape of a training table

    A supervised model learns from a table with one row per thing you want to score, a set of features (inputs) and a label (the outcome). For churn, a row is one subscriber on one snapshot date. Features look backwards from that date; the label looks forwards.

    Build this table in SQL with one rule: a feature may only use events before the snapshot date. Then stack several monthly snapshots so the model sees many examples of people who did and did not cancel.

    -- one row per active subscriber per monthly snapshot (PostgreSQL)
WITH snapshots AS (
  SELECT s.subscriber_id, d::date AS snapshot_date
  FROM subscribers AS s
  CROSS JOIN generate_series(DATE '2026-02-01', DATE '2026-06-01', INTERVAL '1 month') AS d
  WHERE s.signup_date < d
    AND (s.cancel_date IS NULL OR s.cancel_date >= d)          -- still active that day
)
SELECT
  sn.subscriber_id,
  sn.snapshot_date,
  sn.snapshot_date - s.signup_date                              AS tenure_days,
  (SELECT COUNT(*) FROM sessions AS x
    WHERE x.subscriber_id = sn.subscriber_id
      AND x.started_at >= sn.snapshot_date - INTERVAL '30 days'
      AND x.started_at <  sn.snapshot_date)                    AS sessions_30d,
  (SELECT COUNT(*) FROM tickets AS t
    WHERE t.subscriber_id = sn.subscriber_id
      AND t.created_at >= sn.snapshot_date - INTERVAL '90 days'
      AND t.created_at <  sn.snapshot_date)                    AS tickets_90d,
  s.plan,                                                       -- use a plan-history table if plans change
  CASE WHEN s.cancel_date < sn.snapshot_date + INTERVAL '30 days'
       THEN 1 ELSE 0 END                                        AS churned_30d  -- label looks forward
FROM snapshots AS sn
JOIN subscribers AS s USING (subscriber_id);
    Key ideas
    • Analysis answers a question once for people; ML builds a function that scores every new row for a process.
    • Describe and explain questions need SQL, charts, tests or regression. Predict and segment questions may need ML.
    • A supervised training table has one row per entity per snapshot, features from before the snapshot and a label from after it.
    • A prediction is not an explanation: a model can rank churners well without telling you what causes churn.
    Common mistakes
    • Building a churn model when the stakeholder really wanted to know why churn went up.
    • Using features computed on the export day, after the outcome already happened.
    • Treating a model's most important feature as the cause of the outcome.

    12.2 · Predicting a category

    Classification

    A classifier predicts which category a row belongs to: will this subscriber cancel (yes or no), which plan will this trial user pick. Under the hood it outputs a probability, and you choose the cut-off that turns probabilities into actions. That cut-off is a business decision, not a property of the model.

    Why it matters for analysts

    Churn, lead scoring, fraud flags and "likely to upgrade" lists are all binary classifiers. You will be asked to build them, or to judge someone else's, and the questions that matter are about thresholds, base rates and costs.

    From rows to a risk score

    The model reads one subscriber's features and returns \(P(\text{churn})\), a number between 0 and 1. A threshold turns it into a decision: at or above it, the subscriber gets a retention offer.

    Start simple, then try trees

    Logistic regression (area 10) is the right first model: fast, stable and easy to explain. Gradient-boosted trees (scikit-learn's HistGradientBoostingClassifier, LightGBM, XGBoost) are the usual next step for tabular data because they capture thresholds and interactions on their own. Keep the boosted model only if it beats the logistic baseline on a later month.

    import pandas as pd
from sklearn.compose import ColumnTransformer
from sklearn.preprocessing import OneHotEncoder, StandardScaler
from sklearn.pipeline import make_pipeline
from sklearn.linear_model import LogisticRegression
from sklearn.ensemble import HistGradientBoostingClassifier
from sklearn.metrics import roc_auc_score

df = pd.read_parquet("churn_snapshots.parquet")       # the SQL table from 12.1
num = ["tenure_days", "sessions_30d", "tickets_90d"]
cat = ["plan"]

# split by time: learn from older snapshots, validate on the newest
train = df[df["snapshot_date"] < "2026-05-01"]
valid = df[df["snapshot_date"] == "2026-05-01"]
X_tr, y_tr = train[num + cat], train["churned_30d"]
X_va, y_va = valid[num + cat], valid["churned_30d"]

onehot = OneHotEncoder(handle_unknown="ignore", sparse_output=False)
logit = make_pipeline(
    ColumnTransformer([("num", StandardScaler(), num), ("cat", onehot, cat)]),
    LogisticRegression(max_iter=1000))
gbm = make_pipeline(
    ColumnTransformer([("cat", onehot, cat)], remainder="passthrough"),
    HistGradientBoostingClassifier(max_depth=4, learning_rate=0.05, early_stopping=True))

for name, model in [("logistic", logit), ("boosting", gbm)]:
    model.fit(X_tr, y_tr)
    p = model.predict_proba(X_va)[:, 1]                # P(churn) per row
    print(name, "ROC-AUC", round(roc_auc_score(y_va, p), 3))

    Choosing the threshold

    Each flagged subscriber is either a churner you caught (true positive, TP) or a false alarm (false positive, FP). Each subscriber you leave alone is a missed churner (false negative, FN) or a correct "no action" (true negative, TN). Two ratios summarise the trade-off.

    \[ \text{precision} = \frac{TP}{TP+FP} \qquad \text{recall} = \frac{TP}{TP+FN} \] Precision: of the people you flagged, how many were going to cancel. Recall: of the people who were going to cancel, how many you flagged.

    Lowering the threshold flags more people: recall rises, precision falls, and offer costs grow. Often the threshold is set by capacity instead, such as "the retention team can call 300 people a week", in which case you flag the top 300 scores.

    Churn threshold, confusion matrix and value Try it

    Key ideas
    • A classifier outputs a probability; the threshold that turns it into an action is your choice.
    • Precision is about wasted actions, recall is about missed cases. Moving the threshold trades one for the other.
    • Set the threshold from costs and values, or from capacity (flag the top N).
    • Start with logistic regression and keep a more complex model only if it wins on later data.
    Common mistakes
    • Leaving the threshold at 0.5 because it is the default.
    • Reporting accuracy when only 4% to 20% of rows are positive.
    • Splitting snapshots randomly, so the same subscriber's neighbouring months land in both train and validation.

    12.3 · Finding groups without labels

    Clustering & segmentation

    Clustering groups rows that look alike when you have no label to predict. Give it each subscriber's usage and spend, and it returns a segment number per subscriber. The algorithm finds the groups; you decide whether they mean anything and what to call them.

    Why it matters for analysts

    Segmentation feeds marketing, pricing and product decisions: who gets which email, which plan to promote, which users to interview. A clean, well-named segmentation that people actually use is one of the most visible things an analyst can ship.

    How k-means works

    k-means is the workhorse. You choose the number of groups \(k\). It drops \(k\) centres, assigns every point to its nearest centre, moves each centre to the mean of its points, and repeats until no point changes group. Each round lowers the inertia: the sum of squared distances from points to their centres.

    \[ \text{inertia} = \sum_{i=1}^{n} \lVert x_i - \mu_{c(i)} \rVert^2 \] \(\mu_{c(i)}\) is the centre of the cluster that point \(x_i\) is assigned to. Lower is tighter, but inertia always falls as \(k\) grows, so it cannot pick \(k\) on its own.

    Scale before you cluster

    k-means measures plain distance, so a feature with bigger numbers dominates. Monthly spend in dollars spreads over tens of units while sessions per week spreads over a few, so in raw units two subscribers 6 sessions apart look closer than two subscribers $19 apart. Standardizing each feature (subtract the mean, divide by the standard deviation) lets both count.

    Now run k-means yourself. The points are 88 subscribers from four behaviour groups, and the algorithm works on standardized values. Step through assign and update, watch inertia fall, and try different \(k\) and starting points.

    Choosing k and naming segments

    Plot the best inertia for each \(k\) and look for the elbow, where adding a cluster stops helping much. The silhouette score (from -1 to 1) measures how much closer points are to their own cluster than to the next one. Both are guides; the final test is whether each segment is big enough to act on and different enough to treat differently.

    from sklearn.preprocessing import StandardScaler
from sklearn.cluster import KMeans
from sklearn.metrics import silhouette_score

feats = ["sessions_per_week", "monthly_spend", "tenure_months"]
X = StandardScaler().fit_transform(subs[feats])      # z-scores: every feature counts

for k in range(2, 8):
    km = KMeans(n_clusters=k, n_init=10, random_state=0).fit(X)
    print(k, round(km.inertia_, 1), round(silhouette_score(X, km.labels_), 3))

km = KMeans(n_clusters=4, n_init=10, random_state=0).fit(X)
subs["segment"] = km.labels_

# profile in original units; churn was NOT used to build the clusters
profile = subs.groupby("segment").agg(
    subscribers=("subscriber_id", "size"),
    sessions=("sessions_per_week", "median"),
    spend=("monthly_spend", "median"),
    churn_rate=("churned_30d", "mean"))
profile["share"] = profile["subscribers"] / len(subs)
print(profile.round(2))

    Then name each segment by what it does, and check that the names survive a re-run with a different random seed and next month's data.

    Committed regulars31%11$301.5%Early access, referral asks

    Key ideas
    • k-means alternates assign and update steps until no point changes cluster; inertia falls every round.
    • Standardize features first, or the feature with the largest numbers decides the clusters.
    • Different random starts can end in different groupings; run several (n_init) and keep the lowest inertia.
    • Choose \(k\) with the elbow, silhouette and, above all, whether the segments are usable.
    • Profile segments with metrics that were not used to build them, such as churn.
    Common mistakes
    • Clustering raw dollars next to counts without scaling.
    • Treating clusters as real, fixed "types" of customer rather than a useful summary that shifts over time.
    • Picking k by inertia alone; it always decreases as k grows.
    • Feeding dozens of loosely related columns in, so no segment has a clear story.

    12.4 · Is it any good?

    Evaluating models

    A model is good if it beats a simple alternative on data it has never seen, at the operating point you will actually use. That needs three things: a split that mimics the future, a baseline to beat, and metrics that match the decision, usually how well the model ranks the riskiest customers.

    Why it matters for analysts

    You will often review a model someone else built. Asking "how was it split, what baseline did it beat, and what is precision in the top 10%?" catches most overstated results in a few minutes.

    Test the way you will use it

    A churn model trained in June will score July's subscribers. So validate on months that come after the training months, never on a random sample of rows. A random split lets the same subscriber's May and June snapshots land on both sides, and the score comes out too optimistic.

    Always put a baseline next to the model: the churn rate itself (what random targeting achieves), and the rule the team uses today, such as "no sessions in 14 days or a failed payment". If the model barely beats the rule, the rule may be the better product: cheaper, clearer and easier to trust.

    Ranking metrics: ROC, PR and lift

    Most churn campaigns contact the top N scores, so what matters is ranking. ROC-AUC is the chance that a random churner scores higher than a random stayer (0.5 is random, 1.0 is perfect). The precision–recall curve and its summary, PR-AUC (average precision), focus on the positive class and fall when positives are rare. Lift answers the stakeholder question directly.

    \[ \text{lift}_{\text{top }10\%} = \frac{\text{churn rate among the top 10\% of scores}}{\text{overall churn rate}} \] Example: if 20% of all subscribers churn and 70% of the riskiest 10% churn, lift is 3.5: contacting that group finds 3.5 times as many churners as contacting 10% at random.

    In the demo, the scores of churners and stayers are two overlapping bell curves. Make the model better or worse, and change how common churn is. Notice which numbers move with the churn rate and which do not.

    Calibration and error bars

    If people will read the score as a probability ("73% likely to cancel"), check calibration: among subscribers scored around 0.7, roughly 70% should churn. And treat every metric as an estimate. With 400 churners in the test month, a precision of 0.40 in the top 1,000 has a 95% interval of about ±0.03 (\(1.96\sqrt{0.4 \cdot 0.6 / 1000}\)), so a 0.01 improvement is noise.

    import pandas as pd
from sklearn.metrics import roc_auc_score, average_precision_score
from sklearn.calibration import calibration_curve

p = gbm.predict_proba(X_te)[:, 1]                   # June: the untouched test month
print("ROC-AUC", round(roc_auc_score(y_te, p), 3),
      "PR-AUC", round(average_precision_score(y_te, p), 3),
      "base rate", round(y_te.mean(), 3))

# baseline: the rule the retention team already uses
rule = (X_te["sessions_30d"] < 3) | (X_te["tickets_90d"] >= 3)
print("rule flags", int(rule.sum()), "precision", round(y_te[rule].mean(), 3))

# lift by decile (decile 1 = highest scores)
t = pd.DataFrame({"y": y_te.to_numpy(), "p": p})
t["decile"] = pd.qcut(t["p"].rank(method="first", ascending=False), 10, labels=range(1, 11))
lift = t.groupby("decile", observed=True)["y"].agg(rows="size", churn_rate="mean")
lift["lift"] = lift["churn_rate"] / t["y"].mean()
print(lift.round(2))

# calibration: predicted vs observed churn in 10 bins
observed, predicted = calibration_curve(y_te, p, n_bins=10)

    Key ideas
    • Validate on later months than you train on; open the final test month once.
    • Beat two baselines: random targeting (the base rate) and the current business rule.
    • ROC-AUC ignores how rare churn is; PR-AUC and precision at top N do not.
    • Lift at the top decile is the metric stakeholders understand fastest.
    • Every metric has an error bar; small differences on one test month are noise.
    Common mistakes
    • Random train/test splits on monthly snapshots of the same customers.
    • Reporting ROC-AUC 0.85 on a 2% churn problem without the precision you will get in practice.
    • Tuning on the test month and then reporting the test score as if it were fresh.
    • No baseline, so nobody knows whether 0.80 is good.

    12.5 · Opening the box

    Explaining predictions

    A score of 0.93 is hard to act on by itself. People want to know what drives the model overall, and why this particular subscriber scored so high. Global explanations rank features across all rows; local explanations split one prediction into the contribution of each feature.

    Why it matters for analysts

    Explanations decide whether a model gets used. A retention agent who sees "failed payment, 3 support tickets" next to a score knows to fix the card and apologise, rather than send a generic discount. Explanations are also your best tool for spotting leakage and bias.

    Global: what drives the model overall

    Permutation importance is model-agnostic and easy to explain. Shuffle one column in the validation data, which breaks its link to the label, and re-score. The bigger the drop in your metric, the more the model relied on that column.

    Local: why this subscriber

    SHAP values split one prediction into additive pieces: start from the model's average output and add one contribution per feature until you reach this row's prediction. For a logistic regression the pieces are exact and simple: each feature contributes its coefficient times (its value minus the average value), in log-odds. For tree models, the shap library's TreeExplainer computes the same kind of breakdown.

    The demo uses a small logistic model (example coefficients) so the contributions are exact. Change the subscriber and watch which bars flip from pushing risk up to pushing it down.

    Why is this subscriber at risk? Try it

    What explanations cannot tell you

    A contribution says how the model uses a feature, not what would happen if you changed it in the real world. Support tickets push risk up, but closing tickets faster will not necessarily cut churn: tickets may simply be a symptom of a broken product. To learn what an action does, run an experiment (area 09). Also watch correlated features: if sessions_30d and sessions_7d both exist, importance gets split between them and each can look minor.

    import pandas as pd
from sklearn.inspection import permutation_importance

# global: how much does each column matter on the validation month?
r = permutation_importance(gbm, X_va, y_va, scoring="average_precision",
                           n_repeats=10, random_state=0)
imp = pd.Series(r.importances_mean, index=X_va.columns).sort_values(ascending=False)
print(imp.round(3))

# local, exact for the logistic pipeline from 12.2: coef * (value - average)
prep, clf = logit[0], logit[-1]
Z_tr = prep.transform(X_tr)
z_row = prep.transform(X_va.iloc[[0]])[0]
contrib = pd.Series(clf.coef_[0] * (z_row - Z_tr.mean(axis=0)),
                    index=prep.get_feature_names_out())
base = clf.intercept_[0] + clf.coef_[0] @ Z_tr.mean(axis=0)   # average log-odds
print(round(base, 2), contrib.sort_values(key=abs, ascending=False).round(2))

# the same breakdown with the shap library, drawn as a waterfall
import shap
explainer = shap.LinearExplainer(clf, Z_tr)
sv = explainer(prep.transform(X_va))
shap.plots.waterfall(sv[0])
    Key ideas
    • Global explanations rank features across all rows; local explanations break down one prediction.
    • Permutation importance: shuffle a column, re-score, measure the drop. Use validation data.
    • SHAP-style contributions add up from the average prediction to this row's prediction.
    • Explanations describe the model, not cause and effect; test actions with experiments.
    • A single feature doing most of the work is a prompt to check for leakage.
    Common mistakes
    • Telling stakeholders "tickets cause churn" because tickets have a large contribution.
    • Computing importance on training data, where an overfit model looks like it relies on noise.
    • Comparing raw logistic coefficients across features measured in different units.

    12.6 · Judgement

    When not to use ML

    Most questions an analyst gets are better answered with a query, a chart or an experiment. A model is worth its upkeep only when you need a fresh prediction for many rows, again and again, someone will act on it, you have enough labelled history, and a simple rule cannot do nearly as well.

    Why it matters for analysts

    Saying "a rule gets 90% of the value this week" is often the most useful thing you can say. It ships faster, everyone understands it, and it becomes the baseline any later model must beat.

    A quick decision path

    Ask four questions in order. Each "no" sends you to a simpler tool.

    Start with a rule, then climb only if it pays

    For churn, a two-condition rule often captures much of the value. Write it in SQL, measure its precision on last month's data, and make it the baseline. Each step up the ladder below adds a little precision and a lot of upkeep.

    -- baseline rule: flag low usage or a failed payment
SELECT subscriber_id
FROM subscriber_features
WHERE snapshot_date = DATE '2026-07-01'
  AND (sessions_30d < 3 OR payment_failed_30d);

-- how good was the same rule last month? (labels are known by now)
SELECT AVG(churned_30d::numeric) AS precision, COUNT(*) AS flagged
FROM subscriber_features
WHERE snapshot_date = DATE '2026-06-01'
  AND (sessions_30d < 3 OR payment_failed_30d);
    SituationBetter choiceWhy
    "Why did sign-ups drop in May?"Funnel and segment analysisA one-off explanation, not a per-row prediction
    "Does the new onboarding increase retention?"A/B testCausal question; a model only finds associations
    40 churn events in totalRules plus label collectionToo few examples to learn from or to evaluate
    Scores nobody has a process to useNothing yetAn unused model is pure cost
    Regulated or high-stakes decisionsTransparent rules or a simple model, with reviewYou must be able to explain and audit every decision

    The hidden costs of a model

    A model is a product, not a notebook. It needs a feature pipeline that runs on schedule, retraining as behaviour drifts, monitoring for broken inputs, and someone to answer "why did this customer get flagged?". It can also change the data it learns from: once the team contacts every high-risk subscriber, next year's labels reflect the campaign, not natural churn. Use the helper to test a project idea.

    Should this be ML? Try it

    Key ideas
    • ML fits repeated, per-row predictions that someone acts on, with enough labelled history.
    • Explain and "did it work?" questions need analysis or experiments, not a classifier.
    • A measured SQL rule is the first baseline and often the final answer.
    • Models carry ongoing costs: pipelines, retraining, monitoring and explanation.
    Common mistakes
    • Building the model before anyone has agreed what action a high score triggers.
    • Skipping the rule baseline, so a model's 28% precision has nothing to be compared with.
    • Using a predictive model to answer a causal question like "does the discount work?".
    In practice

    Write a one-paragraph brief before any modelling: the decision, who acts, how often, the baseline rule's measured precision, and the gain that would make a model worth maintaining. If you cannot fill it in, you are not ready to build.
