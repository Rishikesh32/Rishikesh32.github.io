A/B testing & experiments

An experiment is the one tool that tells you what a change actually caused. This area teaches you to design a test, size it, read the result honestly, catch the traps that fool even experienced teams, and estimate effects when you cannot randomize at all.

In this area

    Every lesson here follows one running example: a subscription app wants to ship a redesigned pricing page. About 4% of the people who see today's page start a paid plan within 7 days. You first design the test (who gets randomized and what you measure), then size it so it can detect a change worth caring about. While it runs you guard against peeking, broken splits and novelty. When it ends you read the confidence interval, resist slicing it into twenty segments, and, for the changes you cannot randomize, you reach for quasi-experiments such as difference-in-differences.

    09.1 · Randomize, then compare

    Experiment design

    An A/B test randomly splits people into a control group (A, today's pricing page) and a treatment group (B, the new page). Because a coin flip decides who sees what, the two groups are alike in every way except the page. So if B converts more often than A by more than chance allows, the page caused it.

    Why it matters for data analysts

    Before/after comparisons are polluted by seasonality, marketing pushes and price changes. Randomization is the only design that removes all of those at once. Analysts are usually the ones who write the test plan, pick the metric and unit, and get blamed when the result can't be trusted.

    How a user lands in a group

    Assignment must be random and sticky: the same person should see the same page every time. The standard trick is to hash the user id together with the experiment name into a number from 0 to 99, then send buckets 0 to 49 to A and 50 to 99 to B. Hashing is deterministic, so no lookup table is needed, and adding the experiment name makes each test's split independent of the others.

    import hashlib

def bucket(user_id: str, experiment: str, buckets: int = 100) -> int:
    # same inputs always give the same bucket; the experiment name decorrelates tests
    digest = hashlib.sha256(f"{experiment}:{user_id}".encode()).hexdigest()
    return int(digest[:8], 16) % buckets

def variant(user_id: str) -> str:
    return "A" if bucket(user_id, "pricing-v2") < 50 else "B"

print(variant("u_10482"), variant("u_10482"))   # identical on every call

    Choosing the randomization unit

    The randomization unit is the thing the coin is flipped for: a user, a session or a single page view. Smaller units give you more units and faster tests, but a returning visitor may then see both pages, which confuses them and blurs the effect. As a rule, randomize at the level you analyse: if the metric is "share of users who pay", flip the coin per user.

    Key ideas
    • Randomization makes the groups alike in everything except the change, so the difference in outcomes is causal.
    • Hash the user id with the experiment name for a split that is random, sticky and independent across tests.
    • Write the hypothesis, primary metric, guardrails, unit, size and decision rule before launch.
    • Randomize at the level you analyse; for visible changes that means the user.
    Common mistakes
    • Randomizing page views but analysing users, so many users saw both versions and the standard errors are wrong.
    • Counting everyone who was assigned, including people who never reached the pricing page, which dilutes the effect.
    • Picking the primary metric after seeing which one moved.
    • Reusing the same bucket split for every experiment, so the same users are always in treatment.

    09.2 · How many users, how many days

    Power & sample size

    Small effects hide in noise. If the new pricing page lifts conversion from 4.0% to 4.4%, a test with a few thousand users will usually miss it. Power is the probability that your test detects an effect of a given size when it is really there. You choose the size of effect worth detecting, and the maths tells you how many users that takes.

    Why it matters for data analysts

    Stakeholders always ask "how long do we need to run it?". An underpowered test wastes weeks and ends with "no significant difference", which people then misread as "no effect". Sizing the test up front is the analyst's job, and it often kills a test idea before it wastes anyone's traffic.

    Four numbers in, one number out

    • Baseline rate \(p_1\): today's conversion, here 4.0%.
    • Minimum detectable effect (MDE): the smallest lift worth acting on. A 10% relative MDE means 4.0% → 4.4%, an absolute change of 0.4 percentage points (pp).
    • Significance level \(\alpha\): the false-positive rate you accept, usually 0.05.
    • Power \(1-\beta\): the chance of detecting a true MDE-sized effect, usually 0.8.
    \[ n_{\text{per variant}} \approx \frac{\left(z_{1-\alpha/2} + z_{1-\beta}\right)^2 \,\big[p_1(1-p_1) + p_2(1-p_2)\big]}{(p_2 - p_1)^2} \] With \(\alpha = 0.05\) and power 0.8, \((1.96 + 0.84)^2 \approx 7.85\). For 4.0% → 4.4%: \(7.85 \times (0.0384 + 0.0421) / 0.004^2 \approx 39{,}500\) users per variant.

    The MDE drives everything

    Sample size grows with the inverse square of the effect. Halving the MDE means four times the users, so the most important conversation is "what lift would change our decision?", not "what lift do we hope for?". At 5,000 pricing-page visitors a day, a 10% relative MDE needs about 79,000 users, roughly 16 days. A 5% MDE needs about 309,000, roughly two months.

    Sample size and duration calculator Try it

    Traffic is split 50/50, so each variant gets half the daily visitors. Round the duration up to whole weeks: weekday and weekend visitors behave differently, and a test that covers only some weekdays over-represents them.

    from statsmodels.stats.proportion import proportion_effectsize
from statsmodels.stats.power import NormalIndPower

p1, p2 = 0.040, 0.044                       # baseline and baseline + 10% relative MDE
h = proportion_effectsize(p2, p1)           # Cohen's h (arcsine transform)
n = NormalIndPower().solve_power(effect_size=h, alpha=0.05, power=0.8,
                                 ratio=1.0, alternative="two-sided")
print(round(n))                             # about 39,450 users per variant

daily_visitors = 5_000
days = 2 * n / daily_visitors               # about 15.8, so plan 3 full weeks

    To need fewer users

    Accept a larger MDE, test a bigger change, pick a metric with less variance (conversion rather than revenue per user), or use variance reduction such as CUPED, which adjusts for each user's pre-experiment behaviour.

    What does not help

    Lowering power to 50% just to finish sooner. You then miss half of all real wins, and the wins you do catch overstate the true effect.

    Key ideas
    • Power is the chance a test detects an effect of the MDE size when it is real; 80% is the usual target.
    • Sample size depends on baseline rate, MDE, α and power, and grows with the inverse square of the MDE.
    • Choose the MDE from the business decision: the smallest lift that would change what you do.
    • Duration = total users needed ÷ eligible daily traffic, rounded up to whole weeks.
    Common mistakes
    • Mixing relative and absolute MDE: 10% of 4% is 0.4 pp, not 10 pp.
    • Using all site traffic in the duration estimate instead of only users who reach the pricing page.
    • Reading "not significant" from an underpowered test as proof that the change does nothing.
    • Running until the planned n and then extending "a bit longer" because the result is close.

    09.3 · Estimate, interval, decision

    Reading results

    The test has run its planned three weeks. Control converted 1,600 of 40,000 users (4.00%) and the new page 1,760 of 40,000 (4.40%). The headline is not "B won". It is an estimate with uncertainty: +0.40 percentage points, 95% CI +0.12 to +0.68 pp, p = 0.005. Read the interval first and the p-value second.

    Why it matters for data analysts

    Your write-up decides whether a feature ships. Reporting only "significant, +10%" hides how unsure you are and invites people to bank the point estimate. Reporting the interval lets a product manager see the worst plausible case before committing.

    The confidence interval for a difference

    Each conversion rate has a standard error that shrinks with the square root of its sample size. The standard error of the difference combines both, and the 95% interval is the difference plus or minus 1.96 of those standard errors.

    \[ \hat d = \hat p_B - \hat p_A, \qquad SE = \sqrt{\frac{\hat p_A(1-\hat p_A)}{n_A} + \frac{\hat p_B(1-\hat p_B)}{n_B}}, \qquad \text{95\% CI} = \hat d \pm 1.96\, SE \] Here \(SE = \sqrt{0.04 \cdot 0.96/40{,}000 + 0.044 \cdot 0.956/40{,}000} \approx 0.00142\), so the CI is \(0.40 \pm 0.28\) pp. In relative terms that is a lift of about 10%, plausibly anywhere from 3% to 17%.

    What the p-value says

    The p-value is the probability of seeing a difference at least this large if the new page truly did nothing. To compute it, pool both groups to estimate the shared rate under "no effect", divide the observed difference by that standard error to get \(z\), and read the two tails of the normal curve beyond \(\pm z\).

    Two-proportion result reader Try it

    Keep the rates at 4.0% and 4.4% and move only the sample size. The point estimate never changes, but the interval shrinks with \(\sqrt{n}\) until it clears zero. Significance is a statement about your evidence, not about the size of the effect.

    -- per-variant counts for the primary metric (users exposed to the pricing page)
SELECT e.variant,
       COUNT(*)                                        AS users,
       COUNT(*) FILTER (WHERE s.first_paid_at >= e.exposed_at
                          AND s.first_paid_at <  e.exposed_at + INTERVAL '7 days') AS converters
FROM (
  SELECT user_id, MIN(variant) AS variant, MIN(exposed_at) AS exposed_at
  FROM experiment_exposures
  WHERE experiment = 'pricing-v2'
  GROUP BY user_id                 -- one row per user (users in both variants already excluded)
) e
LEFT JOIN subscriptions s ON s.user_id = e.user_id   -- one row per user: first_paid_at
GROUP BY e.variant;
    from statsmodels.stats.proportion import proportions_ztest, confint_proportions_2indep

conv  = [1760, 1600]                 # B, A
users = [40000, 40000]

z, p = proportions_ztest(conv, users)                 # pooled z test, two-sided
lo, hi = confint_proportions_2indep(conv[0], users[0], conv[1], users[1],
                                    compare="diff", method="wald")
print(f"z={z:.2f}  p={p:.4f}  diff CI=[{lo*100:+.2f}, {hi*100:+.2f}] pp")
# z=2.82  p=0.0048  diff CI=[+0.12, +0.68] pp
    Key ideas
    • Report the difference, its 95% confidence interval and the p-value, in absolute and relative terms.
    • The p-value is the chance of a difference this large if the change did nothing; it is not the chance B is better.
    • Statistical significance (CI excludes 0) and practical significance (CI clears the smallest worthwhile lift) are separate questions.
    • Check guardrail metrics before shipping a primary-metric win.
    Common mistakes
    • Saying "p = 0.005 means a 99.5% chance the new page is better".
    • Banking the point estimate (+10%) in a forecast when the interval runs from +3% to +17%.
    • Calling a wide, zero-crossing interval "no effect" instead of "inconclusive".
    • Running a t-test on per-page-view rows when users were randomized, which overstates the sample size.

    09.4 · Keeping the run honest

    Pitfalls: peeking, SRM & novelty

    Most wrong experiment conclusions come from three traps. Peeking: checking the p-value every day and stopping the first time it dips below 0.05. Sample ratio mismatch (SRM): the split you asked for is not the split you got, which means something in the pipeline is broken. Novelty: users react to anything new, so the first week's lift fades.

    Why it matters for data analysts

    Dashboards make it easy for anyone to watch a test live, and someone will ask "it's significant now, can we ship?". These checks are where analysts protect the company from shipping noise. SRM in particular is a fast, mechanical check that catches bugs nobody else will notice.

    Peeking inflates false positives

    A p-value is only valid for one look at a sample size fixed in advance. The z-statistic of an A/A test (two identical pages) wanders like a random walk as data accumulates. Look once and it lands beyond ±1.96 only 5% of the time. Look every day and stop at the first crossing, and you get many chances to catch a random excursion.

    Peeking simulator: 1,000 A/A tests Try it

    Every simulated test compares two identical pages, so every "win" is a false positive. With one look you get about 5%. With ten looks and the naive rule, about one test in five declares a winner. A sequential design raises the bar at each look so the overall false-positive rate stays at 5%; the Pocock boundary uses one constant bar, and many experimentation platforms offer always-valid p-values built on the same idea.

    Equally spaced looks, stop at first p < 0.051251020
    Chance an A/A test "wins"5%8%14%19%25%
     
    import numpy as np

rng = np.random.default_rng(0)
sims, looks = 10_000, 10
# A/A test: equal batches of data per look; z at look k = (sum of k N(0,1) increments) / sqrt(k)
z = rng.standard_normal((sims, looks)).cumsum(axis=1) / np.sqrt(np.arange(1, looks + 1))

print("one planned look:", (np.abs(z[:, -1]) > 1.96).mean())        # about 0.05
print("peek at every look:", (np.abs(z) > 1.96).any(axis=1).mean())  # about 0.19

    Sample ratio mismatch: the split is a health check

    If you asked for 50/50 and got 50.6/49.4 across 100,000 users, that is not bad luck. A chi-square goodness-of-fit test compares observed counts with the expected split. When p is below 0.001, stop reading the metrics: some users were lost or added unevenly, and the groups are no longer comparable.

    \[ \chi^2 = \sum_{g \in \{A,B\}} \frac{(O_g - E_g)^2}{E_g}, \qquad \text{df} = 1 \] \(O_g\) observed users in group \(g\), \(E_g\) expected users from the planned split. For 50,412 vs 49,183 users: \(\chi^2 \approx 15.2\), \(p \approx 0.0001\). That is an SRM.
    SRM detector (chi-square) Try it 

    from scipy.stats import chisquare

observed = [50_412, 49_183]                         # users logged in A, B
total = sum(observed)
stat, p = chisquare(observed, f_exp=[total / 2, total / 2])
print(f"chi2={stat:.1f}  p={p:.1e}")                # chi2=15.2  p=9.8e-05
if p < 0.001:
    print("SRM: debug assignment and logging before reading any metric")

    Novelty and primacy effects

    Returning users notice a redesigned page and click around out of curiosity (novelty), or resist it because they liked the old one (primacy). Both fade. Plot the daily lift: if it slides steadily, the first week overstates (or understates) the long-run effect. Run long enough to see it flatten, or compare new users only, who have no old habit to break.

    Key ideas
    • Decide the sample size in advance and read once, or use a sequential method built for repeated looks.
    • Ten naive peeks turn a 5% false-positive rate into roughly 19%.
    • Run a chi-square SRM check on every test; at p < 0.001, debug before reading metrics.
    • Plot lift by day to spot novelty or primacy, and run whole weeks.
    Common mistakes
    • Stopping a test early because it "reached significance" on a dashboard.
    • Dismissing a 50.6/49.4 split as "close enough" on 100,000 users.
    • Fixing an SRM by down-sampling the bigger group, which keeps the bias.
    • Shipping on a week-one lift for a change returning users will notice.

    09.5 · More tests, more false wins

    Multiple tests & segments

    The pricing test came back flat overall, so someone slices it by 20 countries and finds that "the new page wins in Canada, p = 0.03". With 20 independent looks at a 5% false-positive rate, you expect one such win from noise alone, and the chance of at least one is 64%. Every extra metric, segment or variant is another ticket in that lottery.

    Why it matters for data analysts

    Segment deep-dives and dashboards with 30 metrics are part of every test readout. Knowing how to correct for multiple comparisons, and when a segment result is a hypothesis rather than a finding, keeps you from shipping a feature for a "winning" segment that was never real.

    The family-wise error rate

    Run \(m\) independent tests at \(\alpha = 0.05\) when nothing is real, and the probability that at least one comes out significant (the family-wise error rate, FWER) grows quickly.

    \[ \text{FWER} = 1 - (1-\alpha)^m \qquad\Rightarrow\qquad m = 20:\; 1 - 0.95^{20} \approx 0.64 \] Assumes independent tests and no real effects. Correlated metrics inflate it less, but still a lot.

    Two ways to correct

    Bonferroni controls the FWER by testing each hypothesis at \(\alpha/m\): with 20 segments a segment needs p < 0.0025. It is simple and strict, so it also misses real effects. Benjamini–Hochberg (BH) controls the false discovery rate instead, the expected share of your "wins" that are false. Sort the p-values, compare the \(i\)-th smallest with \(\tfrac{i}{m}q\), and reject every hypothesis up to the largest \(i\) that passes.

    Segment lottery: false discoveries Try it

    Bars show \(-\log_{10} p\), so taller means smaller p. Segments that truly differ are marked with a ring. Without a correction, null segments regularly cross the line. Bonferroni rarely lets a null through but can miss real effects; BH usually keeps more real ones while letting few nulls through.

    import pandas as pd
from statsmodels.stats.proportion import proportions_ztest
from statsmodels.stats.multitest import multipletests

rows = []
for country, g in users.groupby("country"):          # one row per user: variant, converted
    agg = g.groupby("variant")["converted"].agg(["sum", "count"]).loc[["B", "A"]]
    z, p = proportions_ztest(agg["sum"], agg["count"])
    rows.append({"country": country, "p": p})
seg = pd.DataFrame(rows)

seg["bonferroni"] = multipletests(seg["p"], alpha=0.05, method="bonferroni")[0]
seg["bh"]         = multipletests(seg["p"], alpha=0.05, method="fdr_bh")[0]
print(seg.sort_values("p").head())

    Plan it

    Name one primary metric and at most a few pre-registered segments (for example new vs returning users). Those get the full α; everything else is exploration.

    Explore it

    Unplanned segment wins are hypotheses. Correct them with BH, report them as "worth a follow-up test", and confirm in a new experiment before acting.

    Key ideas
    • Each extra metric, segment or variant is another chance for a false positive: FWER = 1 − (1 − α)m.
    • Bonferroni (α/m) controls the chance of any false positive; it is strict.
    • Benjamini–Hochberg controls the share of false discoveries and keeps more power.
    • Pre-register a primary metric and key segments; treat the rest as hypotheses to retest.
    Common mistakes
    • Slicing a flat test until some segment is significant, then shipping for that segment.
    • Correcting for the 3 segments you report but not the 40 you looked at.
    • Reading many tiny segments as precise: each has a fraction of the users, so its interval is much wider.

    09.6 · Quasi-experiments

    When you can't randomize

    Some changes cannot be A/B tested. A legal review means the new pricing page can only launch in Germany. A TV campaign reaches everyone in a region. A price change must apply to all customers at once. You can still estimate the effect, but you need a comparison group that shows what would have happened without the change, and an assumption that makes that comparison fair.

    Why it matters for data analysts

    "Did the launch work?" is asked about far more changes than ever get an A/B test. A plain before/after chart mixes the launch with seasonality, marketing and everything else that changed that month. Quasi-experimental methods are how analysts give a defensible answer anyway, and say clearly how much weaker it is.

    Difference-in-differences

    Germany (treated) got the new page in March; France (control) kept the old one. Germany's conversion rose from 3.6% to 4.4%, but France also rose, from 4.0% to 4.3%, because spring is a stronger season. Difference-in-differences (DiD) subtracts the control's change from the treated group's change, removing everything both markets shared.

    \[ \widehat{\text{DiD}} = (\bar y_{T,\text{post}} - \bar y_{T,\text{pre}}) - (\bar y_{C,\text{post}} - \bar y_{C,\text{pre}}) = (4.4 - 3.6) - (4.3 - 4.0) = +0.5 \text{ pp} \] The naive before/after in Germany says +0.8 pp. 0.3 pp of that was the season, which France reveals.

    The assumption: parallel trends

    DiD only works if, without the launch, both groups would have moved by the same amount. You cannot test that directly for the post period, but you can check the weeks before launch: if the lines were already diverging, the estimate absorbs that divergence as fake effect.

    Difference-in-differences lab Try it

    The lab is noise-free so you can see each bias on its own. The shared seasonal change fools the naive before/after estimate but cancels out in DiD. An extra pre-trend in the treated market is exactly what DiD cannot remove.

    -- the 2 x 2 table behind a DiD estimate
SELECT country,
       CASE WHEN visited_at >= DATE '2026-03-02' THEN 'post' ELSE 'pre' END AS period,
       ROUND(AVG(converted::int) * 100, 2) AS conv_pct,
       COUNT(*) AS visitors
FROM pricing_page_visits
WHERE country IN ('DE', 'FR')
  AND visited_at >= DATE '2026-02-02' AND visited_at < DATE '2026-03-30'
GROUP BY 1, 2
ORDER BY 1, 2;
    import statsmodels.formula.api as smf

# one row per visit: converted (0/1), treated (DE = 1), post (after launch = 1)
model = smf.ols("converted ~ treated * post", data=visits).fit(cov_type="HC1")
print(model.params["treated:post"])          # the DiD estimate, about 0.005 (0.5 pp)
print(model.conf_int().loc["treated:post"])
# with only two markets, these standard errors are optimistic: say so in the write-up

    Key ideas
    • Without randomization you need a comparison group and an assumption that makes it a fair counterfactual.
    • DiD = treated change − control change; it removes shocks both groups share, such as seasonality.
    • Parallel pre-trends are the assumption to check, by plotting the weeks before launch.
    • Quasi-experiments give weaker evidence than A/B tests; state the assumption next to the estimate.
    Common mistakes
    • Reporting a before/after change as the effect of a launch.
    • Choosing a control group that was hit by its own change in the same period.
    • Skipping the pre-period plot, so a pre-existing trend gets credited to the launch.
    • Trusting tiny standard errors when there are only two markets.
