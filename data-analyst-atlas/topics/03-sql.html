SQL for Analysts

SQL is the foundational lingua franca of data analytics. From querying transaction tables and joining dimension models to calculating rolling cohort retention with advanced window functions, mastering SQL allows you to extract precise, trustworthy answers from relational databases and cloud data warehouses at scale.

In this area

    Writing production SQL requires thinking in sets and understanding the query engine's logical order of operations. The diagram below illustrates how SQL clauses transform raw tables through joins, filters, grouping, and analytical window frames into business metrics.

    03.1 · Query foundations

    SELECT, filtering & sorting

    The SELECT statement retrieves rows and columns from database tables. Writing disciplined queries requires understanding three-valued logic, explicit column projection, and deterministic sorting.

    Column Projection and Three-Valued Logic

    In production analytics, avoid SELECT *. Explicitly naming required columns reduces network bandwidth, memory consumption, and I/O costs. In columnar data warehouses (Snowflake, BigQuery, Redshift), reading unneeded columns directly inflates query billing.

    The NULL and Three-Valued Logic Trap

    In SQL, comparisons with NULL evaluate neither to TRUE nor to FALSE, but to UNKNOWN. Writing WHERE status != 'cancelled' will drop all rows where status is NULL! To safely include them, write WHERE status != 'cancelled' OR status IS NULL, or use COALESCE(status, '') != 'cancelled'.

    Deterministic Ordering

    Without an explicit ORDER BY clause, relational database tables are unordered mathematical sets. The order in which rows return is non-deterministic and can vary between identical query runs. For predictable pagination with LIMIT and OFFSET, always include a unique tie-breaker column (such as primary key id) in the sort list.

    03.2 · Summarizing sets

    Aggregation & GROUP BY

    Aggregations collapse multiple rows into single summary metrics. Mastering GROUP BY semantics and distinguishing between row-level filters and group-level filters is vital for metric computation.

    The Mechanics of GROUP BY

    The GROUP BY clause defines the grain of the output. In standard SQL, every column in the SELECT clause must either be listed in the GROUP BY clause or wrapped inside an aggregate function (e.g. SUM, AVG, COUNT, MIN, MAX).

    SELECT 
  channel,
  DATE_TRUNC('month', order_date) AS order_month,
  COUNT(DISTINCT customer_id)      AS active_customers,
  SUM(revenue)                     AS total_revenue,
  ROUND(AVG(revenue), 2)           AS aov
FROM orders
WHERE status = 'completed'
GROUP BY 1, 2
HAVING SUM(revenue) >= 10000;

    WHERE vs HAVING

    • WHERE: Filters individual candidate rows before aggregation takes place. Cannot contain aggregate functions.
    • HAVING: Filters aggregated group buckets after the grouping and aggregation are computed.

    03.3 · Combining relations

    Joins

    Real business data is normalized across relational entities. Joins allow you to stitch tables together based on shared keys. Knowing the differences between join types prevents subtle data loss and accidental duplicate fan-outs.

    Join Archetypes

    • INNER JOIN: Returns rows only when the join condition matches in both the left and right tables. Unmatched rows in either table are discarded.
    • LEFT (OUTER) JOIN: Preserves all rows from the left table. If no matching row exists on the right, right-side columns are filled with NULL.
    • FULL OUTER JOIN: Preserves all rows from both tables, filling unmatched columns on either side with NULL.
    • CROSS JOIN: Computes the Cartesian product, pairing every row of the left table with every row of the right table (\(N \times M\) rows).

    The Fan-Out Multiplication Bug

    If you join an orders table (1 row per order) to an order_items table (multiple rows per order) on order_id, and then sum orders.total_amount, each order's total is multiplied by its number of items! Always aggregate the child table to the parent grain before joining, or calculate measures at the item grain.

    03.4 · Modular query architecture

    Subqueries & CTEs

    Complex analytical questions require multi-stage data processing. Common Table Expressions (CTEs) transform unreadable nested subqueries into clean, modular, top-down pipelines.

    Common Table Expressions (WITH Clauses)

    CTEs create named temporary result sets that exist only within the execution scope of a single query. They improve maintainability and enable recursive processing:

    WITH first_orders AS (
  SELECT 
    customer_id, 
    MIN(order_date) AS first_order_date
  FROM orders
  GROUP BY customer_id
),
cohort_size AS (
  SELECT 
    DATE_TRUNC('month', first_order_date) AS cohort_month,
    COUNT(customer_id)                    AS new_users
  FROM first_orders
  GROUP BY 1
)
SELECT * FROM cohort_size ORDER BY cohort_month;

    NOT EXISTS vs NOT IN with NULLs

    Always prefer WHERE NOT EXISTS (...) over WHERE id NOT IN (...) when testing for non-existence. If the subquery in a NOT IN statement returns even a single row with a NULL value, the entire predicate evaluates to UNKNOWN, returning zero rows.

    03.5 · Advanced analytical calculations

    Window functions

    Unlike GROUP BY, which collapses individual rows into a single summary row, window functions compute metrics across sets of rows that are related to the current row without collapsing the underlying row grain.

    Core Window Function Classes

    • Ranking Functions:
      • ROW_NUMBER(): Assigns a unique sequential integer (1, 2, 3...) to each row in the partition.
      • RANK(): Assigns ranks with gaps for ties (e.g. 1, 2, 2, 4).
      • DENSE_RANK(): Assigns ranks without gaps for ties (e.g. 1, 2, 2, 3).
    • Value Navigation Functions:
      • LAG(col, 1): Fetches the value from 1 row prior in the partition (ideal for day-over-day growth).
      • LEAD(col, 1): Fetches the value from the next row in the partition (ideal for sessionization).
    • Frame-Bounded Aggregates:

      Compute rolling totals and moving averages with explicit window frames:

      SUM(revenue) OVER (
  PARTITION BY customer_id
  ORDER BY order_date
  ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
) AS cumulative_customer_spend

    03.6 · Scale & optimization

    Query performance

    An analytical query that runs in 2 seconds on a test laptop can bring down a production warehouse when executed against a billion rows. Understanding query planning, indexing, and columnar storage transforms slow queries into snappy pipelines.

    Reading Execution Plans (EXPLAIN ANALYZE)

    Using EXPLAIN ANALYZE reveals how the optimizer executes your SQL. Look out for:

    • Seq Scan (Full Table Scan): The engine reads every page on disk because no suitable index exists.
    • Index Scan / Index Only Scan: The engine traverses a B-tree index directly to the target rows, minimizing I/O.
    • Hash Join vs Nested Loop: Nested loops scale as \(O(N \times M)\) on unindexed columns. Hash joins build an in-memory hash table of the smaller relation for linear \(O(N + M)\) performance.

    Non-Sargable Predicates

    Wrapping an indexed column inside a function prevents the query engine from using an index seek:

    -- SLOW: forces full table scan
WHERE YEAR(created_at) = 2026;

-- FAST: sargable range seek on B-tree index
WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01';
